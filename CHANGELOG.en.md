# Changelog

Version numbers follow [Semantic Versioning](https://semver.org/). During 0.x, incompatible changes may also be released in a minor version (such as 0.2.0).

## 0.5.0 (2026-11-22)

- **Image warnings inside inline boxes and footnote bodies** (HTML and XSL-FO; typesetting results and PDF output do not change; **compatibility changes**: diagnostics and exit codes): 0.4.0 reported nothing for missing images (`image/not-found`, severity error), images that cannot be drawn (`image/unsupported`), images that can be drawn only in part (`image/partial`) and missing references inside SVG (`image/reference-not-found`) inside `inline-block`, `fo:inline-container` and footnote bodies (HTML `float: footnote`, `fo:footnote-body`), because the layouts that measure their content did not report warnings. They are now reported once each, as elsewhere. They are added to `warnings` and `diagnostics`, and the exit codes of `--fail-on error` (missing images) and `--fail-on warning` on the command line change
- **Fixes to PDF/X and PDF/A output** (the PDF does not change when they are not requested; **compatibility changes**: unknown PDF/X versions, PDF/X-1a printing conditions not in the registry, the kinds of profiles, and the check of PDF/X-4 after writing (an error when it does not conform); **the PDF changes**: actions and output intents in PDF/X, and missing glyphs and XMP in PDF/X-4): (1) when the written PDF/X was read back and checked, characters in the glyph data of font files (TrueType streams without the `Length1` length entry) that look like operators (`PS`, `rg` and so on) were taken as operators, so documents using some characters of the default fonts (such as 戀 in bold Mincho and 赥 in Gothic) could not be written with `--pdfx x1a`, `x3` or `x4`. Only the content streams of pages, Form XObjects, patterns, Type3 glyphs and annotation appearances are now checked, and the PDF/A check does the same. The glyphs of Type3 fonts written directly in resources and the streams of annotation appearances (`/AP`) are now checked too, for both PDF/X and PDF/A. (2) The `--pdfx x4` check took structure elements of type `JavaScript` (XSL-FO `role="JavaScript"`) for JavaScript actions and refused to write the PDF; this is fixed. (3) An unknown value for `pdfx.version` in the API (such as `'x4'`; case-sensitive) silently produced PDF/X-3; it is now an option error (`KumioriOptionError` with `option` set to `pdfx.version`), as with `pdfa.version` (leaving it out still means PDF/X-3). (4) Keywords consisting only of separators (XSL-FO `axf:document-info name="keywords" value=","`) wrote an empty `Keywords` entry, and the PDF/A and PDF/X-4 checks stopped with "Keywords in Info differs from XMP"; empty keywords are no longer written. (5) On the command line, the list of places that do not meet the PDF/X or PDF/A rules was printed on one line with `\x0a` in place of the line breaks; each item is now printed on its own line. (6) PDF/X-1a:2001 and PDF/X-4 output, and the check after writing, now follow the text of ISO 15930-1 and ISO 15930-7. PDF/X (X-1a, X-3 and X-4) no longer writes actions (bookmarks keep only their titles and destinations within the document, and destinations pointing outside are dropped; annotations with actions (links to outside, submit and reset buttons) are not written either; the count is given in a `pdfx/actions-dropped` notice, which is not shown by default but appears with `--verbose` or `--diagnostics json` on the command line and in `diagnostics` in the API). The `RegistryName` of the output intent is written only when the printing condition is in the ICC registry (0.4.0 always wrote `http://www.color.org`). For PDF/X-1a, a printing condition that is not in the registry without a profile (`pdfx.profile`, `--output-profile`) is an error (`pdfx/profile-required`). The profile must have an AtoB1 table (A2B1) for PDF/X-1a and be an output device profile (device class `prtr`) for PDF/X-4; otherwise it is an error (`pdfx/profile-invalid`). PDF/X-4 no longer draws characters that have no glyph in the font (.notdef), as with PDF/A and PDF/UA. PDF/X-4 output is now also read back and checked after writing. (7) The XMP packet (PDF/X-4, PDF/A, PDF/UA) now contains about 2,000 bytes of white space so that it can be rewritten later (XMP Specification Part 1 §7.3.2; **the PDF changes**: compared with 0.4.0, only PDF/X-4 changes; PDF/A and PDF/UA are new in 0.5.0)
- **README and documentation reorganized** (typesetting results do not change): the README is now an entry point with highlights, getting started, features and a guide to the documentation. The details moved to new documents: the library guide ([`docs/en/library.md`](docs/en/library.md)), using the web app ([`docs/en/app.md`](docs/en/app.md)), the feature list ([`docs/en/features.md`](docs/en/features.md)), fonts ([`docs/en/fonts.md`](docs/en/fonts.md)), architecture ([`docs/en/architecture.md`](docs/en/architecture.md)) and development and testing ([`docs/en/development.md`](docs/en/development.md)). The Japanese versions are in `docs/`
- **Command reference** (typesetting results do not change): added [`docs/en/cli.md`](docs/en/cli.md) (Japanese: [`docs/cli.md`](docs/cli.md)), which organizes the options of the Node CLI into tables by category (argument, default, description), with common examples, detailed examples with output, environment variables and exit codes; the "Node CLI" section of the README was removed, and the README now has only a one-line example in "Getting started" and a pointer to this reference. The `--help` descriptions of `--lang` and `--font-cache` now match the actual behavior (the locale is looked up in `LC_ALL`, `LC_MESSAGES`, `LANG`, and the Linux cache also honors `$XDG_CACHE_HOME`)
- **CLI `-o` ending with `/`** (typesetting results do not change; **compatibility changes**: an `-o` naming a missing directory with a trailing `/` and an empty `-o` become errors): with a single input, passing a missing directory ending with `/` to `-o` (`-o out/`) wrote a PDF without an extension under the name with the trailing `/` dropped (`out`) and exited with 0. An `-o` ending with `/` (also `\` on Windows) is now taken as a directory: if it does not exist, this is an error (exit code 1); if it exists, `<input name>.pdf` (`.svg` or `.png` with `--format svg` or `png`) is written inside it. The behavior with several inputs (`-o` is the output directory, created if missing) and when an existing directory is given without `/` does not change. With standard input (`-`), an `-o` ending with `/` or naming an existing directory, which used to stop with a write error, is now an error asking for a file name in `-o` (exit code 1). With a single input, an `-o` ending with `/` that names an existing file is an error saying it is not a directory; with several inputs, an `-o` naming an existing file, which printed a stack trace, is now an error message (exit code 1). When `-o` ends with `/` or is an existing directory, the output format is not taken from the `-o` extension (a PDF is written even inside a directory named `d.svg`). An empty `-o` (`-o ''`), which wrote next to the input as if `-o` were not given, is now an invalid-value error (exit code 1)
- **CLI outputs no longer overwrite files the conversion reads, or outputs of other inputs** (typesetting results do not change; **compatibility changes**: an `-o` that writes to a file the conversion reads or to the output of another input becomes an error, and colliding output names change): if an output is a file the conversion reads (the input (including the file behind standard input, when redirected with `< a.fo`), the images, CSS and fonts the document uses, the fonts read from `--font-dir` and `--font-cache`, the files of `--css`, `--font`, `--spot-colors`, `--output-profile`, `--drawio-stencils` and `--plugin`, and the files under a directory given to `--drawio-stencils`; a hard-linked alias counts as the same file) or an output written from another input in the same run, nothing is written and it is an error (exit 1). When the same input is given more than once (`a.html a.html`), it is typeset only once, with a note (previously it was written again as `a-2.pdf`; when several inputs were given, `-o` stays the output directory after they are merged, except that with `-o -` the merged input is written to standard output). When the output is the same as standard output (a file or a pipe), as in `-o /dev/stdout > out.pdf` or `-o /dev/stdout | cat > out.pdf`, the conversion report goes to standard error (previously the report line overwrote the start of the PDF, or was appended to its end, and broke it). On machines whose file systems ignore case (macOS, Windows), the output names of `A.html` and `a.fo` are also treated as colliding. Previously, typesetting `fig.html` with `<img src="fig.svg">` as `--format svg` overwrote the image `fig.svg` with the page SVG (exit 0), and giving `-o` the same name as the input (`-o one.html`) overwrote the input with the PDF (since 0.4.0). When output names collide (`a.html` and `a.fo` in the same directory, for example), later ones now keep the input name with its extension (`a.fo.svg`; if that still collides, `a.html.2.svg`) instead of getting `-2`, `-3` (previously, typesetting a 3-page `a.html` together with `a.fo` as `--format svg` wrote the output of `a.fo` as `a-2.svg`, erasing page 2 of `a.html`; the names of PDF outputs change the same way). `--watch` with `--format svg` or `png` no longer re-typesets a multi-page document over and over (only `a.svg` was excluded from watching, while the files actually written, `a-1.svg` …, triggered re-typesetting). An image whose relative reference contains `%2F` (`<img src="a%2Fb.png">`) no longer stops the command with exit 1 without a PDF; it is warned about as an unreadable image and the document is typeset
- **SVG and PNG output of the same document can be run again** (typesetting results do not change): the "images the document uses" that outputs must not overwrite are now the images the typesetting actually looked up, not every image whose content the library read. Previously, typesetting `a.html` with `<img src="img/a.svg">`, or `b.html` whose text mentions `b.png`, twice with `--format svg` or `png` took the earlier output (matched only by the end of its name, or merely named in the text) as a file the conversion read, and the second run failed (exit 1; with `--watch`, every time). Inputs are now merged only when they are the same name in the same directory (a symbolic link or a hard-linked alias in another directory is a separate input, written next to itself). The files inside a directory given to `--drawio-stencils` and the `--plugin` files are no longer overwritten by outputs either
- **Checks of CLI arguments and library options** (**typesetting results change**: an `.xml` input with `--xhtml` is read as XHTML, not XSL-FO; nothing else changes; **compatibility changes**: the arguments and options below become errors, and the error type of `createFontLoader` changes): if the value of a CLI option that takes a value is the name of another option (`-o --print`), it is taken as a missing value and is an error (exit 1; previously a PDF named `--print` was written). Control characters (such as ESC) in argument error messages are written in a visible form, as in warnings. `--xhtml` now takes effect for `.xml` inputs too (previously `.xml` was read as XSL-FO; since 0.4.0). Numbers for `--image-max-dpi` are now written as for `--dpi` (digits and a decimal point; previously `0x10` and `1e3` were accepted too). Diagnostics for XSL-FO attributes that were not read and for values not in the list of allowed values (`fo/unsupported`) now carry the location (line and column) of the element. Values of the library options `documentLang`, `tagged`, `print`, `pdfua`, `name` and `unreferencedCss` outside their types, and `options`, `setup` or `pdf` that are not objects (such as `null`), are now option errors (`KumioriOptionError`) (previously `documentLang: 123` returned an unreadable PDF without an error, and a `null` `options` gave a raw `TypeError`). When `createFontLoader` of `kumiori/node` cannot fetch a font, the error is now a `KumioriFontError` (`code: font/load-failed`) like the other font errors (previously an `Error` without a `code`). The API reference and [`docs/en/library.md`](docs/en/library.md) now note that when calls with different `TypesetOptions.lang` values run at the same time, the language of the call that started last applies while they overlap
- **Security and robustness against crafted input** (protection of time and memory when typesetting documents written by others on a server; the typesetting results of documents that do not reach a limit do not change (**compatibility changes** and **typesetting results change**: on the command line, documents that refer to files whose names start with `.` under the input directory; see the item on attachment annotations below), and neither do their PDFs except in the items marked **the PDF changes**; limits and their grounds are in the source comments; when a limit is reached, the document is typeset as far as possible and a diagnostic is reported):
  - In tagged PDF tables, the total number of empty cells (`TD`) added to even out the rows is limited to the number of cells in the document or 10,000, whichever is larger (a single cell spanning 1000 columns added 999 empty cells to every other row, and a 4KB document produced a 12.8MB PDF). In a table beyond the limit, each row gets a single empty cell whose column span (`ColSpan`) evens out the columns (diagnostic `limit/table-structure-cells`). Counting the row widths now takes time proportional to the number of cells rather than the number of columns
  - The descriptions (`Contents`) of the annotations of links that span lines or pages in a tagged PDF: the full text of the link was rebuilt and written for every annotation; it is now built once per link, reused, and cut at 2,000 characters (counted after collapsing white space) (diagnostic `limit/link-description`). Long links made the PDF and memory grow as "number of lines × number of characters", and with `--pdfa 3b` the strings exceeded the PDF/A length limit so no PDF/A could be written
  - The actions of the annotations of links that span lines or pages (also in untagged PDF): the full URL was written for every annotation; annotations with the same target now refer to one action (the PDF grew as the number of per-line annotations × the URL length; a link with a 200KB URL and 6,000 words (235KB) took 9.9 seconds and 473MB, now 2.5 seconds and 287MB. Since 0.4.0. **The PDF changes**: in documents with external links (URLs), even short ones, the annotation's action (`A`) is written as a reference to an indirect object instead of a dictionary written directly in the annotation. How the PDF looks and behaves when opened does not change)
  - XSL-FO warichu (`kumiori:warichu="auto"`): whether an `fo:inline` can be a warichu and whether it is inside one are remembered per element and decided from the results of its children and parent (it took time proportional to the square of the number of warichu times the nesting depth; a 27KB document took 19 seconds)
  - Internal entities in the XSL-FO DOCTYPE: the expansion of each entity is built once and reused (referring many times to nested entities that expand to nothing took time growing exponentially with the depth while the length stayed the same; a 1KB document took more than 200 seconds). The limits on the nesting depth (8 levels) and on the expanded length stay as before
  - Re-breaking the last lines of `text-wrap: pretty` paragraphs of more than 100 lines when set one line at a time: at most 200 line lengths are tried per group (for lines very long compared with the font size, such as 1pt text in a 16000pt line, the number of tries grew with the line length and the time with its square; a 49KB document took 57 seconds. In paragraphs whose line length exceeds 200 times the font size (1pt when the font size is smaller than 1pt), the tried lengths are spaced more widely). Also, the length of exactly 3/4 was sometimes not tried because of rounding errors; this is fixed
  - Locations of diagnostics for unsupported and unknown CSS: the text search is done only for the diagnostics that are kept (200 per code; none for codes that are not reported), and lines are looked up in a table of line starts (each item searched the whole CSS and document; a 549KB document with 40,000 unknown CSS properties took 34 seconds)
  - In the lines of the command-line option `--diagnostics json`, DEL and C1 control characters (U+007F to U+009F, including U+0085), U+2028, U+2029, bidirectional marks and controls (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) and the BOM (U+FEFF) from the document are written like `\u2028` (readers that treat them as line breaks split one entry into two lines, and the 8-bit CSI U+009B starts a terminal control sequence). The text output also shows these in a visible form. Line breaks and control characters in input file names are also shown in a visible form in the conversion report and in the error line of an input that could not be typeset (a line break in a name used to start a new line, which could look like a fake line starting with `{`)
  - Table and note structure in tagged PDFs: to decide the scope of header cells (`th`), whether a row has a `td` is checked once per row (a 100KB document with 10,000 `th` in a row took 14 seconds). When numbers are added to IDs of notes (Note) with the same id, the next number is remembered per value (20,000 notes took 18 seconds). When the rows (TR) of tables split by `ends-row` and `starts-row` without `fo:table-row` are built, the list of children of the parent is rebuilt only once at the end. The structure tree and the PDF do not change
  - File attachment annotations (XSL-FO `axf:annotation-file-attachment`): annotations that attach the same file point to a single embedded file (a 14KB document attaching a 1MB file 100 times produced a 100MB PDF. **The PDF changes**: only for documents that attach the same file more than once; the appearance and the attached contents do not change)
  - Custom structure types in XSL-FO (`role`, `axf:pdftag`): types such as `role="JavaScript"` were taken for actions by the PDF/A check, so no PDF could be written with `--pdfa`; this is fixed. Type names with non-ASCII characters (`axf:pdftag="名前タグ"`) are written as PDF names in UTF-8 bytes (characters up to U+00FF were written as one Latin-1 byte and later characters as 4-digit hexadecimal character codes, so readers read them as different names. **The PDF changes**: only for documents that use custom type names with non-ASCII characters)
  - The 127-byte limit on custom structure type names in XSL-FO (ISO 32000-1 Annex C) is counted in UTF-8 bytes instead of characters (Japanese names of 43 to 127 characters were used as they were, and with `--pdfa 3b` the error "a name longer than 127 bytes" stopped the PDF/A output; such names now give a standard type instead of a custom one. **The PDF changes**: only in documents using custom type names of 128 bytes or more in UTF-8 (from about 43 Japanese characters); those elements get a standard structure type. How the PDF looks when opened does not change)
  - References made of `url(` and a long run of spaces (HTML image `src`, and XSL-FO `external-destination`, form submit targets and `axf:annotation-file-attachment`): the regular expression that extracted the content made the leading and trailing spaces and the content compete for the same spaces, taking 8 seconds for a 2 KB value (`<img src="url(`, 2,000 spaces and `x">`) and over 200 seconds for 6,000 spaces. The surrounding parts are now removed before the content is examined (time proportional to the length; the extracted content is the same as before)
  - The columns of an HTML table (the sum of the `span`s of `<col>` and `<colgroup>`) are now limited to 1,000 per table, as in XSL-FO (previously only a single `span` was limited to 1,000, so 1,000 `<col span="1000">` made a million columns and took 3.6 seconds, and 2,500 took 19 seconds and 1.3 GB). The excess columns are dropped, and a new diagnostic `limit/table-columns` (warning) is reported once per table
  - XSL-FO form submit targets (`external-destination` of `axf:form`): absolute paths (`/…`) and UNC paths (`\\host\…`) were written as-is as `SubmitForm` targets. As with the link policy, they are now written only with `links.launch` (`--link-launch`); otherwise they are left out and reported
  - File attachment annotations (XSL-FO `axf:annotation-file-attachment`): matching a file by the end of its name alone is now limited to files passed with a name without a directory, and references pointing outside the document's location (`file:`, absolute paths, `..`) are never matched by name, and are reported as pointing outside the document's location (a path that goes up and back into the input directory, such as `url('../doc/note.txt')`, also counts as outside; variations such as `./` and `//` in paths are normalized on both sides) (previously it matched any file under the input directory by the end of its name, so `url(../../x/.env)` could attach another `.env`; since 0.4.0). The command no longer passes files under the input directory whose names start with `.` (such as `.env`) as the document's files, as with directories starting with `.` (**compatibility changes** and **typesetting results change**: 0.4.0 skipped only directories starting with `.`. An image whose name starts with `.` (`<img src=".dot.svg">`) becomes a missing image (`image/not-found`), and a style sheet (`<link href=".s.css">`) silently does not apply. To use such a file, name its path with `--css`, or give it a name that does not start with `.`)
  - Deep nesting: values with `calc(` nested 5,000 levels deep (CSS, XSL-FO, SVG) and XHTML nested 4,000 levels deep exhausted the call stack (`RangeError`), so the whole document could not be typeset. Parentheses and functions inside `calc()` are now limited to 64 levels (deeper values are ignored as invalid), and rewriting XHTML no longer uses the call stack to walk the nesting
- **Long footnotes on multi-column pages** (XSL-FO and HTML; **typesetting results change** for documents whose multi-column pages reference a footnote that does not fit below the referencing line, and for documents where the rest of a long footnote carries over to the next page): in a multi-column document (`column-count` in HTML, `column-count` on `fo:region-body` in XSL-FO) with footnotes placed at the bottom of the page (the area spanning all columns), a footnote longer than the space left below the referencing line (but short enough to fit on a page) was reserved whole, shrinking the columns to a few lines. The referencing line then kept moving to the next page, page after page held only two lines per column, and on a later page the footnote was drawn over the body lines. Such a footnote now starts on the page of the reference, and the rest is split by lines and continued at the top of the footnote area of the following pages (XSL 1.1 §6.12.3, CSS GCPM 3 §2; as on single-column pages). The footnote area never overlaps the body lines. A footnote inside a before-float (the entry below) is split in the same way (the reference position is taken at the float's anchor in the column; the float stays at the top of its page and the rest of a footnote that does not fit continues on the next page, rather than moving the float and the footnote together to the next page). When the continuation of a footnote from the previous page is carried over again to the next page, the footnotes referenced on the page still start on the page of the reference (before, once one continuation was carried over, all the footnotes of the page were carried over too, so footnotes referenced while a long footnote was continuing moved away from the page of the reference; with a height limit on the footnote area (`max-height` in `@footnote`) they are still carried over in order, as before). On the pages added after the end of the body, continuations that cannot be split (such as one-line footnotes) were stacked whole, so the footnote area grew taller than the body area and its top lines went off the page and disappeared without a warning; such a continuation now goes to the next page when the page already has footnotes, and one that does not fit on a page with nothing else is placed with the overflow warning. The relayout that decides the height of the footnote area (the reservation for each page) now settles the pages from the front (before, the reservations only grew, so a reservation made for footnotes in the first layout stayed after the body moved, leaving pages with a few body lines and no footnotes, adding pages and "a line does not fit on the page" errors). However, in a multi-column document with more footnote text than fits on a page, the relayout of the reservations can swing between raising and lowering and settle on the larger one, leaving an almost blank page (0.4.0 does the same). On a page with body text, the reservation leaves the height of one body line. The limit on relayouts is raised from 6 to 16 (a long multi-column document with many footnotes can take about twice as long to typeset)
- **Floats and absolutely positioned boxes inside HTML inline elements** (HTML, in every style; **typesetting results change** only for documents with a float or an absolutely positioned box inside an inline element): (1) floats (`float: left`, `right` and so on) inside inline elements (`em`, `span`, warichu and so on) are now laid out (CSS 2.1 §9.5). Before, they disappeared with their content and without a warning. They are placed in the enclosing block, and one written inside a paragraph is placed at the height of the start of that paragraph (as when it is written directly in the paragraph). A float inside an inline element that contains blocks (such as a `div` inside a `span`) is, for now, placed after those blocks (not at the height where the float is written). Floats inside a footnote body (`float: footnote`), an element moved to a running header (`position: running()`) and flex and grid items (including items of `inline-flex` and `inline-grid`) are laid out inside it (in the footnote area, the margin box or the item; a float written directly in a footnote was already laid out in the footnote area). (2) absolutely positioned boxes (`position: absolute`, `fixed`) and floats inside inline elements now inherit the font size and other inherited properties from their parent inline element in the document tree (CSS 2.1 §6.2; before, they inherited from the enclosing block). For example, the text of an absolutely positioned box inside a `span` with `font-size: 6pt` changes from 12pt to 6pt, and its position changes with the text size
- **Pages can be written as PNG** (new feature; typesetting results and PDF output do not change): the API's `result.renderPageToPng(page, { dpi, guides })` and the command's `--format png` (can be omitted when `-o` ends with `.png`), `--dpi <value>` (96 by default) and `--pages` turn typeset pages into PNG (8-bit RGB on white paper; up to 40 million pixels per image, beyond which a `RangeError` is thrown). It works in the browser and in Node and rasterizes by itself with no added dependencies (each shape is computed only over its own area, with anti-aliasing). Glyphs come from the font outlines, SVG images are the same shapes as in the PDF, and color glyphs are drawn too. Apart from how the edges of glyphs and lines are anti-aliased, it matches the same page's PDF rendered with pdftocairo. A text-heavy A4 page at 150dpi takes about 0.5 seconds. CMYK JPEG and interlaced PNG images are not drawn and a warning is given. Decoded images are kept up to 100 million pixels in total per typeset result and reused across pages (an image used as the background of many pages is not decoded again for each page; large images that together exceed the 100-million-pixel memo may be decoded again for each page when placed alternately, still within the per-page limit), and images decoded for one page may total up to 400 million pixels (reducing a kept original-size image to another size counts its original pixels too; images after that are not drawn, with a `png/image-limit` warning; this is counted separately from the work limit below, so decoding 400 million pixels of images can take about 50 seconds for JPEG: four 100-million-pixel JPEG images on one page take about 48 seconds for A4 at 96dpi). The work of rasterizing one page (the sum of the pixels in the bounding box of each shape, the edges crossed on each scanline, the work of sorting them and so on) is limited to 128 times the number of pixels in the page plus 64 million (beyond that, the rest is not drawn, with a `png/raster-budget` warning; SVG images that could not be finished are drawn as placeholder boxes). Opacity groups and mask contents are drawn on layers only as large as their contents (the layers held at once are limited to 8 times the number of pixels in the page (but not less than 16 million pixels) and to 64 million pixels (1GB); deeper nested opacity groups beyond that are drawn without a layer, applying the opacity to each shape inside (overlaps inside get darker), and masks and color glyph compositing beyond that are not drawn, with a `png/layer-limit` warning; the limit is checked before a layer is allocated, so a small HTML file with deeply nested opacity boxes no longer uses several GB); the coverage of the intersection of nested clips counts toward the same limit (at 4 bytes per pixel, as a quarter of a layer pixel; no array is made when the new clip fully covers the area of the outer clip), and a deeper clip beyond it is drawn with the outer clip only when it encloses the outer clip (its own edge is not applied), and otherwise its contents are not drawn, with a `png/clip-limit` warning (before, a 1.6KB HTML file with 60 nested full-page boxes with `overflow: hidden; border-radius: 1px` used 2.4GB at 300dpi), and a pattern tile with the same content is drawn once per page (tiles kept up to 16 million pixels in total). Strokes outside the area being drawn are skipped without building their outlines (an SVG with 200 fine dashed lines outside the area being drawn took about 5 seconds before, and about 0.03 seconds now). Decoded images are identified by their content (data: images inside SVG are reused across pages too). Links, annotations and form fields are not drawn. The work count does not include that the work per pixel of a gradient with many color stops (such as a fine `repeating-linear-gradient`) grows with the number of stops, so when rasterizing documents written by others, put a time limit on it from outside ([`docs/en/cli.md`](docs/en/cli.md), "Limits and memory"). The languages matched against SVG `systemLanguage` (`--svg-lang`) and the content of SVG `foreignObject` have no effect on PNG and SVG output (`switch` chooses by the language of the runtime, and `foreignObject` content is not drawn; the PDF draws them)

- **Warichu (inline cutting notes)** (HTML and XSL-FO; new feature; documents that do not use warichu are typeset as before): typesets a note in two lines of characters smaller than the main text inside a line (JLREQ §3.4). Neither standard CSS and XSL-FO nor the extensions of other formatters have a way to write it, so it is written with Kumiori extensions: `-kumiori-warichu: auto` on an inline element in CSS (the initial value is `none`), and `kumiori:warichu="auto"` on `fo:inline` in XSL-FO (namespace `https://github.com/n-lights-co/kumiori/ns`; the declaration `xmlns:kumiori` is required, and a document without it is an XML error whose message explains how to declare it). The size of the warichu characters is the font size of that element. The brackets around it are set with `-kumiori-warichu-brackets` and `kumiori:warichu-brackets` (`auto` = full-width parentheses, `none`, or two strings), at twice the size of the warichu characters, with no space between a bracket and the adjacent character. The two lines are divided at the line-break opportunity nearest to the middle of the content, and the second line is not made longer than the first (when the line-breaking rules prevent a division near the middle, the second line is made one character longer or starts with a character that must not start a line, so that the line of the main text does not overflow). There is no hyphenation inside a warichu. The center of the two lines is aligned with the center of the main text characters, and the line height does not change (also in HTML quirks mode (documents without a DOCTYPE), a warichu counts in the line height as a box containing characters, so lines with only a warichu are not set closer). A warichu that does not fit on one line of the main text is divided at the end of the line and continued on the next line or page, and the part on each line is divided into two lines separately (brackets only at the first and last parts). The opening bracket is not put at the end of a line, nor the closing bracket at the start of a line. Vertical writing (the first line on the right) is also supported. In a right-to-left paragraph (`dir="rtl"` and so on), when the brackets are at a right-to-left level (the surrounding text runs right to left), the opening bracket is put on the right and the closing bracket on the left (with mirrored glyphs; UAX #9 L4), and the outer side of each bracket (the right of the opening one, the left of the closing one) is trimmed (before, the brackets faced outward and the closing bracket overlapped the adjacent character; this is for horizontal writing only, and warichu in right-to-left paragraphs in vertical writing are as before). Ruby inside a warichu is set at the size of the warichu characters, and only when there is ruby over the base characters of the second line (or ruby under the first line), a gap of the ruby's size is left between the two lines (the warichu may then extend above and below the line of the main text by that much). Boxes that are not characters, such as images and inline-blocks, are not typeset inside a warichu, and a warning is reported. For a warichu inside a warichu, the inner one is not made a warichu, and a warning is reported. A warichu whose content is only white space is not made a warichu. `-kumiori-warichu: auto` has no effect on elements that are not inline elements (`display: inline`), and a warning is reported. The border, padding, margin and background of the warichu element are put outside the warichu including its brackets, as for other inline elements, and vertical padding and borders are not counted in the line height. A warichu that spans lines follows `box-decoration-break` (slice puts none on the divided side; clone puts them on each line). In tagged PDF it becomes a Warichu structure element (content WT, brackets WP; ISO 32000-1 §14.8.4.4). See section 9.2 of the HTML and CSS volume and section 4.6 of the XSL-FO 1.1 volume of the Conformance Guide
- **Tagged PDF** (HTML and XSL-FO; new option; typesetting results do not change): `--tagged` on the command line and `tagged` in the API put the document structure and reading order into the PDF (ISO 32000-1 §14.7, §14.8). Tags are added by default (see the item above). Table rows with missing cells are padded with empty TD elements so that all rows have the same number of columns. Ruby becomes Ruby (base text RB, annotation RT), and emphasis marks are artifacts. Top and bottom margin boxes and fo:region-before and fo:region-after become Header and Footer pagination artifacts. Annotations other than links go into Annot and form fields into Form structure elements, with a description (TU) on the field. It cannot be combined with `--pdfx x1a` or `x3`. The structure types (H2, P and so on) and reading order of absolutely positioned elements (`position: absolute`), spanning headings (`column-span: all`) and boxes in an orthogonal writing mode (such as a vertical paragraph in horizontal text) are kept (they used to lose their types and become text directly under the document, and absolutely positioned elements were read at the end of the document). Ruby inside `aria-hidden` becomes an artifact, base text and annotation alike (it used to get marked-content numbers (MCID) that were not in the structure tree)

- **Order of SVG `filter` and `clip-path`, `mask` and `opacity`** (**typesetting results change**: only SVG with a `filter` and a `clip-path`, `mask` or `opacity` on the same element or an ancestor, when drawn on Node; browsers rasterize the whole SVG and were already right): `filter` was applied to the shapes after clipping, masking and opacity; it now follows the specified order (filter → clipping → masking → opacity; Filter Effects 1 §5, CSS Masking 1 §2), on the shape-approximation path, the pixel path and the transparency-flattening path of PDF/X-1a and X-3 alike. Examples: a red rectangle clipped by a circle of radius 10 and dilated by 5 with `feMorphology` was a circle of radius 15 → a circle of radius 10 (as in Chromium). A rectangle with `opacity="0.4"` and `feFuncA type="discrete" tableValues="0 1"` drew nothing → an opaque rectangle drawn at 0.4. With `opacity=".5"` and `feDropShadow`, the shadow showed through the shape → the shadow and the shape are made translucent together. Also, a masked image (an image with transparency, such as a filter result computed in pixels) is put in a transparency group before the mask is applied (the image's SMask replaced the soft mask of the graphics state, so the mask had no effect; ISO 32000-2 §11.6.5.3). - **Speed of documents with many rules whose rightmost part is `*`** (HTML, and `<style>` in SVG written directly in HTML and in SVG images; which declarations apply to which elements does not change): rules whose rightmost compound is a bare `*` with a descendant or child combinator on its left (`*:nth-child(3n+3) *`, `g > *` and so on) cannot be narrowed by the rule index (the rightmost id, class or element name), and were matched for each element by walking its ancestors, so the work grew as the number of rules × the number of elements × the depth of ancestors (25 seconds for 1000 such rules and 20,000 shapes split into 200 `g` elements, in SVG written directly in HTML). The answer for such a rule depends only on the element's parent and is the same for siblings, so it is now matched once per parent and reused for the siblings (3 seconds for the same document, about the same as typesetting it without the rules). For rules with an element name and so on in the rightmost part, the answer for the part left of the rightmost compound (the part that walks the ancestors) is likewise reused for siblings with the same parent (1000 rules of `*:nth-child(kn+k) span` and 20,000 `span` elements: 24 seconds → 8 seconds). When drawing in Node): the shifted copy dropped the pattern or gradient, so a pattern became a flat fallback gray (128, 128, 128) and a gradient a flat area of its last color. The pattern or gradient is now shifted together with the shape (as in Chromium; Filter Effects 1 §9.19). The same holds for PDF, for flattening transparency in PDF/X-1a and X-3, and for PNG output. For pattern-filled shapes that are also blurred, the strokes that widen the shape to approximate the blur are no longer drawn (a pattern cannot be used for strokes, so they made a gray edge)
- **Overlapping children of an SVG element with a `mask`** (**typesetting results change**: only SVG with two or more overlapping shapes inside an element with a `mask` (`g` and so on), SVG with a `mask` on a single shape with both fill and stroke, SVG with shapes whose stroke width does not scale (`vector-effect="non-scaling-stroke"`) inside a `mask` (masks inside groups and groups inside masks too; PDF), SVG with nested `mask`s (PNG), and SVG with a shadow `filter` (`feDropShadow` and so on) around an element with a `mask`, when drawn in Node; PDF and PNG): (1) the mask was applied to each child shape (and separately to the fill and the stroke of a single shape with both), so where the mask was faint, the color under an overlapping child showed through (the lower child was faintly visible under the upper one). The mask is now applied once to a transparency group of the children (CSS Masking 1 §7.1: a mask applies to the rendered element; as in Chromium). When the children include shapes whose stroke width or size does not scale (`vector-effect`), the mask is applied to each child as before. (2) In PDF, strokes whose width does not scale inside a mask (including masks inside groups and groups inside masks) were drawn without dividing by the scale at which the SVG is placed. (3) In PNG, the outer mask of nested masks was applied twice and came out fainter. (4) Shadows approximated with shapes (copies shifted by `feDropShadow` and so on) were cut by the masks and clip paths at the original position. Shadows now move together with the masks and clip paths of the descendants (Filter Effects 1 §9.19; as in Chromium), and a group with a mask is copied as a group with the mask applied once, in the shadow copies too
- **Order of relayouts in the app** (app; typesetting results do not change): when a new load started while the previous one was waiting for fonts, hyphenation patterns or images (for example after changing settings in quick succession), the result of the previous load could finish later and be shown over the new one. Loads now carry a generation mark, and the result of an older load that finishes after a newer one has started is not shown. Earlier bugs are fixed as well: adding a font while an HTML document was shown went back to the XSL-FO opened before, opening only MathML re-laid out the previous XSL-FO, and changing settings or adding images, fonts or shape libraries while a document was being opened went back to the previous document. The document now shown is re-laid out (a document being opened is laid out with the settings at the time its loading starts)
- **Balancing the last page of page columns** (HTML; typesetting results do not change except for the heights of the column boxes): with `column-count` on `body` or the like, short content with no more lines on the last page than columns (a one-line paragraph, for example) was typeset in full but warned "a line does not fit on the page". When finding the column height for the last page of columns that span pages, a height at which lines overflow the columns was taken as fitting, and the column height was lowered to nearly 0. Now a height at which more lines or boxes overflow an empty column is not taken as fitting (CSS Multi-column 1 §7.1). Lines and glyphs stay where they were, and the column boxes become as tall as the lines (since before 0.4.0)
- **SVG with `isolation: isolate` and children with blend modes in PDF/X-1a and X-3** (**typesetting results change**: only such SVG in PDF/X-1a and X-3): when flattening transparency, groups with opacity 1 are opened and their children are drawn directly, but isolated groups (`isolation: isolate` and so on) with `mix-blend-mode` children were opened too, so the children were also blended with what lies under the group and their colors changed (a `multiply` blue inside the group on green became nearly black, for example). Now groups with children that have blend modes are not opened, and the whole group is turned into an image (Compositing and Blending 1 §3.3, §5.3). Groups without such children are opened and drawn as before (no transparency group is written)
- **Checking the content fetched from draw.io's distribution** (`fetchStencils`, `--fetch-drawio-stencils`; typesetting results do not change): the shape libraries (`js/stencils.min.js`) and images fetched from the default source (the URL of the v24.7.5 tag in draw.io's public repository) are checked against the SHA-256 list for v24.7.5 that Kumiori holds, and files that do not match or are not in the list are not used, with a warning (a tag can be moved). Nothing is checked when you choose the source yourself (`stencilsUrl`, `--drawio-stencils-url`). See "Checking fetched shape libraries and images" in [`docs/en/drawio.md`](docs/en/drawio.md)
- **Line wrapping style `text-wrap-style`, `text-wrap-mode` and the `text-wrap` shorthand** (HTML; new feature; documents that do not use them are typeset as before): CSS Text 4 §5.1, §5.4 and §5.5 (W3C Working Draft 2026-08-14) are now read (they were reported as unsupported properties and ignored). `balance` evens out the remaining space of the lines without changing the number of lines (the lines are cut again at the shortest length that keeps the number of lines; separately for each group divided by forced line breaks; a group of more than 10 lines is the same as `auto`). `pretty` and `avoid-short-last-line` choose the lines looking at the whole paragraph (the Knuth–Plass method: the breaks with the smallest total badness of squeezing and spacing; breaks that leave the last line shorter than 1/4 of the line length are avoided; a paragraph never gets more lines than when set one line at a time (only the number of lines is compared, so a paragraph can become slightly taller when more of its lines hold larger characters); in a paragraph of more than 100 lines when set one line at a time, only the last 4 lines are cut again when the last line is short). Setting such a paragraph takes about 2 to 3 times as long. `stable` is the same as `auto`. With every value, the rules for line-breaking prohibitions (kinsoku), squeezing, hanging punctuation and hyphenation stay the same (a line cut again at a shorter length keeps its line-end punctuation inside the line instead of hanging it when it fits in the line length, and the last line of a paragraph is not justified). `text-wrap-mode: nowrap` and `text-wrap: nowrap` stop wrapping (`white-space: nowrap` and `pre` also set `text-wrap-mode` to `nowrap`: §3). They are also read in page-margin boxes (`@top-center` and the like). A paragraph with lines beside a float and a paragraph with `::first-line` are set as `auto`. Added section 6.14 to the HTML and CSS volume of the conformance manual and removed the properties from the list in chapter 16. The text of that volume (except inside the examples) is now set with `text-wrap: pretty` (the page counts of both languages do not change). An element with only `white-space-collapse` now inherits the parent's no-wrap setting (it used to replace `white-space` and wrap). Invalid values of shorthands (`text-wrap`, `text-decoration`, `font` and so on) are discarded without a warning, like invalid values of other properties (they used to be reported as unknown CSS properties)
- **Diagnostics (kinds and severities of warnings) and error types** (API; typesetting results, PDF output and the texts and order of `warnings` do not change (except for the image warnings inside measured layouts; see the item on them); **compatibility changes**: the form of the warning lines the command writes to standard error, the `name` of errors (option errors change from `TypeError` to `KumioriOptionError`), and the type and text of XML errors in XSL-FO and XHTML (from xmldom's `ParseError` to `KumioriInputError`)): typesetting results now have `diagnostics` (the results of `typeset` and `typesetToPdf`, and Area Trees with diagnostics). They hold the same events as `warnings`, with a code (`code`, such as `css/unknown-property`; not changed across versions), a severity (`severity`: `error`, `warning`, `info`), the text, the embedded values (`args`) and the number of identical occurrences (`count`). Unsupported and unknown CSS and XSL-FO and characters with no glyph are one diagnostic per item. Up to 200 diagnostics are kept per code, and the rest are gathered into one diagnostic, "n more warnings of the same kind (m distinct) were omitted" (`args.omitted` and `args.omittedKinds`). Errors thrown by Kumiori are now `KumioriError` and its subclasses (`KumioriInputError`, `KumioriLimitError`, `KumioriFontError`, `KumioriPdfError`), which carry a code `code`, and invalid options throw `KumioriOptionError`, which extends `TypeError` (`isKumioriError` tells them apart; `AreaTreeFormatError` is a subclass of `KumioriInputError`). Error messages are unchanged, and `name` is now the name of the type (XML errors in XSL-FO and XHTML such as unclosed elements, which used to throw xmldom's `ParseError` as is, now throw a `KumioriInputError` with "XML parse error: …", like other parse errors). The codes are listed in `docs/en/diagnostics.md`. A diagnostic has its location in the input `source` when known (file, line, column, element, the Area Tree `sourceRef`, the PDF page): the line and column of the element for XSL-FO, the line and column of the element inside Node and Web Workers for HTML, and the first place written for unsupported and unknown CSS properties (the browser app now reads XSL-FO with @xmldom/xmldom, the same as the library). The command prints one line per diagnostic as "warning [code] file:line:column (element): text" (error, warning or info by severity; this replaces the former "warning: text", and unsupported and unknown specifications get one line per item), and prints notices (`info`) only with `--verbose`. `--diagnostics json` prints one JSON object per line (an error that stops typesetting an input is also printed as one line, with `name`, `code` and `severity: "fatal"`). Frequent diagnostics are condensed in the text output: characters with no glyph go on one line listing the 20 most frequent, and other codes are printed up to 20 lines each followed by one "n more … (m distinct)" line (JSON keeps one line per diagnostic). Diagnostics can be suppressed by code (`diagnostics: { ignore }` in the API, `--ignore-warning` on the command line), and the command's `--fail-on error|warning` exits with code 2 when there is a matching diagnostic. The warnings column of the browser app shows the severity mark, code, element and page, and clicking a line with a page moves to that page. The warnings column of the browser app also shows diagnostics about limits hit while reading (`limit/table-structure-cells` for table structure in tagged PDF). The command-line options `--format svg` and `png` do not build the structure tree (so diagnostics that only concern tagged PDF are not reported)

## 0.4.0 (2026-11-19)

- **Centring with `auto` left and right margins** (HTML, every style. **Typesetting results change**): the margins were made lengths from the estimate of the containing block width at import time, so inside a table cell (where the estimate is close to the whole table width) the margins went into the content width that decides the column widths, and that column took most of the table while the other columns shrank to their minimum width (the same for boxes with a fixed width inside `<td align="center">` and `<center>`). When the place was narrower than the estimate, the margins did not shrink and the box overflowed. The margins are now shared out from the width of the place at layout time, and count as 0 when measuring the content width (CSS 2.1 §10.3.3, §10.3.7, §17.4, CSS Sizing 3 §5.1). Other changes: (1) a table with a fixed width and collapsed borders (`border-collapse: collapse`; tables in the default style `kumiori` are collapsed too) centred with `margin: 0 auto` or `align="center"` moves right by the width of its outer border, and the space left and right is now equal (it was shifted left by the part of the border that sticks out; 0.75pt for a table with `border="1"`, 6pt for a 6pt outer border) (2) a table with only `margin-left: auto`, and absolutely or fixed positioned boxes with `left`, `right` and `width` all set, go to the right (they stayed on the left) (3) floated tables and `display: inline-table` tables are not centred by `auto` margins (they were centred; in CSS 2.1 §10.3.5 and §10.3.9 `auto` margins are 0) (4) inside right-to-left text (`direction: rtl`), a box or table wider than its place overflows to the left (it overflowed to the right; by the rule of §10.3.3 the `auto` margins become 0 and `margin-left` is solved again, as in Chrome) (5) a box inside a vertical parent is centred top to bottom by `auto` in `margin-top` and `margin-bottom` (the left and right `auto` were read) (6) a box or the rest of a table that runs onto a page of a different width (such as after `:first`) is centred again for the width of that page (it kept the margins of the first page)
- **The base of percentages** (HTML, every style. **Typesetting results change**): percentages in `width`, `max-width`, `min-width`, `padding`, `margin` and `text-indent` (and `calc()` with percentages) were made lengths from the estimate of the containing block width at import time (which takes off only what normal-flow blocks take), so inside floats, inline-blocks, absolutely positioned boxes, flex and grid items, columns of a multi-column box and table cells the width of the outer box was the base, and boxes overflowed (a `width: 50%` box in a column of `columns: 2` took the full column width; `width: 50%` in a 100pt grid column was 150pt). For an element that names a page with `page` (`@page body { margin: … }`), the base was also the page area of the unnamed `@page`. They are now resolved at layout time against the actual containing block where the box is placed (CSS 2.1 §10.2, §8.3, §8.4, §10.4, CSS Paged Media 3 §10.1; in vertical text the base of `padding` and `margin` is the height of the containing block, CSS Writing Modes 4 §7.2; inside a page-margin box the base is the margin box). When measuring the content width, percentage widths count as `auto`, `padding`, `margin` and minimums as 0, and maximums as none (CSS Sizing 3 §5.2.1). Also: (1) percentages in `width` and `max-width` of images are resolved against the width of the box that sets the line (the default style's `img { max-width: 100% }` now works inside grid columns and columns of a multi-column box; it was resolved against the body width and the image overflowed the column) (2) a table or image with `width="100%"` in a cell of an auto-layout table does not widen the outer table (it widened the column of that cell nearly to the page width; as in browsers) (3) the column count from `column-width` and percentages in `column-gap` are decided by the width at layout time too (`columns: 40pt` in a cell about 110pt wide: 3 columns → 2) (4) percentages of normal-flow blocks in the body are the same as before
- **Pages with different margins, and fixed boxes** (HTML, every style. **Typesetting results change**: only documents with pages whose margins or sizes differ by `:first`, `:left`, `:right` or named pages): percentage widths and margins, and the position and size of fixed boxes (`position: fixed`), were decided on the page area of the unnamed `@page`, so on a `:first` page with wider margins a `width: 100%` box and fixed boxes overflowed the body area. They are now decided on the page area of the page where the box is placed, and a box that runs over pages is resolved for each fragment with the width of its page (CSS Paged Media 3 §3, CSS Fragmentation 3 §5.1; fixed boxes are placed again on each page)
- **Content widths (min-content and max-content)** (HTML, every style. **Typesetting results change**): boxes sized by their content (columns of auto-layout tables, floats, inline-blocks, `width: max-content` and so on) counted the following wrongly. (1) A block whose width is given as a length inside a cell of an auto-layout table was counted by the length of its lines, not by the width of the box (the box overflowed the cell). The outer width of the box (width and margins) is now counted. Percentage widths count as `auto`, and `max-width` and `min-width` given as lengths limit the content width (CSS Sizing 3 §5.1, §5.2.1) (2) the max-content width of a list (`ul`, `ol`, elements with `display: list-item`) in a cell was counted as the full length of the measuring line (the whole table width), so the other columns shrank to their minimum width.   - flex containers shrink image items (they did not, and the image ran into the next item). The height of the shrunk image stays the height of the attribute (as in Chrome; CSS Flexbox 1 §9.7): in a 200pt wide container, an image with 600×400 attributes and `min-width: 0` next to a 150pt item went from 200×133.3pt to 50×300pt. An image with `flex: 0 0 100pt; min-width: 0` (also `flex-basis: 50%`) went from 200×133.3pt to 100×300pt
  - flex also shrinks images with `overflow: hidden`, images with a length `min-width` (`min-width: 40pt` in the example above gives 50×300pt), and, even without a next item, images with `min-width: 0` whose own padding, border and margin make the item wider than the container (160×300pt with 10pt padding, a 5pt border and a 5pt margin)
  - an image item with a width (also by attributes) in a flex container is placed without shrinking below its automatic minimum size (only the item width was shrunk and the image ran into the next item: in a 200pt wide container, an image with `width: 150pt` next to a 150pt item makes the next item shrink to 50pt; CSS Flexbox 1 §4.5)
  - the automatic minimum size of an image that is itself a flex item is limited by a length `max-width` (it was not, for images whose size is not known while importing, such as `data:` SVG: a 300×200px image with `flex: 0 0 30%; max-width: 50px` went from 225pt (running into the next item) to 37.5pt; as in browsers; CSS Flexbox 1 §4.5)
  - an image with `flex: 1` grows, and its height stays the height of the attribute (it did not grow: in a 200pt wide container, an image with 20×10 attributes went from 15×7.5pt to 200×7.5pt; as in Chrome; CSS Flexbox 1 §9.7)
  - an image with attributes widened by `min-width` or `min-height` keeps the other size of the attribute (it was widened by the aspect ratio: an image with 100×50 attributes and `min-width: 150pt` went from 150×75pt to 150×37.5pt, and with `min-height: 100pt` from 200×100pt to 75×100pt; as in browsers; CSS 2.1 §10.4)
  - an image with attributes for which the author writes only `max-height` has only its height limited (it was shrunk by the aspect ratio: an image with 600×400 attributes and `max-height: 100pt` in a 500pt wide place went from 150×100pt to 450×100pt; as in browsers). When the default style's (`kumiori`) `max-width` shrinks the width too, the aspect ratio is kept as before (150×100pt in a 200pt wide place)
  - for `min-*` and `max-*` on an image with only one size given, the given size is changed only by its own `min-*` and `max-*`, and the other comes from the aspect ratio and then gets its own `min-*` and `max-*` (an image with a 2:1 aspect ratio and `width: 40pt; max-height: 10pt` went from 20×10pt to 40×10pt; CSS 2.1 §10.4, §10.3.2, §10.6.2)
  - images that cannot be read and SVG without a size are sized by the aspect ratio of the attributes (an image with 200×100 attributes and `width: 100pt; height: auto` went from 100×75pt to 100×50pt; HTML §15.4.3)
  - `width="0"` and `height="0"` (and 0 in CSS) are valid sizes (0 was taken as no size, and the image was drawn at its natural size; CSS 2.1 §10.2)

(1) Lengths such as `em` and `rem` in `background-size` (the background image was drawn at its natural size as if no size were given: an icon with `background: url(icon.svg) no-repeat 0.65em center / 1.25em 1.25em` was drawn large over the text; CSS Backgrounds 3 §2.9; percentages and `auto`, `cover`, `contain` stay as they are) (2) lengths in `em`, `rem`, `calc()` and `var()` in `box-shadow` and `filter: drop-shadow()` (the shadow was not drawn) (3) `calc(percentage ± length)` in `border-radius`, `background-position` and `background-size` (they were dropped) (4) percentages, `calc()` and font-size keywords in declarations of page-margin boxes, `@footnote`, `::footnote-call` and `@page` (`@top-center { font-size: 150% }` stayed at 10pt). `em` in a page-margin box is based on the font size of the page context (`@page`) (5) percentages in `letter-spacing` and `word-spacing` are relative to the font size (CSS Text 4 §8.1, §8.2; they were relative to the containing block width, and letters were spaced far apart)

Gradient backgrounds of `@page` read `background-size` and repetition too. Gradient backgrounds of `html` and `body` are drawn on the page like other backgrounds (they were not drawn; CSS Backgrounds 3 §2.11.1)
- **Area Tree types** (typesetting results do not change): to carry the `calc(percentage ± length)` above, the area types were widened. The radii in `corners` of `borderRadius` may now be a sum of a percentage and a length, `{ pct, len }` (`pct` is the percentage number, 10 for 10%; `len` is in pt; they were only lengths or percentage strings; the type is `RadiusLength`). `backgroundImage` (and the images in `under`) gained `xOffset` and `yOffset` (lengths added to percentage positions) and `widthOffset` and `heightOffset` (lengths added to percentage sizes), and `fitPosition` of image areas gained `xOffset` and `yOffset` (lengths added to percentage positions; all in pt). The version of the Area Tree JSON (3) does not change

The type of the `toPdf` options is now exported as `PdfOptions` (unchanged in content)

From the second pass on, the static content is laid out and the pages are turned into area trees as each page-sequence is finished, to collect the fonts and images used (collected again if the pass does not settle). After the passes settle, the document is laid out once more to write the PDF. The PDF and the warnings are the same as with reuse. For the FO of the PostgreSQL documentation (3,231 pages), the maximum live heap goes from about 2.3GB to about 0.9GB (the most is used while reading the FO; it can be typeset with a 1GB heap limit), and the time from 160 s to 231 s (with a 4GB limit)

An author's `html { font-family: … }` or `html { text-align: … }` used to be overridden by the default value on `body` and never reached the document (the browser default style sets neither on `body`, so in a browser the author's value applies; CSS Cascade 4 §6.1, §7.2). Documents that set neither, or set them on `body`, do not change. The Python 3.14 documentation typeset with Sphinx's print CSS (`html { font-family: Fira Sans }`) now has its body text in Fira Sans instead of the default font (Tinos)
- **vertical-align of inline boxes** (typesetting results change for HTML documents that set the values below on inline text elements): `vertical-align: top`, `bottom`, `middle`, `text-top` and `text-bottom` are now read for non-replaced inline boxes (`span`, `::before` and so on; CSS 2.1 §10.8.1; horizontal lines. Previously they were all silently aligned to the baseline. `top`, `bottom` and the others were already read for images). An inline box is the line-height box (the first available font's ascent and descent plus the half-leading). `top` and `bottom` align the box of the element and its contents (the aligned subtree, per line fragment) with the top or bottom of the line box, and widen the line if it is taller. `middle` aligns the box's centre with the parent's baseline plus half the x-height, and `text-top` and `text-bottom` align the box's top or bottom with the top or bottom of the parent's content area. The "•" in the table of contents of Sphinx's print CSS (`font-size: 30pt; line-height: 10pt; vertical-align: bottom`) now sits in the middle of the line instead of floating above it, and no longer widens the line (as in WeasyPrint and Chromium). Images and inline-blocks that are themselves `top` or `bottom` inside a `top` or `bottom` element are not put in the outer element's subtree, and each is aligned by its own value
- **@page padding** (typesetting results change only for HTML documents that set `padding` in `@page`): the padding of the page box (`padding` and the four sides such as `padding-top`) is read, and the body area shrinks by it. Margin boxes (`@top-center` and so on) sit in the page margin, so they do not move. Before, it was ignored (with `@page { padding-top: 1em }` of the Sphinx print CSS, the body started just below the page margin, about one line higher than WeasyPrint). Percentages are against the page width for left and right, and against the page height for top and bottom. Negative values are invalid

Before, it was looked up by the part after the last `#` (`b`), so table-of-contents entries whose links do not resolve still got page numbers (such as `href="#document-tutorial/interpreter#invoking-the-interpreter"` in the table of contents of Sphinx single-file HTML; such references now give "?" and a warning, like other missing references)
- **Percentages of top and bottom for relative positioning** (typesetting results change only for HTML documents that set `top` or `bottom` as a percentage on a `position: relative` box): when the height of the containing block is definite, the box is offset by that percentage of the height. With a containing block of indefinite height, it stays auto (no offset) as before. The height counts as definite for boxes whose `height` is a length, and for flex items stretched to the container height (items with auto height and stretch in a one-line container whose line has the container height). The containing block is the nearest block ancestor (CSS 2.1 §10.1). The `height` of inline elements and of `display: contents` elements is not used (inside inline elements, boxes are still not offset). Flex and grid items, however, are block boxes even when their `display` is an inline value (such as a `span`), so they become containing blocks (CSS Display 3 §2.7). Before, percentages were not read and the box was not offset
- **WeasyPrint behaviour** (typesetting results change only for HTML documents typeset with `--style weasyprint`): to match WeasyPrint, (1) lines that hold only empty markers (such as `<span id="…"></span>`) break margin collapsing (the margins before and after are added; the other styles collapse them as the CSS specification says), (2) `target-counter()` references whose target is not found give empty text (the other styles give "?"; both warn), and (3) when a wrapping flex container (`flex-wrap: wrap`) of definite height has a single line, the line gets the container height whatever `align-content` is (the other styles do so only for `align-content` `normal` and `stretch`, as the specification says). In documents with the Sphinx print CSS, the space before headings, the deeper table-of-contents entries and the position of the cover title become the same as in WeasyPrint

(1) Border longhands of margin boxes (such as `@top-right`): `border-bottom-width`, `-style`, `-color`, and `border-width`, `border-style`, `border-color`. Before, only the shorthands (`border`, `border-bottom` and so on) were read, and borders written with longhands were not drawn (the line under the header of the Sphinx print CSS). (2) Translucent border and background colors of margin boxes are drawn over what is below, instead of as an opaque color mixed with white paper. Background color names (such as `red`) are read too (before, only colors starting with `#`). (3) Longhands of the `@footnote` separator (such as `border-top-width`), and the `margin` and `padding` shorthands
- **Properties of the page context, margin boxes and @footnote** (typesetting results change only for HTML documents that use the properties below): properties of CSS Paged Media 3 Appendix A that apply to the page context and margin boxes, and were not read, are read now. (1) `border` of `@page` (shorthands and longhands; the initial width is `medium`; drawn inside the page margin, and the body area shrinks by its width) and `outline`, (2) `background-image` of margin boxes (url() and gradients, also via the `background` shorthand; the initial position is the top left) and `outline`, (3) `min-width`, `max-width`, `min-height` and `max-height` of margin boxes (the widths of the boxes on the top and bottom edges are redistributed with the three boxes together), (4) `max-height` of `@footnote` (the upper limit of the footnote area height in CSS GCPM 3; footnotes beyond it move to the next page. The limit is not applied on footnote-only pages added after the end of the body; §2.4.2)
- **Initial width of borders of margin boxes and the footnote separator** (typesetting results change only for HTML documents that set a border (such as `border: solid`) without a width on margin boxes (such as `@top-center`) or on the `@footnote` separator): a border without a width gets the initial `medium`, the same as for document elements (CSS Backgrounds 3 §3.3). The width goes from 1.5pt to 2.25pt. With `--style ah`, `thin`, `medium` and `thick` of margin boxes are 1, 3 and 5pt (the same as for document elements; the footnote separator is 2.25pt). Borders whose width is given as a length do not change

In documents that wrap everything in one box (such as `div.book` of DocBook HTML), the named pages of the front matter, part title pages and the index (with their running heads and page number styles) now take effect. Enclosing boxes are split at the switch; the start margin and border stay on the first fragment and the end ones on the last. In the split fragments, `height`, `min-height`, `max-height` and `aspect-ratio` apply to the first fragment only, and boxes with `box-decoration-break: clone` also get their border and padding at the splits (CSS Break 3 §5.3, §5.4). Before, the style argument was not read and the target page's own numbering was used
- **Page number reference text on pages reused in re-layouts** (typesetting results change only where the error below appeared, in documents with page number references typeset in the default mode (not `--low-memory`)): in the re-layouts that settle page number references (`fo:page-number-citation` in XSL-FO, `target-counter()` in HTML), when the pages of the previous pass were reused and only the reference text was replaced, characters shifted by one could appear where the value had a different number of digits ("1" and "3" alternating where "13" should be, with the link rectangle one character too narrow). - **Position of background images of @page and margin boxes** (typesetting results change only for HTML documents with a background image in `@page`, a margin box or the root element (html, body)): the position, the size (percentages, `cover`, `contain`) and the origin of repetition of the `@page` background image are determined inside the page margin and border (the padding area of the page box) (CSS Paged Media 3 §3.1; CSS Backgrounds 3 §2.8, §2.9; it is still painted up to the bleed). Before, one format for the whole document was used for every footnote
- **Continuation pages for footnotes and floats** (typesetting results change only for documents whose continuation of footnotes and floats after the body runs beyond 50 pages): the pages added after the end of the body for the continuation of footnotes and floats are no longer cut off at 50 pages; pages are added until the continuation has been placed (0.3.0 dropped what went beyond 50 pages; in single-column flows and multicol alike). When no progress is made because footnotes or floats cannot be placed on any page (what is carried over does not change for 3 pages in a row), it stops, with a warning giving the number of footnotes and floats dropped. As a safeguard, the number of pages is limited to twice the sum of the number of indivisible units (lines and boxes without children) of the footnotes carried over and the number of floats carried over (not less than 50 pages). Splitting a footnote with a very large number of lines (such as 200,000) no longer stops with an exception (RangeError) (a bug since 0.3.0)
- **Border widths of the default style** (typesetting results change for borders whose width is not a whole number of px, in HTML documents typeset with the default style `kumiori`): border widths are not snapped to pixels (a `0.3pt` line is drawn 0.3pt wide and a `1pt` line 1pt; a PDF has no screen pixels). The styles that follow browsers (`browser`, `browser-margin`, `vivliostyle`) still round. In documents with many thin borders, line positions and page breaks change (the English conformance guide goes from 127 to 125 pages)
- **hsl() and hsla() in XSL-FO** (typesetting results change only for XSL-FO documents typeset in compatibility mode (`--compat antenna`) that use `hsl()` or `hsla()` for colors): these Antenna House extension color functions are read (only a hue without a unit (degrees) is read, and values with a unit (`deg`, `turn`, `rad`, `grad`) are reported as unreadable colors; saturation, lightness and alpha are 0%–100% or 0.0–1.0). Before, they were dropped as unsupported colors. In spec mode they are reported as values read only with the compatibility option
- **The lh unit in XSL-FO** (typesetting results change only for XSL-FO documents that use `lh` in lengths): in compatibility mode (`--compat antenna`), any length (`space-before`, `space-after`, `margin-*`, positions, sizes and so on) is read relative to the line height of the element (`font-size` is relative to the parent's line height; it cannot be used in `line-height`, which is not read and is reported; before, only border widths were read, and other lengths were dropped as unsupported). - **Warnings for missing targets** (no change to the typeset result): warnings for missing targets of page number references (`target-counter()`, `fo:page-number-citation`) and bookmarks are grouped into one line per kind (the count and the first 10 ids). Before, one line per id was given, which came to thousands of lines in documents with many references to missing targets
- **Condensing in XSL-FO (overflow="condense")** (typesetting results change only for XSL-FO documents typeset in compatibility mode with `overflow="condense"` on `fo:block-container`): this Antenna House extension is read. When the content exceeds the height to fit in, the font size or the line height is reduced to fit, by the methods of `axf:overflow-condense` (`font-size` (default), `line-height`). The height to fit in is the height of a container whose `height` or `max-height` is definite (also in table cells, list item bodies and `fo:static-content`, and in absolutely positioned containers; `min-height` if `max-height` is less than `min-height`). A container of indefinite height is fitted into the body area (one page) if it is a keep-together container in the body flowing onto pages; otherwise it is not condensed and a warning is given. Font sizes given as absolute values inside are not changed (a font size written on the container itself is condensed). Inner condensing containers are not changed by the outer condensing. Nor are the font size and line height of elements with `axf:overflow-condense="none"` (`fo:inline`, `fo:block` and so on) and their content. Lower limits are `axf:overflow-condense-limit-font-size` (a length) and `-limit-line-height` (a ratio to the font size), with an initial value of 0. A method with a lower limit reduces down to the limit, and if the content still does not fit at the end, it is left overflowing with a warning (with `hidden` or `error-if-overflow` after the limit, it is clipped, with the box height set to `height`, or without it to the height to fit in, but not less than `min-height`; `repeat` is reported as unsupported). A method without a lower limit that cannot make the content fit at all does not reduce (if no method makes it fit, it is left overflowing with a warning). `axf:overflow-condense` (except `none`) and `-limit-*` are inherited by child elements. In nested condensing, the result of condensing the same container under the same conditions is reused, and the number of content measurements made for the inner containers is limited per outermost condensing container (the larger of 10,000 and 40 times the number of nodes inside that container; ordinary nesting of two or three levels does not hit it however many inner containers there are). When the limit is hit, the remaining containers inside that container are laid out without condensing, and one warning is given only if containers that do not fit because they were left uncondensed this way remain in the result placed on the pages (other outermost containers are still condensed; condensing containers in static content laid out on every page are counted afresh on each page, so they do not hit the limit however many pages there are). Before, it was unsupported and the content overflowed. Condensing in vertical writing, `font-stretch`, `letter-spacing` and condensing in `fo:inline-container` are reported as unsupported. In spec mode it is not read and is reported
- **Breaks and span="all" in XSL-FO multi-column containers** (**typesetting results change** only for XSL-FO documents with `page`, `even-page` or `odd-page` of `break-before` / `break-after`, or `span="all"`, inside an `fo:block-container` with `axf:column-count` (the Antenna House extension for multi-column layout); in spec mode and in compatibility mode): (1) `page`, `even-page` and `odd-page` inside the columns are page breaks (XSL 1.1 §7.20.1, §7.20.2, §4.8: the first (last) area generated by the FO is placed first (last) on a page). Before (since 0.3.0), `page` was a column break to the next column on the same page, and `odd-page` and `even-page` went to the next page without a blank page (of the wrong parity) when the current page already had the requested parity, and to the next column on the same page otherwise. Now the remaining columns are left empty and the content continues in the first column of the next page (a blank page is inserted when the parity does not match, and the page master with `blank-or-not-blank="blank"` applies to it), and the column set before the break is not balanced. Page breaks in `break-before` of the first child and `break-after` of the last child of the multi-column container become breaks before and after the container (before, they had no effect). Inside a multi-column container with a fixed height (which cannot continue across pages), they are column breaks (before, `odd-page` and `even-page` left columns empty for the blank page, and the content after them overflowed the box and was lost) (2) Blocks with `span="all"` are placed across the width of the container and split the columns before and after them also in multi-column containers that continue across pages (before, only containers that fit on one page were split, and in containers that continued across pages they were placed inside a column). `span="all"` inside nested blocks is also brought up directly under the container and takes effect (following the product's samples; before, it had no effect, and in spec mode, where the content of the container is wrapped in a block for the container's indents, `span="all"` on its children did not take effect either). The pieces of the split blocks and containers are treated as continuations of the same FO (`id` is kept on every piece, and `fo:page-number-citation-last` gives the page of the last piece; `text-indent` applies only to the first line of the first piece). `break-before="column"` at the head of the first column of a new column set does not leave a column empty (the break condition is already satisfied) (3) Multi-column layout with `column-count` on `fo:region-body` already followed these rules and does not change
- **keep-together and the spaces at the start and end of columns in XSL-FO multi-column containers** (**typesetting results change** mainly for XSL-FO documents that use an `fo:block-container` with `axf:column-count` / `column-count` (the Antenna House extension for multi-column layout), in spec mode and in compatibility mode. The changes for HTML multi-column layout, multi-column layout of `fo:region-body` and XSL-FO documents without multi-column layout say so at the start of the line. How fitting in a single column is measured, and other details, are in the "Multi-Column Layout" section of `docs/en/xslfo-import.md` and section 12.3 of the HTML and CSS volume of the Conformance Guide):
  - when balancing the columns of a multi-column container, a block, block-container or table with `keep-together.within-column="always"` (also `within-page` and `keep-together="always"`) is not split across two columns if it fits in a single column (before, balancing lowered the columns and broke it at the column boundary: a container holding only a four-line block went from 2 + 2 lines to 4 lines in the first column; XSL 1.1 §7.20.3). Content that does not fit in a single column is still split and stays on the page as before
  - `space-before` / `space-after` with `conditionality="discard"` (the default) at the start and end of the columns of a multi-column container are discarded (the columns are treated as reference areas; XSL 1.1 §4.3.1, §6.5.3): in a container starting with `space-before="10pt"`, the first line of the first column sat 10pt lower than that of the second → at the same height. `space-after="20pt"` of the last block of a column is discarded, and the block after the container moves up by 20pt. `retain` spaces, `margin-top` and `margin-bottom` are kept as before
  - the same spaces are discarded at the start and end of the area of a block with `span="all"` in a multi-column container (before, `space-before` / `space-after` around the span block and `space-before` at the head of the following column set were kept: a span block surrounded by 10pt spaces moves up by 10pt, and the first line of the column after it, with `space-before="8pt"`, by 28pt)
  - a `discard` `space-before` of a multi-column container moved to the head of the next page because little room is left on the page is discarded (before, it was kept at the head of the next page: a container with `space-before="10pt"` moves up by 10pt; XSL 1.1 §4.3.1)
  - when checking whether the line at the head of a column of a multi-column container fits, the space discarded there is not counted (before, balancing made the columns taller by that space: a container with three lines and a three-line block with `space-before="20pt"` went from 56pt to 36pt high). This also fixes the last row of a table split across two columns sometimes disappearing (a four-row table in compatibility mode, with `space-before` on the blocks in cells with borders, went from 2 + 1 rows and a warning to 2 + 2 rows)
  - HTML multi-column layout (`columns`; every style): a block or table with `break-inside: avoid` / `avoid-column` is not split across two columns by balancing if it fits in a single column (before, it was split: a four-line block with `break-inside: avoid` went from 2 + 2 lines to 4 lines in the first column; CSS Fragmentation 3 §3.3). Content that does not fit in a single column is still split as before
  - HTML multi-column layout with `--style ah`: the space discarded at the head of a column (`margin-top` of `p` and the like) is not counted when checking whether a line fits in the column (before, lines sometimes overflowed the balanced columns and disappeared, with the warning that the content does not fit in the multi-column container: a nine-line paragraph in three columns went from 2, 3 and 2 lines (two lines lost) to 3, 3 and 3 lines)
  - multi-column layout of `fo:region-body` (`column-count`): `margin-bottom` of a block with `span="all"` is kept in compatibility mode too (it was discarded: after a span block with `margin-bottom="10pt"`, the lines of the columns move down by 10pt; spec mode keeps it as before)
  - XSL-FO documents without multi-column layout: a `space-before` of the first block of the flow, discarded at the head of the page, is not counted when checking whether a line fits on the page (before, the bottom of the page was left empty by that space and lines were moved to the next page: a 16-line paragraph starting with `space-before="100pt"` went from 13 + 3 lines on two pages to one page; XSL 1.1 §4.3.1)
- **XSL-FO drop caps (`axf:initial-letters`)** (new feature; **typesetting results change** only for XSL-FO documents with `axf:initial-letters`, in both the spec and the compatibility mode): the Antenna House drop-cap extension is now read (before, it was reported as unsupported, the letter was not enlarged, and a leading image stayed at its own size in the line). The first letter of an `fo:block` (with the punctuation around it; a word-initial Dutch `IJ` counts as two letters) or its first image is set several lines tall at the start of the line, and the following lines flow beside it, with the same mechanism as HTML `initial-letter`. Values read: the number of lines (`<number>`), a length (`<length>`), the number of lines to sink (`<integer>`, `drop`, `raise`), `adjacent` and `<integer2>` (also indent lines after the drop cap) of `axf:initial-letters`; `axf:initial-letters-end-indent` (space after the drop cap per line), `-first-line-head-height` (`cap-height`, `x-height`, `auto`: align to the x-height when lowercase small caps follow), `-width`, `-text-align`, `-color`, `-leading-punctuation="hide"` and `-leading-punctuation-position="hang"` (the `dcem` and `ic` units in these lengths are read in every mode). The `text-indent` of the block holding the drop cap shifts the drop-cap box (the `dcem` unit is read only in the compatibility mode; the spec mode reports and ignores it). Blocks after a block shorter than the drop cap's lines are also indented beside the drop-cap box (with `adjacent` too, as far as the box reaches); a block with a gap (`space-before`, `space-after` and so on) between it and the previous block, and a block with `clear`, is moved below the drop-cap box. Right-to-left horizontal text puts the drop cap at the right edge, and vertical writing is also set. Nothing happens when an `fo:block` with `axf:initial-letters`, an `fo:inline-container` and similar come before the letter, or when `text-align` is other than `start`, `left` or `justify`. Not supported (reported as warnings): the size and color of leading punctuation (`<length>` and `<color>` of `-leading-punctuation`), intruding it (`intrude` and the length of `-leading-punctuation-position`), `-leading-punctuation-shift`, `axf:initial-letters-start-intrusion="first-line"`, and ruby as the first letter. The descender of the letter (the part of g below the baseline) is not counted in the height of the drop-cap box. A `space-before` that is discarded at the head of a page, a column or a table cell (`conditionality="discard"`) is not counted for the position of the drop-cap box either, as for the lines (the box is not placed lower than the lines by the discarded space)
- **initial-letter and floats at the head of a column** (typesetting results change only for HTML documents typeset with `--style ah` that have `initial-letter` or a float in a paragraph with `margin-top` at the head of a column in multi-column layout, and HTML documents in any style that have a float in the first paragraph, with `margin-top`, of a list item (`li`)): the `margin-top` discarded at the head of the column or of the list item is not counted for the position of the initial letter box and the float either, as for the lines (before, only the initial letter box and the float were moved down by the discarded margin and did not line up with the lines; in a list item, the item marker was moved down to the height of the float too)
- **Absolutely positioned boxes in multi-column layouts** (**typesetting results change** only for documents with an absolutely positioned box inside a multi-column layout: XSL-FO `fo:block-container` with `axf:column-count` or `column-count` and `fo:region-body` with `column-count`, and HTML `position: absolute` inside `columns`): each trial layout that balances the columns added the box to the page, so the same box was drawn many times (about ten) on top of itself; it is now placed once (since 0.3.0)
- **Speed and memory** (no change to the typeset result): less memory for typesetting XSL-FO documents of thousands of pages. (1) The layout passes repeated to settle page number references (tables of contents and so on) no longer turn the pages into the area tree; only the pass that settles is turned into the area tree (previously every pass built the area tree of the whole document, and the next pass was laid out while the previous tree was still held). (2) When the area tree is built, the intermediate layout tree of each page is released as soon as the page has been turned into areas. (3) When reading FO, the "attributes read" remembered for each element are limited to the attributes written on the element (previously the names of all properties the importer asked for were remembered for every element, including those not written). (4) Leader dots aligned to a grid (`leader-alignment`) no longer copy empty margins and borders for every dot. (5) In the intermediate layout tree, the drawing data of a glyph (character, font, size, colour, position) is shared among glyphs with the same data, and the fields of a glyph node fit inside one object (about 370 → about 200 bytes per glyph). (6) Glyph areas without decorations are built without the fields that have no value (`backgroundColor`, `sourceId`) (about 336 → about 312 bytes per glyph; the Area Tree written as JSON does not change). (7) The Node command, with `typesetToPdf`, writes the PDF page by page and releases the intermediate layout tree of each page once it is written (it never holds the area tree of the whole document; the area tree of a page is built twice, once to collect the fonts and images used and once to draw it). The result of `typeset` (`areaTree`, `toPdf`, `renderPage`) still holds the area tree of the whole document. The command's report "layout N ms" no longer includes the time to turn the pages into area trees (it is part of writing the PDF). Typesetting the FO of the PostgreSQL documentation (37.7MB, 3,231 pages) with the command: previously it stopped at Node's default heap limit, and could be typeset once the limit was raised to 13GB (maximum heap in use, including garbage not yet collected, about 9.4GB; layout time 199 s). Now it can be typeset with a 3GB heap limit (maximum live heap after GC about 2.3GB). With a 4GB limit, the total time is 160 s. The PDF is the same apart from the creation date (and the document ID derived from it). (8) When writing the PDF, the operators of each finished page are turned into the compressed bytes they are saved as, and released (previously the operators of every page were kept as small objects until saving). The PDF is the same, down to the compressed bytes. Typesetting the same document with `typeset` and calling `toPdf`: maximum live heap about 3.2GB → about 2.8GB (what writing the PDF adds goes from about 0.4GB to about 0.03GB). (9) Images: an image in a file passed with the document is no longer kept twice; once it has been copied into the image store, the read contents of the file are dropped (this frees memory for files whose contents are given as a function, as the command does). When only the PDF is made (the command, `typesetToPdf`), the image store's contents of each raster image are also dropped once it has been embedded in the PDF (if the same contents are referred to in other ways, not until the last reference has been embedded; SVG is kept; an image an SVG refers to from inside is kept until that SVG has been embedded, and if there is an SVG with foreignObject or a use pointing at an external SVG, all are kept to the end; a dropped image does not become an unreadable image when laid out again). Typesetting a 240-page FO with 240 images (570MB in all) with the command: maximum resident set size about 2.57GB → about 1.62GB (`--low-memory`: about 2.70GB → about 1.70GB; `typeset` and `toPdf`: about 2.02GB). The PDF is the same
- **Images embedded in the PDF** (no change to the typeset result): when the same image file is referred to in different ways (upper and lower case, `./`, references with `#…`, paths from other directories, CSS `url()` and `img`, inside and outside SVG), the image is embedded in the PDF only once, and the same image is drawn everywhere (ISO 32000-2 §8.8, §8.9.5). Before, it was embedded again for each reference. The PDF gets smaller, and where and how images are drawn does not change. Different files with the same contents are still embedded separately
- **Translucent text colors in HTML** (typesetting results change only for HTML documents that use colors with alpha (`rgba()`, `hsla()`, `#rrggbbaa` and so on) for text, text decoration lines, emphasis marks or ruby): text is drawn with its alpha, over what is below (CSS Color 4 §4.2, §5; ca and CA of the PDF ExtGState). The same goes for the text color of margin boxes. Before, it was drawn as an opaque color mixed with white paper, so on a colored background the background did not show through and the text looked whitish. This is the behavior of PDF/X-4 and output other than PDF/X (how translucent text is drawn in PDF/X-1a and X-3, which do not allow transparency, depends on transparency flattening)
- **Transparent text color** (typesetting results change only for HTML documents that set `color: transparent` (or a color with zero opacity, such as `rgba(…, 0)` or `#rrggbb00`, or one whose opacity is 0 in 8 bits, such as `rgba(…, 0.001)`) for text): text in a color with zero opacity is not drawn (it still takes up space, and text positions and line breaks do not change; CSS Color 4 §4.1, §6.3). Text in colors whose opacity becomes 0 in 8 bits (such as `rgba(…, 0.001)` or `rgb(… / 0.1%)`), which would be invisible if drawn, is not drawn either (nor are text decorations, emphasis marks and ruby in such colors). Underlines, borders, emphasis marks and so on that use `currentColor` are not drawn either (§6.4). If a child sets `color` again, it is drawn in that color. Before, a color with zero opacity was treated as not specified, and the text was drawn in the parent's color (an error from before 0.3.0). As `background-clip: text` is not supported, with styles that paint text with the background (such as a gradient), the background fills the whole box and the text is not drawn (before, text in the parent's color appeared over it)
- **Paint-only effects of fixed-position boxes and margin boxes** (typesetting results change only for HTML documents that set `transform`, `opacity`, `outline` or `clip` on `position: fixed` boxes, or `outline` on margin boxes or `@page`): the transform, opacity, outline and clip of fixed-position boxes are drawn on every page where the box appears (CSS 2.1 §9.6.1, §11.1.2; CSS Transforms 1; CSS Color 4 §3.3; CSS UI 4 §3). Before, the copies made for each page did not get the effects: transform and opacity were silently dropped, and outline and clip were reported as unsupported. Outlines of margin boxes and `@page` are drawn the same way as for document elements (they follow the rounded corners of margin boxes; before, they were drawn as separate border-only boxes, and margin-box outlines were reported as unsupported although they were drawn)
- **PDF/X-1a** (`pdfx: { version: 'X-1a' }` and `'X-1a:2003'` in the API, `--pdfx x1a` and `x1a:2003` on the command line): PDF/X-1a (CMYK and spot colors only, no transparency), long used by Japanese printers, can now be written. :2001 is PDF 1.3 (`GTS_PDFXVersion` `PDF/X-1:2001` and `GTS_PDFXConformance` `PDF/X-1a:2001` in Info), :2003 is PDF 1.4. No XMP is written, and a registered printing condition name is enough (a profile, if given, must be CMYK). The written PDF is read back and checked against the rules known from public descriptions (version, encryption, markers, output intent, boxes, color spaces, transparency, font embedding, annotations within the bleed area), and an error is thrown if it does not meet them. Not checked against the text of the PDF/X standards (ISO 15930-1, -4)
- **Transparency flattening for PDF/X-1a and X-3**: transparency (CSS opacity, colors with alpha, images with alpha, translucency, masks and blend modes in SVG) is replaced with opaque objects, keeping the appearance as far as possible. When only a single-color fill (the background of a rectangular or rounded box, rotated ones included, or the white page) lies under a transparent object, the CMYK color is computed with the Normal compositing formula (ISO 32000-2 §11.3.3) and the object is drawn as an opaque vector object (text stays text). Otherwise the area is rasterized together with what lies under it into a CMYK image (300ppi; 600ppi where text under 12pt is involved), with a warning (images of glyphs on the same line are merged into one; a warning also says when text within rasterized areas loses quality and can no longer be selected as text). An error is thrown if transparency that cannot be flattened remains (such as transparency of color glyphs; PDF/X-4 is suggested). Overlapping areas are composited in CMYK (as in printing), so they look slightly different from screen viewers that composite in RGB. PDF/X-4 and non-PDF/X output keep transparency
- **Changes in PDF/X-3 output** (only for documents that use transparency or contain grey-only images): transparency is flattened (see above) instead of being kept with a warning. Transparency that cannot be flattened is an error instead of a warning. The written PDF is read back and checked against the PDF/X-1a rules with the ban on device-independent color (ICCBased, Lab, CalRGB, CalGray) lifted, and an error is thrown if it does not meet them
- **Grey-only images in PDF/X** (only for PDF/X-1a, X-3 and X-4 output of documents with grey-only images): images whose pixels are all R = G = B (RGB and RGBA PNGs, 16-bit and 1-bit grey PNGs, grey + alpha PNGs, RGB JPEGs) are embedded as DeviceGray images instead of DeviceRGB (the same tones; ISO 32000-2 §8.6.4.2). They used to be written as DeviceRGB (a bug since 0.3.0), leaving RGB images in PDF/X
- **Development** (typesetting results do not change): when run from npm, `npm run ci:local` runs the npm main script (`npm_execpath`) directly with the Node that runs the script, without a shell. On Windows too, `npm.cmd` is not run and the arguments are passed as they are, so the deprecation warning from Node 24 about passing an argument list to a shell does not appear. In the node-min job, npm also runs on the same Node when the lowest supported Node is put first in PATH. When run directly as `node scripts/ci-local.mjs`, the `npm` in PATH is called as before
- **Security and robustness against crafted input** (protection of time and memory when typesetting documents written by others on a server; typesetting results of valid documents do not change; limits and their grounds are in the source comments):
  - Regular expressions that took time quadratic in the input length now read the text once from the front: `width` and `height` in the start tag of SVG images (long runs of spaces), grid `repeat()` (a `repeat(` without a comma and long runs of spaces), and runs of unclosed `url(` (computed lengths of `filter`, `box-shadow` and the like, `background` of `@page`, `background-position`, and XSL-FO `axf:printer-marks`; an unclosed `url(` ends at the end of the value: CSS Syntax 3 §4.3.6)
  - Deeply nested math functions such as `calc()` (in computed values of `filter`, `box-shadow`, `grid-template-columns` and others) took time proportional to depth × length and overflowed the stack, so the whole document could not be typeset
  - The selector before `::footnote-call` and `::footnote-marker` is matched with the same matcher as the cascade (short selectors over deep nesting or many siblings took exponential time). The memo for matching selectors that mix combinator kinds has a total budget per cascade; once it is spent, such selectors are not applied and a warning is given (valid documents do not reach it)
  - Paragraphs with many line breaks around comments, tables with many `rowspan="0"` cells, documents with many named pages and track lists with large `repeat()` counts are typeset in time proportional to their size
  - Documents with many `span="all"` blocks deep inside nested blocks of a multi-column container (XSL-FO `axf:column-count`): the number of fragments made to lift the spans out is limited; spans beyond the limit are set within the columns and reported by the importer
  - When an SVG filter is approximated with shapes, the number of clipping rectangles for primitive subregions and the number of layers no longer grow exponentially with stacked `feComposite` and `feMerge` (with too many layers, the approximation is dropped and the filter is computed in pixels)
  - When flattening transparency for PDF/X-1a and X-3: the 72 ppi floor of the rasterization resolution is gone, and the pixel limit of one image is always kept (very large pages made images of billions of pixels. **Typesetting results change** only for large pages where rasterizing the whole page exceeds the limit: the resolution goes below 72 ppi, and the lowered resolution is reported in the warning. An area beyond the limit even at 1 ppi is an error, since it cannot be rasterized). The objects under a translucent object are looked up through a grid index of the page (each translucent glyph walked all objects drawn on the page)

The fixed layout looks only at the cells of the first row, so the borders excluded are those of the first row's cells. The Antenna House sample (`table-border-conflict-resolution-1` in the sample FO collection; a 5-column table whose first-row borders are 5, 10, 5, 5 and 15pt) also gives all five columns the same content width (about 86.4pt). In that sample the text of the 15pt cell no longer wraps onto two lines, and the output has two pages like the sample. In the sample FO collection five samples change in the specification mode and nine in the compatibility mode (`--compat antenna`) (each is closer to the sample, or the same to within 0.01%). The conformance documents (all four) do not change. With the other HTML styles (`kumiori`, `browser`, `browser-margin`, `vivliostyle` and `weasyprint`) the column boxes are still divided equally, as before (reading "borders or cell spacing" in the same sentence as the table's borders and the cell spacing; browsers (Chromium) also divide the column boxes equally)
- **Specified widths of the edge columns of collapsed-border tables** (every XSL-FO mode, and HTML tables with `table-layout: fixed` and `border-collapse: collapse`; **typesetting results change**): a specified column width (`column-width`, or `width` on `col`) is now the distance between the grid lines for the columns at the edges of the table as well. Previously, in the specification mode the first and last columns were narrower by half of the outer border that sticks out (or wider by the inner half of the table's border when the table holds the outer border), and in the compatibility mode (`--compat antenna`) the last column was narrower by the width of the outer line (inner columns also shifted when the inner lines had different widths). The table width is the distance between the outer grid lines (row-width in CSS 2.1 §17.6.2), so the specified column widths add up to the table width. The Antenna House sample (`axf-form-field-event-1` in the sample FO collection: four columns of 30, 30, 30 and 40mm) also makes the distance between the grid lines equal to the specified width, for the edge columns and the last column too. Automatic-layout tables, whose column widths are measured from their contents, do not change. In the sample FO collection ten samples change in the specification mode and nine in the compatibility mode (in the compatibility mode the difference of `table-spanned-1` from the sample falls from 0.39% to 0.02%, and the right edge line of `table-within-page-1` is now at the same position as in the sample). The CSS-Print book does not change
- **Fixed column widths without column specifications in separated-border tables** (XSL-FO tables with `border-collapse="separate"` in every mode, and HTML tables with `table-layout: fixed` and `border-collapse: separate` under `--style ah` (Antenna House compatibility); **typesetting results change**): columns without a specified width now share the width so that their widths excluding the borders of the first row's cells are equal, as for collapsed-border tables (see "Column widths of collapsed-border tables with fixed layout and no column specifications" above; CSS 2.1 §17.5.2.1). Previously the cell boxes, including their borders, were divided equally. With the other HTML styles the cell boxes are still divided equally, as before (as in browsers (Chromium)). The sample FO collection, the conformance documents and the CSS-Print book have no such tables and do not change
- **XSL-FO orthogonal `fo:block-container` without an inline-direction size** (all modes; **typesetting results change**): a container whose writing mode is orthogonal to its parent's (such as `writing-mode="tb-rl"` inside horizontal body text) and that has no `inline-progression-dimension` (the height for vertical text) used the body width as its line length, so the box exceeded the page height, was pushed to the next page and overflowed at the bottom, cutting off characters. XSL 1.1 §6.5.3 says this size may not be auto and does not define how to lay it out (auto in §7.15.7 is "determined by the formatter taking all other constraints into account"), so, as for orthogonal blocks (E-16 in BACKLOG), the line length is now the remaining page height (the page height from the next page on), lines are stacked up to the parent's width, and lines that do not fit continue on the next page. A box that fits on one page fills the parent's width, as before. A bordered (border or padding) container rotated by 90° or 270° with no size specified was laid out as a single box whose lines, stacked beyond the body width in its local block direction, overflowed the box; it is now stacked up to the body width and continued on the next page, like a container without borders (the borders at the breaks follow `conditionality`, as for block fragments)
- **Word spaces in justified lines in the XSL-FO spec mode (`--compat spec`, `compat: 'spec'`, the default)** (**typesetting results change**): Latin word spaces are no longer compressed to pull a character or word into the line in justified lines either (the non-final lines of a paragraph with `text-align="justify"`, and lines set with `text-align-last="justify"`). Spaces never become narrower than their natural width; the word that used to fit by compression goes to the next line, and the line is filled by widening the word spaces (previously spaces could be compressed to 1/3 to take one more word). In XSL 1.1 §7.17.8, a word space for `word-spacing="normal"` or a length has `.minimum = .optimum` (no room to shrink). A release that adds flex features, WOFF/WOFF2, an API for loading referenced files, and more. While in 0.x, it is a minor release because it includes fixes that change typesetting results.

- **Security** (protection when typesetting documents written by others):
  - Link actions in the PDF are limited to safe ones. By default only destinations inside the document, URLs with the schemes `http`, `https`, `mailto` and `tel`, and relative references to PDFs (GoToR) are written. To get the previous behavior, use `links: { schemes: ['*'], launch: true }` in the API or `--link-schemes '*' --link-launch` on the command line. Schemes are read the way browsers do, after removing leading and trailing control characters and tabs and newlines anywhere (`java<TAB>script:` is dropped too). Resources collected by following references (`file:` files returned by `resolveResource`, CSS and fonts fetched from the network) are never attached. An attachment copies the bytes of a file into the PDF as they are, so when collected resources could be attached too, a document written by someone else could, with the default settings, copy files of the machine that typesets it (`file:///etc/passwd`) or responses from the internal network (`http://169.254.169.254/…`) into the output PDF, by making another reference (`<link>`, `url()`; even one written inside an XML comment is picked up) collect them

Documents with a single `fo:flow`, and documents whose first `fo:flow` matches the body region, are unchanged. An `fo:flow` whose name matches no region, or one without `flow-name`, is still flowed into the body, with a warning ("no region matches flow-name "…"; its content was flowed into the body region"; it used to be reported as the unread attribute flow-name)
- **XSL-FO: unprefixed attributes on `axf:form-field`** (`field-type`, `field-name`, `field-default-text`, `field-maxlen`, `field-multiline`, `field-checked`, `field-value`, `field-button-face`, `action-type`, and `field-submit-method` on `axf:form`, among others): **results change.** Attributes written without `axf:` on `axf:form` and `axf:form-field`, as in Antenna House’s examples and samples, were not read (every field became a "text" field with a generated name, and default values, options and button captions were lost). They are now read like the `axf:` names (`axf:field-type` etc.), whatever `--compat` is (the `axf:` name wins when both are present). Per-event actions (`axf:form-field-event`) and button `action-type` values other than `submit` and `reset` (`javascript`, `uri` etc.) are still not written to the PDF (no scripts are written); the warning now names them
- **XSL-FO: gradients in `background-image`** (`linear-gradient()`, `radial-gradient()`, `repeating-linear-gradient()`, `repeating-radial-gradient()`): in compatibility mode (`--compat antenna`, `compat: 'antenna'`) they are drawn as the same gradient backgrounds as in HTML (**results change in compatibility mode**: nothing was drawn before, and there was no warning). The values of `background-image` in XSL 1.1 §7.8.3 are `<uri-specification> | none`, so in specification mode they are not drawn and a warning reports them (`background-image:linear-gradient()`). The same applies to a gradient inside the `background` shorthand
- XSL-FO: `axf:background-size` (size of the background image: lengths, percentages, `auto`, `cover`, `contain`; first layer only) is read, whatever `--compat` is (**results change for documents that use this attribute**: it used to be reported as unread). `background-image`, `background-repeat` and `background-position` on `fo:simple-page-master` are read as the page background image in compatibility mode only (by the specification the background properties do not apply to `fo:simple-page-master`, so in specification mode they are still reported in the warning)
- XSL-FO: a `start-indent` written as a length on the `fo:list-item-body` of the second and later list items is read (XSL 1.1 §7.11.7). When it equals the value on the first item the result is unchanged and the warning "unread attribute start-indent (fo:list-item-body)" no longer appears. A value larger than the first item’s indents that body by the difference (**results change for documents written that way**: the body used to be placed at the first item’s position). A smaller value cannot be placed and is still reported in the warning
- **XSL-FO: the background color is now painted up to the padding rectangle** (XSL 1.1 §4.9.4; independent of `--compat`): **results (appearance) change.** The background color used to be painted up to the outer edge of the border (the border box), so it showed through the gaps of dashed, dotted and double borders and under borders with a transparent color. It is now painted up to the inner edge of the border (the padding rectangle), as the specification says. Only boxes that have both a background color and a border with gaps (dashed, dotted, dot-dash, double, wave) or a transparent color on the same element change (`fo:block`, `fo:block-container`, `fo:table`, `fo:table-cell`, region borders in compatibility mode, and so on). Boxes with opaque solid or 3D-style (`groove`, `ridge`, `inset`, `outset`) borders and boxes without borders are unchanged. With rounded corners (`axf:border-radius`) the background corners follow the inner curve of the border. The parts that overlap the outer border of a collapsed-border table are not changed yet (backgrounds of inline boxes, `fo:inline`, are also painted up to the padding rectangle, as described in a separate item above)
- **Content written after `</body></html>`** (HTML; the Node command and the API; **the result changes**): elements and text written after `</html>` (or `</body>`), as in `<html><body><p>a</p></body></html><p>b</p>`, were dropped. They are now laid out as a continuation of body, as browsers do (the "after body" and "after after body" insertion modes of the HTML Standard). Comments after the end, and whitespace at the end of the document, add nothing, as before
- **Positive left and right `margin` on inline boxes and line wrapping** (HTML; **the result changes**): the left and right `margin` of a `display: inline` box (`span` and so on) is no longer separated from the first and last characters of the box (CSS 2.1 §9.4.2, CSS Text 3 §5.5: a line is broken outside the margin edge of the box). Before, the end `margin` could be left at the start of the next line, shifting the first character to the right (setting `一二三四<span style="margin-right: 30pt">五</span>六七` five characters wide shifted 六 by 30pt), the start `margin` could be left at the end of the previous line, an empty line was added at the end of a paragraph, and a full stop could come to the start of a line. Now, when the `margin` does not fit on the line, the character moves to the next line with it (as in browsers). An inline box with `box-decoration-break: clone` also gets its left and right `margin` on each fragment (CSS Fragmentation 3 §5.4). Only with the AH Formatter compatible style (`--style ah`), a start `margin` that comes to the start of a wrapped line is dropped (as in the reference output). Inline boxes without `margin`, negative `margin`, and `space-start` / `space-end` in XSL-FO are unchanged
- **Heading of the conversion report on the screen**: the report said "XSL-FO 変換レポート" (XSL-FO conversion report) even for HTML documents (EPUB included); the heading now follows the kind of document ("HTML 変換レポート" for HTML; the hint for images not found and the line shown when nothing is unsupported also follow the kind of document)
- **`@font-face` fonts of a previously opened document staying on the screen (Kumiori in the browser)**: when HTML documents that use the same `font-family` name for different font files were opened one after another, the later document was set in the font of the earlier one (and a bold face that only the earlier document had could be used for bold text in the later one). Each time a document is opened, its `@font-face` files are now registered again and faces that only the previous document had are removed (including the fonts registered with the browser). Re-laying out the same document after changing a setting does not reload the fonts. The Node command and the API already keep fonts separate per document and are unchanged
- **Kerning in content-size estimates (max-content, min-content)** (HTML): content widths such as those of flex items (children of `display: flex`) were estimated without kerning, so runs that kerning widens (such as "2.2" in some fonts) did not fit the item's width and split into "2." and "2" with `overflow-wrap: break-word`. The estimate now adds the same kerning to the same character pairs as line layout does (following `font-kerning` and the "kern" setting of `font-feature-settings`). **Results change** (boxes sized by their content, with kerned Latin text, get slightly different widths)
- **XSL-FO: `background-color` on `fo:simple-page-master` is read only in compatibility mode (`--compat antenna`)**: the background properties do not apply to `fo:simple-page-master` (XSL 1.1 §6.4.13), so in specification mode (the default) it is not read and the load warnings report it. **Results change for documents typeset in specification mode** (a background color written on the page master no longer appears). `axf:background-color`, whose name carries the prefix, is read in every mode
- **PDF: the original text (ActualText) attached to words in right-to-left scripts (Arabic, Hebrew) is now written in reading order** (ISO 32000-2 §14.9.4: replacement text is the characters equivalent to what a person sees). It used to be written in drawing order (left to right). **Text extracted from the PDF changes**: in the Chrome and Edge viewers (PDFium) the characters of each word now come out in reading order (they were reversed); poppler's pdftotext and MuPDF also reorder ActualText characters, so their words now come out reversed (they used to be in reading order). The appearance does not change

## 0.1.0 (2026-11-08)

The first public release.

- **Input**: HTML+CSS (own CSS cascade), XSL-FO 1.1 (supports part of Antenna House's `axf:*` extensions, focusing on the commonly used ones), JSON logical tree
- **Japanese typesetting**: vertical and horizontal writing, ruby, tate-chu-yoko, emphasis marks (kenten), line-breaking rules (kinsoku), hanging punctuation and pushing out, punctuation compression, spacing between Japanese and Latin text (JLREQ)
- **Pages**: page masters, running heads and page numbers (folios), footnotes, multi-column layout, floats, tables (splitting, repeated headers, automatic column width), page number references, bookmarks, links, annotations, forms
- **Output**: Canvas preview, PDF (subset font embedding, trim marks, PDF/X-3 marking)
- **Other scripts**: right-to-left scripts such as Arabic and Hebrew (UAX #9, joined forms of Arabic letters), Latin hyphenation
- **Usage**: the browser web app, the Node CLI `kumiori` (`--help`, `--version`, `--lang ja|en` and `KUMIORI_LANG` for English messages, a cache for the default fonts, warnings for unsupported CSS and XSL-FO), the library (`kumiori`: ES module; `kumiori/browser`: a single file for browsers with the dependencies bundled; the `lang` option for English warnings)
- **Documentation**: the Conformance Guide (HTML and CSS volume, XSL-FO volume; Japanese and English editions), the Area Tree JSON specification, and English versions of the README and docs (README.en.md, docs/en/)
