# Changelog

Version numbers follow [Semantic Versioning](https://semver.org/). During 0.x, incompatible changes may also be released in a minor version (such as 0.2.0).

## 0.3.0 (2026-11-16)

A release that adds draw.io diagrams, plugins that add image formats, PDF/X-4 and more, and widens what SVG can draw. While in 0.x, it is a minor release because it includes fixes that change typesetting results.

- **draw.io diagrams**: draw.io (diagrams.net) diagram files (`.drawio`, `.dio`, including compressed pages) are read as images by default. A page is converted to SVG and placed in the PDF as shapes and text (usage: `docs/en/drawio.md`)
  - The page to draw is selected after `#` in the image reference: `#page=N` (counted from 1), `#page-id=ID` or `#<page name>`. Without one, the first page is drawn; for a page that does not exist, the first page is drawn with a warning. `#` references that select the same page reuse the drawn diagram
  - Shapes, edges and arrows are drawn by code ported from the public source code of draw.io and mxGraph: standard shapes, icon frames (AWS, GCP, Cisco and so on), shapes that draw.io draws in JavaScript (about 750), edge routing, line jumps, thick arrows, 34 edge end types, label placement per shape and curved text. Shadows (shapes, text and the whole diagram), the glass effect, gradients with end opacities, the sketch style (`sketch`, rough.js) and jiggled lines (`comic`)
  - Shapes from shape libraries (`mxgraph.*`) and shapes embedded in diagrams (`stencil(…)`) are drawn. The libraries are not included in Kumiori; they are used only when passed with `drawio.stencils` (`--drawio-stencils` on the command line) or when fetching is allowed with `drawio.fetchStencils` (`--fetch-drawio-stencils`, `--drawio-stencils-url`) (draw.io's distributed `stencils.min.js` and library XML are read). The same applies to images from draw.io's distribution, such as the images inside SAP icons and clip art. On the command line, fetched files are saved in the font cache directory
  - API: `TypesetOptions.drawio` (the type `DrawioOptions`: `stencils`, `fetchStencils`, `stencilsUrl` and `provideStencils`; `false` means draw.io diagrams are not read as images). `DRAWIO_MIME`, `isDrawio`, `createDrawioStencilRegistry` (creates the shape library registry `DrawioStencilRegistry` that `provideStencils` returns) and the types are exported. Command line: `--drawio-stencils`, `--fetch-drawio-stencils`, `--drawio-stencils-url` and `--no-drawio`. `--watch` also watches `.drawio` and `.dio` files
  - Images given by URL are fetched under the same rules as the document's images (`resolveResource`, `fetchImages`). Text widths are measured with the fonts Kumiori draws with. When the API reuses the same `drawio` option across documents, an image fetched under one document's rules is not used for another document. Warnings are written in Japanese or English, following `lang` (`--lang` or the environment on the command line)
  - The code that draws diagrams (including rough.js) is loaded only when a draw.io diagram appears (as for CGM, EPS, WMF and EMF; a separate file in the web app and the browser library). roughjs and pako were added as dependencies
  - The shapes from draw.io's `shapes/` (`src/drawio/drawioJs/` and others) are ported from v24.7.5 (Apache License 2.0 only), before draw.io put a restriction of use on `shapes/` (`shapes/LICENSE`: use in Atlassian products; since v29.3.2), and follow the drawing of v24.7.5.
    Shapes added after v24.7.5 are not included: `mxgraph.archimate4.*` (36 shapes), `mxgraph.c4.mobileDeviceContainer`, `mxgraph.bpmn.task2`, `data2`, `conversation2`, `mxgraph.atlassian2.icon` and `mxgraph.networks2.icon`. These shapes get only their text, with a warning that they are not drawn because they were added after v24.7.5 (not a warning that a shape library is missing, and nothing is fetched for them).
    Style keys added later (keys that change colors, such as `strokeColor2`, `fillColor2` and `bodyColor`) are not read either
  - The default version of the shape libraries and distributed images to fetch is also v24.7.5 (CC BY 4.0)
  - The files ported from draw.io and mxGraph carry the copyright notices of the original files and a statement that they were changed (section 4 of the Apache License 2.0), and the chunks of the built JavaScript that include the draw.io code start with the copyright notices. The original files, their versions and notices are listed in section 13 of THIRD_PARTY_NOTICES.md. NOTICE also states that code was ported from draw.io and mxGraph
  - Robustness against crafted diagrams: there are limits for inputs that exhaust time or memory from small files (XML close tags and skipped declarations, path moves, the length of `html=0` and placeholder labels and their total per diagram, the SVG length per diagram (16Mi characters, about 16.8 million), line-jump crossings, the inflated size of embedded shapes, cell coordinates and the diagram size (10 million px) and element nesting depth). Parts beyond a limit are not drawn and a warning is given (a single cell that exceeds the SVG length or the diagram size on its own is not drawn, and the rest of the diagram is). The number of hatch lines of sketch-style (`sketch=1`) fills is estimated from the size of the element drawn, also for shapes that a `style` value (`unitNum` of `rackCabinet`, `textSize` of button bars and so on) draws larger than their cell, and elements larger than 10 million px (width plus height) are drawn without the sketch style. Shapes that lay out `,`-separated items (button bars, menus, breadcrumbs, tab bars, pie charts and so on; eleven shapes) are drawn with work proportional to the number of items
- **Web app** (demo): a "draw.io の図" (draw.io diagrams) section was added to the settings. "draw.io の図を読む" (Read draw.io diagrams) turns reading diagrams on or off (on by default; the choice is remembered in the browser). When off, the code that draws diagrams is not loaded, and the open document's images are read again and the document is typeset again. Inside the section you can load draw.io shape library files (remembered in the browser), clear them, and choose to fetch them from draw.io only when a diagram needs them. Shape libraries (`stencils.min.js` or library XML) passed together with the opened files are used for that page session only. Diagrams referenced with a page after `#` (`figure.drawio#page=2`) are also redrawn when the settings change and when the diagram file is opened again on the same page
- **Plugins** (`plugins` in the API, `--plugin` and `--plugin-option` on the command line): plugins that add image formats can be passed (`KumioriPlugin`; the interface version `PLUGIN_API_VERSION` is 1). A format has a content check (`sniff`) and a loader (`load`, which returns SVG and a size), and Kumiori draws the result as an SVG image. `load` receives tools to measure text with the fonts that draw it, to fetch under the same rules as the document's images, to fetch URLs the user allowed through the plugin's options (`fetch`, with the time limit `fetchTimeoutMs`) and to report warnings, the language for warnings (`lang`) and the fragment of the image reference (after `#`; `fragment`, to select which diagram or page of a file to draw). When the same file is referenced with different fragments, it is loaded once per reference (each becomes its own image). A plugin runs with the same rights as Kumiori, so pass only ones you trust. The web app does not run programs supplied by users. The command's `--watch` also watches files with the extensions of plugin formats
  - How the command's `--plugin` is resolved: specs starting with `./` or `../`, absolute paths and `file:` URLs are taken as file paths. Any other spec is first resolved as a package name, as `import()` does, from the current directory with the same conditions as `import()` (`import`, `node`, `default`) (including `@scope/name`, `name/sub` and ones ending in an extension, such as `kp/dist/plugin.js` or `chart.js`; an ESM package whose `exports` has only the `import` condition is loaded too). If it cannot be loaded as a package (no such package, and also when the package does not export that subpath in `exports` or its entry file is missing), the file of that name in the current directory is loaded (`--plugin myplugin.js`). Whenever it can be loaded as a package, the package is loaded (even when a file or directory of that name exists in the current directory), so write `./` to be sure of pointing to the file. When nothing is found, the error message says what was searched, in order
  - When a plugin that cannot be loaded is given (also with `--watch`), the command prints only the error message and exits with code 1
- **PDF/X-4** (`pdfx: { version: 'X-4', profile }` in the API, `--pdfx x4 --output-profile <ICC>` on the command line): PDF/X-4 output is now available (PDF/X-3:2003 remains; X-3 is the default). X-4 requires an embedded output CMYK ICC profile (an error if it is missing or not CMYK), writes XMP metadata (`GTS_PDFXVersion`, dates, title, `Trapped`, IDs) consistent with the Info dictionary (ISO 32000-2 §14.3.2), keeps transparency as is, and writes PDF 1.6. The command-line options `--pdfx x3|x4`, `--output-profile` and `--output-condition` (the printing condition name; default JC200103) are added. Not checked against the text of the PDF/X standards (ISO 15930-6, -7)
- **Changes in PDF/X output** (both X-3 and X-4; non-PDF/X output is unchanged, and so are the positions of text, lines and images): only TrimBox is written on pages (no ArtBox). **Links, annotations and form fields on the pages are not written** (any that overlaps the area up to the bleed (BleedBox) even slightly is left out, and their number is reported in the warnings. The BleedBox encloses the whole artwork of the page, so practically all links on the pages are lost, both internal ones such as those of a table of contents and those to external URLs. 0.2.0 wrote them in PDF/X-3. Bookmarks are not annotations and are still written. Write PDFs for reading on screen without PDF/X). Without a title, Untitled is used. Following the recommendations of the GWG 2022-R1 submission specification, grey (R = G = B) text, lines and fills are written as K-only CMYK (grey images stay DeviceGray), and K 100% body text under 12pt (including text in the page margins) and lines and rules under 2pt get overprint (OP, op, OPM 1; ISO 32000-2 §8.6.7; text and lines inside images such as SVG and EPS do not). Of the GWG 2022-R1 requirements, differing trim sizes (R0004), spot colours (R0020) and image resolution (R0031; 149ppi or less is required, 224ppi or less recommended) are checked and reported in the warnings (the output is not changed)
- **SVG** (typesetting results change: SVG that previously could not be drawn and was rasterized or shown as a placeholder frame is now drawn as shapes):
  - Selectors with combinators (descendant, child, next-sibling, subsequent-sibling), attributes and pseudo-classes in `<style>` now match (Selectors 4; the same matching as for HTML)
  - text: `font-style` (upright glyphs are slanted if there is no italic face), per-character lists of `x`, `y`, `dx`, `dy` and `rotate`, `baseline-shift`, `dominant-baseline` and `alignment-baseline`, `word-spacing`, `paint-order`
  - `objectBoundingBox` for `clipPathUnits` and `maskContentUnits`, `slice` in `preserveAspectRatio` of image, and images referring to external files (PNG and JPEG among the document's files; if missing, only that image is not drawn, with a warning)
  - Gradients, opacity, clipping, blend modes and nested patterns in pattern contents; all 15 values of `mix-blend-mode`
  - `systemLanguage` in switch and the conditional processing attributes, matched against the language where the image is placed (`lang`, `xml:lang`, `language`; the environment's language if none is given). Elements outside switch whose conditions are not met are not drawn either
  - The filter approximation in Node (the CLI and the API) now also handles `feColorMatrix` and `feComponentTransfer` (changing the shapes' colors) and compositing with `feComposite` and `feBlend` (all 16 blend modes) (shadows exported by Figma are drawn too). The result of a filter is clipped to the filter region. When a filter primitive has a subregion (`x`, `y`, `width`, `height`; Filter Effects 1 §9.4), the primitive's result is clipped to that subregion (previously the subregion was ignored and drawn outside it too; a blurred result that must be clipped is computed in pixels)
  - Elements with `opacity`, elements with children such as `g` with `mix-blend-mode`, and elements with `isolation: isolate` are drawn as a transparency group of their children (previously the opacity was applied to each child, so overlapping parts got darker and, for shapes with both fill and stroke, the fill showed through under the stroke). `visibility` is inherited, and children set back to `visible` are drawn (previously the children of a `hidden` element were not drawn at all)
  - CSS syntax: `transform` with units (`rotate(45deg)` and so on), `transform`, `transform-origin` and `transform-box` in `style` and `<style>`, `var()` and `calc()`, basic shapes in `clip-path` (`circle()`, `inset()`, `polygon()`, `path()` and so on) with reference boxes, and `@media` in `<style>` (matched as a print medium)
  - use draws elements of other files (`icons.svg#a`; a missing file is reported as a warning). Links of `a` become PDF links
  - text: `letter-spacing`, `word-spacing` and `text-decoration` on tspan, `side` and `baseline-shift` on textPath, `font-weight` and `font-style` of `@font-face`, and vertical text (`writing-mode`, `text-orientation`; glyph orientation and vertical glyph forms are decided as for vertical body text)
  - `mask-type: alpha`, the mask region and nested masks (previously only the inner one took effect), `context-fill` and `context-stroke`, and GIF, BMP and WebP in image
  - text: `textLength` on tspan, `textLength` and `text-decoration` in vertical text, SVG 2 `inline-size` (automatic wrapping), and SVG fonts (glyphs of the `font` element)
  - Node (the CLI and the API) computes filters that cannot be approximated with shapes (`feTurbulence`, `feMorphology`, `feDiffuseLighting`, `feSpecularLighting`, `feDisplacementMap`, `feConvolveMatrix`, `feImage`, `feTile`, `arithmetic` of `feComposite`, `in`, `out` and `atop` of `feComposite` that cannot be drawn with shapes (such as inner shadows), and so on) in pixels and places them as an image (as specified in Filter Effects 1; previously a placeholder frame)
  - The content of foreignObject (HTML and MathML) is typeset with the same HTML layout as the body and drawn (backgrounds, borders, tables, images and math too; previously a placeholder frame). The rules of the SVG's `<style>` (including selectors such as `#id p` that use the ids and classes of the SVG ancestors) and the formatting inherited from the SVG ancestors (`font-family`, `font-size`, `font-weight`, `font-style`, `color`, `letter-spacing`, `word-spacing` and `visibility`) apply to the content (SVG 2 §23.2, CSS 2.1 §6.2). The body's default style sheet (`--style`, `style`) and the CSS files applied to the body (`--css`, CSS in `files` that the document does not reference) do not apply; the content is typeset with the browser default style sheet. When the typeset content draws nothing inside the foreignObject box (for example when it lies outside the box), a warning is given and only the text is approximated. When it is not typeset through the API (such as when calling `renderPdf` directly), only the text of the HTML is approximated
  - SVG with a clipPath of many points applied to many shapes (such as maps) is drawn as shapes. Previously the clip outline was written again for each shape, exceeded the segment budget, and a placeholder frame was drawn. The same clip shared by consecutive shapes is now written once (ISO 32000-2 §8.4.2, §8.5.4)
  - `svgLanguages` in the API and `--svg-lang` in the CLI: the languages to match SVG `systemLanguage` against (when the place of the SVG has no language)
- **Fonts**: When the document contains emoji not found in the symbol font (Noto Sans Symbols 2) either (faces such as 😀, flags, skin tone modifiers, etc.), the emoji font Noto Emoji (monochrome outline emoji; SIL Open Font License 1.1; about 870KB) is loaded. Previously no default font had emoji, so those characters were set as the missing-glyph box and the warning "no loaded font has a glyph for these characters" was given. **Typesetting results change** only for documents with such emoji (characters the symbol font has, such as ✈ and ❤, are set in the symbol font as before). For colour emoji, pass a font such as Noto Color Emoji, as before. `emoji` was added to `DEFAULT_FONTS`
- **`.minimum` and `.maximum` of XSL-FO `word-spacing`** (spec mode only): now read (they used to be reported as unsupported). In justified lines, word spaces are shrunk down to `.minimum` to fit a character or word, and are widened only up to `.maximum` (XSL 1.1 §7.17.8: “The minimum and maximum values specify the limits of the adjustment.”; the `<space>` datatype in §5.11). Compatibility mode still does not read them and reports a warning
- **Warnings raised while writing the PDF**: notices about glyphs that cannot be drawn, the limits for color glyphs, glyphs in the SVG table, form fields that cannot be made and so on are added to `result.warnings` after `result.toPdf()` (previously they only went to the console, or came after `warnings` was built). The notice for glyphs that cannot be drawn is given once per font. The warnings follow the `lang` used for typesetting. The web app lists them with the other warnings
- **Warnings**: warnings that stayed in Japanese with `lang: 'en'` (`--lang en` on the command line) are now written in English: three image warnings (a placeholder frame is drawn, part of the image cannot be drawn, the image is not found or cannot be read) and the reasons for placeholder frames of unreadable images; in the notices of unsupported CSS and XSL-FO, the reasons attached to items (`a value read only with --style ah`, `unit xx (length …)` and so on) and the separators of the list; the PDF/X warnings on transparency and the ICC profile; the overflow warnings of the layout (lines, boxes, floats, footnotes, table rows and so on that do not fit on the page); the separators of the list of characters without glyphs; the errors when reading EPUB; the error for too deeply nested transforms; the notes inside image formats (elements of CGM, WMF and EMF that cannot be drawn and their limits, and names of EPS features that cannot be drawn); the errors when reading Area Tree JSON (`parseAreaTree`); and errors in the content of fonts and images (CFF, WebP, PNG)
- **Reporting vulnerabilities**: added the procedure for reporting vulnerabilities privately (`SECURITY.md`, `SECURITY.en.md`), linked from the "Reporting vulnerabilities" section of the README
- **flex**: The width of an item (the estimate of its max-content width) now includes the spacing between ideographs and Latin letters or digits (`text-autospace`; CSS Text 4 §8.4). **Typesetting results change**: when a table-of-contents line lays out the entry title, the leader and the page number with flex, the last character of a title mixing Japanese and Latin text, such as “ecoモードの使い方”, is no longer pushed to the next line (previously the estimate lacked the spacing, so the laid-out line did not fit in the item's width)
- **flex**: The width of an item with no specified width (`flex-basis` and `width` are `auto` or a content-based sizing keyword) is now measured by laying out its content at typesetting time (Flexbox 1 §9.2, step 3 E; previously it was estimated at import by adding up character widths, and only items with a page-number citation were measured at typesetting time). If the line does not fit, the items are shrunk again at typesetting time by their `flex-shrink` ratios (§9.7; the min-content width used as the `min-width: auto` lower bound is also measured at typesetting time). **Typesetting results change**: when a table-of-contents line lays out the entry title, the leader and the page number with flex, the estimate was narrower than the laid-out line and the last word or character of the title was pushed to the next line in the following cases, which are now fixed: white space between elements (`<b>1.2</b> <b>Overview</b>`), the left and right margins, borders and padding of inline elements, the content of descendants' `::before` and `::after` (such as chapter numbers from counters), the item's own `::before` and `::after`, `word-spacing`, the width and margins of an `inline-block`, the space between a superscript and the next word, and `letter-spacing` on a child element. The same applies to lines with `justify-content: space-between` or `flex-wrap: wrap` and to `flex: auto` items. The width of an image set by `-ah-image-resolution` and of an item containing a table are now the laid-out sizes (previously the intrinsic size or the estimate was used, and the table overflowed the item). The content width (max-content and min-content) of a row flex container inside a box sized by its content (such as a flex item or a table cell) is measured as the sum of its items' content widths (Flexbox 1 §9.9.1)
- **flex**: In a column (`flex-direction: column`) container, items that are inline elements (such as `span`), runs of text directly in the container, and `::before` and `::after` are now blockified (Flexbox 1 §4, CSS Display 3 §2.7). **Typesetting results change**: previously the items were placed side by side on one line instead of being stacked
- **flex**: The estimate of an item's content width (used as a guide for splitting `flex-wrap` lines and for the box width of aligned items in a column container) now counts white space between elements, the left and right margins, borders and padding of inline boxes, the content of `::before` and `::after`, `word-spacing`, and the width of an `inline-block`. For the ways of writing table-of-contents titles that were examined, it matches the laid-out width within 0.02pt
- **flex**: Borders, padding and backgrounds of items made from inline elements (`span`, `a` and so on) are now applied only to the item's box (items are blockified; Flexbox 1 §4, CSS Display 3 §2.7). **Typesetting results change**: a `span` item with a border or padding no longer pushes its last character to the next line, even for short Japanese-only content, and its border is no longer drawn twice (previously the inline box of the content also got the same border and padding)
- **HTML white space**: White space at the edges of inline elements is no longer removed (CSS Text 3 §4.1.1, §4.1.2). **Typesetting results change**: previously “`word <b>bold </b>word`” became “boldword” and “`Over<b> B </b>view`” became “OverBview”, and white space at the edges of `::before` and `::after` of an empty element was also removed (such as the space after a chapter number “第1章 ” in a table of contents). This also affected entry titles mixing English and Japanese split into elements (`<b>eco </b>モード`). Spaces that meet across the boundaries of inline elements are collapsed to one, and spaces at the start and end of a line are removed. In Japanese text, whether a line break in the source becomes a space or is removed is also decided by the characters before and after it across the boundaries of inline elements, and a line break between Japanese characters is removed (CSS Text 3 §4.1.3, §1.5). A line break just inside a tag (`これは<b>\n強調\n</b>です`) gives “これは強調です” as in 0.2.0, and **typesetting results change**: a line break just outside a tag (`これは\n<b>強調</b>\nです`), which gave a space in 0.2.0, no longer gives one. If either side is not Japanese, the line break becomes a space as before. Forced line breaks, images, inline-blocks, ruby and block boundaries are not crossed
- **Blocks inside inline elements in HTML** (all styles; **typesetting results change**): the blocks inside `<span><p>…</p></span>`, `<a><div>…</div></a>` (card links and the like), `<b><div>`, `<span><ul>`, `<span><table>`, `<label><div>`, `display: block` elements inside inline elements and so on are now typeset (inline boxes containing block boxes, CSS 2.1 §9.2.1.1). The inline box is split before and after the block; the block is laid out as a block, and the inline content before and after it goes on the lines before and after. The inline element's text formatting (color, font, weight and so on) and its link also apply to the block inside, and no border or padding is drawn on the edges where the box is split. Previously the content of the inner block disappeared without a warning, and so did the bookmark targets of headings inside it (the labels of Mermaid 10+ flowcharts, `<span class="nodeLabel"><p>…</p></span>`, have this shape). A block that remains inside an inline box and cannot be placed is reported as a warning. Elements with `display: inline-flex` or `inline-grid` are inline-level boxes (Flexbox 1 §3, CSS Grid 1 §5.1), so block items inside them (buttons and links whose icon and label are written as `div`s, such as `<a style="display: inline-flex"><div>…</div><div>…</div></a>`) no longer split the line of the surrounding paragraph. Block items (and items that are inline elements containing blocks) are placed side by side in the line as unbreakable boxes (the same as `inline-block`; their width is the width of the content); previously the text of these items disappeared. In such a container, each run of text directly inside it also becomes one item in the same kind of box, and runs that are only white space (the line breaks and indentation between items and at the start and end of the container) are not rendered, whatever the value of `white-space` (Flexbox 1 §4, CSS Grid 1 §6). Items that are only inline elements are laid out in the line as before. In neither case is the element laid out as an inline flex or grid container, so the gap between items (`gap`), column direction (`flex-direction: column`), alignment (`align-items`, `justify-content`) and grid columns (`grid-template-columns`) have no effect (the items are aligned on the baseline of the line)
- **Control-character escapes in CSS `content` strings** (every HTML style; **typesetting results change**): escapes of control characters such as `\A` (line feed) and `\9` (tab) in the `content` of `::before` and `::after` became the letters “n” and “t” (`content: "X\A Y"` gave “XnY”; since 0.1.0). The computed value is now written as a CSS string (CSSOM §2.1 serialize a string; `"X\a Y"`). Strings in generated content are also now handled by `white-space` like the document's text (CSS 2.1 §12.2, CSS Text 3 §4.1): a line feed is a forced line break with `pre`, `pre-wrap`, `pre-line` and `break-spaces`, and with `normal` and `nowrap` it becomes a space or is removed by the same rule as line breaks in the document (removed between Japanese characters). A tab becomes a space with `normal`, and a CR (`\D`) is treated as a space. The `content` of page-margin boxes is handled the same way by the box's `white-space` (previously `\A` in a margin box always broke the line, whatever `white-space` was). As a result, a run of spaces in the `content` of a margin box now also collapses to one space when `white-space` is `normal` (the default; CSS Text 3 §4.1.1; previously margin boxes kept runs of spaces). **Typesetting results change**: the two spaces in `content: counter(page) "  |  " string(chapter)` become one. To keep the spaces, use U+00A0 (`\A0`) or U+3000, or write `white-space: pre` in the margin box. Other escapes such as `\"`, `\\`, `\2014` and `\000041 B` are unchanged. A “`\`” followed by a line break inside a string (the way to continue a string on the next line; CSS Syntax 3 §4.3.5) is now dropped without adding anything (previously the “`\`” and the line break remained; a CRLF counts as one line break). The white space dropped after a hex escape is now only CSS white space (space, tab, line breaks); previously a U+3000 or U+00A0 after `\25A0` was dropped too
- **HTML print colours when the same property is declared twice** (**typesetting results change**): within a rule, a later print-colour declaration now wins (CSS Cascade 4 §6.1). Previously, when an earlier declaration of the same property existed, a later `rgb-icc()`, `cmyk()` or `device-cmyk()` declaration was set aside and the earlier colour kept (`.r { color: #00f; color: rgb-icc(255,0,0,#CMYK,0,1,1,0) }` stayed blue even with `--style ah`). With `--style ah`, `rgb-icc()` and `cmyk()` are read as colours, so the later declaration wins; `device-cmyk()` (CSS Color 5 §12.1) wins in every style. In the other styles, `rgb-icc()` and `cmyk()` are still dropped as invalid values (and reported), so the earlier colour remains. Inside a `style` attribute, too, the later declaration of a property wins (previously an earlier print colour beat a later screen colour such as `color: #00f`). In *CSS Page Composition Primer* 4th edition (`--style ah`, with spot-colour values), the borders of the border samples (`.BorderSample`) change from RGB green to the spot colour (PANTONE 627 PC), as in the reference
- **Characters that get the spacing between Japanese and Latin text** (HTML with the default style sheet; **typesetting results change**): the `text-autospace` spacing is now inserted, as defined in CSS Text 4 §8.4.1, between Japanese characters and characters of the Unicode general categories L and M (besides Latin, also Greek, Cyrillic, Arabic, Hebrew, Indic and Thai letters, even a single letter) and Nd digits (including Arabic and Indic digits). Before, only Latin letters, digits and words of two or more Greek or Cyrillic letters got it. It is not inserted next to characters with East Asian Width W or F (Hangul, fullwidth letters and digits), symbols, punctuation, or characters set upright in vertical text (`text-orientation: upright`). The class of a character is that of the base character of its grapheme cluster. Between Japanese characters and right-to-left characters, the space goes at the visual boundary after reordering (§8.4.2). Named results (`result`) that are not referenced later are not kept, and when many results are waiting to be referenced, the resolution is lowered. Each SVG has a computation budget: filters beyond it are computed at a lower resolution, and once it runs out the SVG is treated as unsupported (a placeholder frame and a warning; SVGs with many filtered elements, nested patterns or masks, chains of feImage)
  - SVG: the length of `var()` substitution is limited (2 MiB per value, 16 MiB per SVG; the same idea as on the HTML side). `calc()` is evaluated in time linear in the length of the value, nested at most 32 levels. Attribute selectors in `<style>` are looked up through an index, and selector matching is capped at 500,000 matches. SVG font ligatures are looked up with a trie (up to 64 characters), and glyph outlines count toward the path segment limit. Nested foreignObject elements are not typeset again. An SVG is reused across languages that give the same `systemLanguage` result. Writing an SVG text with very many characters no longer fails in PDF output. SVG links are capped at 5,000 per page
  - Results from image formats (plugins and draw.io diagrams) are checked: a finite size up to 10 million px, a limit on the SVG length, a load time limit (150 s by default), and at most 64 distinct `#` references per file
  - CSS: matching a selector with many descendant (whitespace) or subsequent-sibling (`~`) combinators (60 chained `div`s, for example) tried every choice of non-matching ancestors and took over 30 seconds. A selector whose combinators are all descendant or all subsequent-sibling combinators is now matched in time linear in the number of elements, remembering one number per element (how many compound selectors, from the left, can be matched in order by its ancestors or preceding siblings); a selector of 20,000 `i`s chained with `~` against 20,000 `<i>` elements (240KB) takes 2 seconds. A selector mixing kinds of combinators (`a ~ b c`, for example) memoizes intermediate results, taking time proportional to the number of compound selectors times the number of elements; one with more than 64 compound selectors is not matched against any element and is reported in a warning (real stylesheets have no selectors that long). Apart from selectors over that limit, the rules that apply are unchanged

- **Security** (protection when typesetting documents written by others):
  - Link actions in the PDF are limited to safe ones. By default only destinations inside the document, URLs with the schemes `http`, `https`, `mailto` and `tel`, and relative references to PDFs (GoToR) are written. Other schemes (`javascript:`, `data:`, `file:` and so on), actions that open a relative non-PDF file (Launch, including `.html`), absolute paths to PDFs and `//host/…` are typeset as plain text without an action and reported in a warning. To get the previous behavior, use `links: { schemes: ['*'], launch: true }` in the API or `--link-schemes '*' --link-launch` on the command line. Schemes are read the way browsers do, after removing leading and trailing control characters and tabs and newlines anywhere (`java<TAB>script:` is dropped too). The same applies to links, bookmarks and form submit targets in XSL-FO
  - A file attachment annotation (`axf:annotation-file-attachment` in XSL-FO) now attaches only files passed in `files` (for the command, files in the input directory). Resources collected by following references (`file:` files returned by `resolveResource`, CSS and fonts fetched from the network) are never attached. An attachment copies the bytes of a file into the PDF as they are, so when collected resources could be attached too, a document written by someone else could, with the default settings, copy files of the machine that typesets it (`file:///etc/passwd`) or responses from the internal network (`http://169.254.169.254/…`) into the output PDF, by making another reference (`<link>`, `url()`; even one written inside an XML comment is picked up) collect them
  - Parentheses in PDF strings are escaped: the name after `#` in a link to a relative PDF (GoToR) and the name of an attached file were written into literal strings as they were, so a `)` could close the string and add entries (`/S /JavaScript /JS (…)` and so on) to the action dictionary, bypassing the link restriction above. For file names the same was possible with characters whose low 8 bits are a parenthesis (U+0128, U+0129). A file name with non-ASCII characters (`資料.pdf`) is now written as a file specification dictionary (ISO 32000-2 §7.11.3, with the Unicode name in `UF`), and the name of a named destination as UTF-8 bytes (before, only the low 8 bits of each character were written, and links to PDFs with Japanese names could not be opened)
  - Node command: control characters in warnings and error messages (escape sequences and line breaks written in the document) are printed in a visible form such as `\x1b`, so that a document written by someone else cannot rewrite the screen or the title of the terminal of the person who typesets it, or forge report lines
  - The allow function passed to `fetchImages` / `fetchStyles` is also asked about redirect targets. On Node, redirects are followed one hop at a time and no request is sent to a target that is not allowed (up to 20 hops). A redirect from `https:` to `http:` is not followed even with the default (`true`). In browsers the request does reach the redirect target, and the response is discarded if the target is not allowed (browsers do not expose the target beforehand)
  - Size limits for CSS (16 MB), fonts (128 MB) and images (256 MB) fetched from the network; reading stops as soon as the limit is exceeded
  - Limits on EPUB decompression (256 MB per entry: skipped with a warning beyond it; 1 GB in total and 65,535 entries: an error beyond them)
  - `root` of `createFileResolver` is checked on real paths (see the item above)
  - GitHub Actions: the token of the CI workflow is read-only, and the permissions to deploy to Pages and to publish to npm are given only to the jobs that deploy and publish. Publishing now takes the tarball built by the checking job and publishes it from a job that installs no dependencies and runs no scripts
  - GitHub Actions: the actions used by the workflows are now pinned to commit SHAs instead of tags (`@v6` and so on); tags can be moved later, and this keeps a workflow that holds publishing rights from running different code. Dependabot (`.github/dependabot.yml`) opens PRs for updates
  - Node command: `--no-outside-files` stops reading files outside the input directory that the document points at with `file:` URLs or `../` (for documents written by others; by default they are still read)
  - Network images are fetched up to 8 at a time, and fetching the images of a document has an overall time limit (10 times the limit of a single fetch, 5 minutes by default). They used to be fetched one at a time, so a document listing unresponsive URLs kept fetching for as long as it liked. Fetched images are registered in document order (which image a bare file name resolves to no longer depends on response speed)
  - A Content Security Policy for the browser app (`index.html`; only the site's own scripts run). Dependabot now also watches the npm dependencies

- **Robustness against broken or crafted input** (input that used to hang or crash the process now makes only that image or declaration unreadable; the limits and their rationale are in the source comments):
  - Layout: fixed a hang when a paragraph beside a narrow float gap directly follows a table with `border-collapse: collapse` and an outer border. As a consequence, a box moved below a float (`clear` etc.) right after such a table is now placed exactly at the bottom edge of the float (it used to overlap it by half the border width; CSS 2.1 §9.5.2)
  - XSL-FO: `fo:retrieve-marker` and `fo:marker` inside `fo:marker` are skipped and reported (XSL 1.1 §6.13.5, §6.13.6); an FO document whose elements nest 250 levels or deeper fails with a clear error
  - Math: no crash on extreme `scriptlevel` (math-depth is clamped to ±100; MathML Core 4.5), long `mtext`, very many children or deep nesting (up to 300 levels)
  - HTML and CSS: no crash on `attr()` without arguments, cyclic or exploding `@import`, multiply nested `var()`, huge `colspan`, `rowspan` and `<col span>` (the HTML limits of 1000 and 65534), huge `repeat()` (up to 10000 columns), or overlong counter representations (the fallback style is used beyond 1000 characters; CSS Counter Styles 3 §2). Elements nested deeper than 128 levels are read as following siblings of their ancestor at level 128, with a warning. An `@import` dropped because too much CSS was imported is also reported as a warning. An image URL that could not be fetched is tried only once (the image list of the import report no longer contains duplicates)
  - SVG: no hang on path data with numbers after `Z`, multiplicative expansion of `use`, marker, pattern and mask (up to the number of elements + 500,000 visits), or a long `<style>`
  - WMF, EMF and CGM: point counts, character counts and color table sizes are bounded by the record length; the images of one document may total up to 64 million pixels
  - WMF, EMF and CGM: the total number of pixels that may be turned into images is now also bounded by the file size (260 thousand pixels + 1,024 pixels per byte of the file; the overall limit of 64 million pixels is unchanged). A file of a few hundred bytes using run-length codes (RLE DIBs, run-length cell arrays, tile arrays) could produce a 64-million-pixel image (over a minute and 1.7 GB of memory). **A small file holding an image sparser than 1,024 pixels per byte (for example a large, almost blank scanned image) no longer has that image drawn** (the rest of the document is typeset; a file larger than about 61 KB may use the full 64 million pixels as before)
  - CGM, WMF and EMF: patterns (CGM PATTERN TABLE and geometric patterns, WMF/EMF pattern and hatch brushes) no longer write out the whole pattern definition every time they are used; identical contents share one definition (for CGM, each use is a pattern that references the content pattern by href and only gives its placement; SVG 2 §14.3.4). A CGM of about 27 KB using a 4,096-cell pattern 2,000 times used to fail with an over-long SVG string (about 8 seconds); it now takes 0.6 seconds and produces 520 thousand characters. When the cells of a CGM pattern are written as rectangles, each cell counts as 16 pixels towards the pixel limit. The drawings do not change
  - GIF: the number of pixels is now also bounded by the file size (1 million pixels plus 4,096 pixels per byte of the file, up to 100 million). GIF dimensions are 16-bit, so a 34-byte file could specify 10000 × 10000 pixels, taking 12 seconds and 2.1 GB of resident memory to typeset. GIFs over the limit are not read; a placeholder frame is drawn with a warning. LZW codes are at most 12 bits and one code stands for at most 4,096 pixels (GIF89a, Appendix F), so legitimate GIFs (at most about 2,730 pixels per byte) stay within the limit
  - WebP, JPEG and CCITT: the number of pixels is now also bounded by the data size (1 million pixels plus, per byte, 2,048 pixels for VP8, 32,768 pixels for VP8L and the canvas of animated WebP, 1,024 pixels for JPEG, 2,048 pixels for one-dimensional CCITT coding and 131,072 pixels for two-dimensional coding; with two-dimensional coding the number of rows is at most the number of data bits). A file of a few dozen to a hundred-odd bytes with only large dimensions created a 100-million-pixel array, taking 11 to 19 seconds and 2.1 to 2.6 GB to typeset (a 50-byte VP8: 18.9 seconds and 2.6 GB). The VP8, JPEG and one-dimensional CCITT values exceed the most pixels one byte can represent in the standard coding (the fixed probabilities of RFC 6386 §11.2 and §11.4, the Huffman code lengths of T.81, the code tables of T.4). **A large lossless WebP that is entirely (or mostly) one colour, and a blank CCITT image wider than 16,384 pixels, are not drawn when they exceed the limit** (the zero-bit codes of VP8L and the one-bit white rows of T.6 have no density limit in the standards). Images over the limit are drawn as a placeholder frame with a warning. For CCITT TIFFs the same limit is also checked before falling back to utif when the built-in decoder cannot read the image
  - PNG (Node): the number of pixels (up to 100 million) and the decompressed scanline size (up to 1,032 times the IDAT data, the deflate limit of RFC 1951) are checked before pdf-lib's `embedPng` decompresses the image. A 65-byte PNG with only large dimensions took 9 seconds and 1.3 GB. A PNG over the limit is drawn as a placeholder frame with a warning (images inside SVG and colour glyph images are not drawn)
  - WOFF and WOFF2: the unpacked font may be up to 128 MB, and no more than 100 times the file size + 1 MB (WOFF 1.0 tables are additionally limited to the deflate ratio of 1,032). The tables were unpacked to the 32-bit lengths in the directory, so a 300 KB WOFF took 5.6 seconds and 2 GB, and a 558-byte WOFF2 took 3.3 seconds and 1.7 GB and stopped the document from being typeset. Fonts over the limit are reported as unreadable fonts. zlib decompression (`inflateBytes`) now collects its output in a byte array instead of an array of numbers (which used 8 bytes of heap per byte)
  - TIFF: the per-image pixel limit (100 million pixels) now also applies to PackBits, LZW, Deflate and other TIFFs (a 124-byte TIFF with only large dimensions used 1.6 GB of memory, and larger dimensions allocated correspondingly more). **A TIFF of more than 100 million pixels is treated as an image that cannot be drawn**
  - BMP: RLE8 and RLE4 BMPs are now drawn in Node as well (they used to be drawn as a placeholder frame; the same expansion as metafile DIBs; pixels left unspecified get colour table entry 0). The number of pixels is also bounded by the file size (1 million pixels plus 1,024 pixels per byte)

The sample array of a sampled function, the array of `matrix`, the glyph count of CFF fonts and the ranges added by `usecmap` are charged to the VM, memory and work accounts.     - PNG: a PNG whose `IHDR` is not the first chunk, of length 13, and the only one is not read (pdf-lib sizes its arrays from the last `IHDR`).     - BMP: a bit count other than 1, 4, 8, 16, 24 or 32 is not read (0 passed the file size check)

    - Fonts: when `@font-face` points at a font collection (a TTC or a WOFF2 collection), only the first font is extracted (all of them used to be extracted and the first one used). All values of `retrieve-position-within-table` and `retrieve-boundary-within-table`. When the retrieved content changes the height of the header or footer, the number of rows that fit on the page changes too. The form written as a child of `fo:table` is not supported (reported)

The width of the character differs, so line breaks in documents with `hyphenate="true"` can change. The compatibility mode (`--compat antenna`) and HTML keep U+002D. Write `hyphenation-character="-"` to get U+002D
- **Chinese (Traditional) punctuation**: punctuation drawn in the centre of the character frame (`、。，．` in Traditional Chinese fonts) is no longer trimmed by half an em and overlapped by the next character (`。」`, `，」`, `、）` and so on). Whether full stops, commas and colons (`：；`) are trimmed as closing punctuation or as middle dots is now decided from where the font draws the glyph (CSS Text 4 §8.5.3; colons at the lower left in Simplified Chinese fonts are closing punctuation). Results with Japanese fonts do not change
- **Vertical punctuation (Traditional Chinese fonts)**: when a font has `vert` but does not substitute the comma or full stop, the default (centred) glyph is used as is (it is not replaced by the Unicode vertical form, which sits at the upper right)

In documents that only have `<html lang="ja">` or `<html lang="zh-…">`, the Japanese- and Chinese-only rules of `line-break: normal` (also the initial value `auto`) and `loose` now apply (a break is allowed before `〜` and `゠`, and so on; CSS Text 3 §5.2). **Results change**: in such documents the position before `〜` becomes a line break opportunity and a place where justification may add space. The hyphenation language of `hyphens: auto` also follows the `lang` of `html` (documents in languages other than English and Latin are no longer hyphenated with the English rules). With `--style ah`, the choice of the line's baseline (whether the document is CJK) also follows the `lang` of `html`
- **Chinese quotation marks for `quotes: auto`** (the `q` element and so on): Simplified Chinese (`zh`, `zh-Hans`, `zh-CN` and so on) uses `“ ” ‘ ’`. Traditional Chinese (`zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO`) keeps `「 」 『 』` (the CLDR quotation marks that CSS Content 3 §4.1 refers to)
- **Latin-script text (Vietnamese), Greek and Cyrillic**: decomposed sequences (NFD, such as `e` + U+0323 + U+0302 or polytonic Greek) of Latin, Greek and Cyrillic letters are set with the precomposed character when the font has it (same appearance and width as the precomposed form; CSS Fonts 4 §5.3). Latin Extended Additional (U+1E00–1EFF: `ế`, `ệ`, `ṃ` and so on) is set in the same Latin font as the rest of the word and takes part in Japanese–Latin spacing and pair kerning. Greek and Cyrillic pairs are kerned with the font's kern data
- **Right-to-left scripts (Arabic, Hebrew)**: Arabic combining marks are stacked in the order of UTR #53 (a fatha sits above a shadda). The zero-width non-joiner (U+200C) inside a word has no width, and stand-alone invisible characters such as LRM, RLM and WJ have no width (they used to take the width of a space). Arabic in vertical text is joined and set sideways as a word (CSS Writing Modes 3 §5.1.1). Text can be extracted from the PDF in reading order (ActualText per word or cluster; fixes swapped or wrong characters). In the Canvas outline renderer, marks of right-to-left clusters are placed correctly. With the Hebrew letters of Tinos, vowel points and cantillation marks now avoid each other (the fixes for the font's contextual rules also apply to right-to-left scripts)
- **Greek and Cyrillic in Japanese documents**: with a generic or default font (a pair of a Japanese font and a Latin font), a word of two or more Greek or Cyrillic letters (`Россия`, `Ελλάδα`, `αβγ`, `Санкт-Петербург`) is set in the Latin font like a Latin word, and Japanese–Latin spacing is inserted between it and Japanese characters (before, letters the Japanese font has were set in the Japanese font and only the others in the Latin font, mixing fonts within one word). A single letter (`α`線, `Ω`, `β`-カロテン, `μ`m) stays in the Japanese font as before. **Results change** for words of two or more Greek or Cyrillic letters that were set in the Japanese font. Not changed with Antenna House compatibility (`--style ah`, `--compat antenna`)
- **Hyphenation**: added rules for Russian (`ru`), Ukrainian (`uk`) and Modern Greek (`el`, monotonic spelling) (`hyphens: auto`, `hyphenate="true"`; in text of these languages, words in Cyrillic or Greek letters are broken). The rules are loaded only when a document that uses them is opened
- **Hebrew (Tinos, Arimo and similar fonts)**: a dagesh or a shin/sin dot written after a vowel point now forms the glyph combined with the consonant (the points are passed to the font in the same order as HarfBuzz). The reordering of Arabic and Hebrew combining marks applies only to what is passed to the font; text extracted from the PDF keeps the original order

For each language and script, a table gives whether the default fonts can set it or a font must be specified (and the fonts it was checked with), how lines wrap, vertical writing and the main limitations (it also names the scripts that have not been checked and the languages that have hyphenation rules; variable fonts and color emoji fonts can be used as described in the "Variable fonts" and "Fonts with colored glyphs" items above). The value table of section 5.4 of the XSL-FO volume now lists the same languages with hyphenation rules as the text (Russian, Ukrainian and Modern Greek were missing). The "Other scripts" item of the README now mentions Chinese, Vietnamese, Greek and Cyrillic and points to this table

- **Height of the background, border and link area of inline boxes (`span` and so on)** (HTML): now the ascent above and the descent below the baseline of the element's first available font (the hhea ascent and descent) (CSS 2.1 §10.6.1, CSS Inline 3 §6.4). **The rendered result changes**: it used to be the font size (1em) high. With the default fonts (Latin Tinos / Arimo paired with the Japanese fonts) it is about 1.11em (0.01em more above, 0.10em more below), with the monospace font (Cousine) 1.13em, and with fonts that are tall above and below (Myanmar, Tibetan and so on) it covers the whole of the characters. Documents that specify only a Japanese font through `@font-face` keep the character frame (1em) and do not change (for fonts whose OS/2 typo ascender and descender span 1em, those values are used; Chromium uses the hhea values, which gives about 1.44em for Noto Serif JP and Noto Sans JP). The frame of a `span` that contains an image, ruby or superscript encloses the height of that element's text, not the whole line. Line heights and character positions do not change. `fo:inline` in XSL-FO does not change
- **Side of ruby and emphasis marks in vertical writing (`writing-mode: vertical-lr`)** (HTML): ruby (`ruby-position` unspecified or `over`) and emphasis marks (`text-emphasis-position` unspecified or `right`) are placed to the right of the text (CSS Writing Modes 3 §6.4: the over side of a line is the right in vertical-lr too; CSS Ruby 1 §4.1, CSS Text Decoration 4 §3.4). `under` and `left` go to the left. **Results change for vertical-lr documents**: they used to go on the opposite side (ruby and emphasis marks on the left, `ruby-position: under` on the right), and emphasis marks could not be put on the right. Horizontal writing, vertical-rl and XSL-FO do not change
- **Line spacing for ruby on the under side (`ruby-position: under`)** (HTML): when `line-height` is too small to hold the ruby, the missing amount is added on the side that has the ruby (below the line; on the left in vertical writing) rather than above the line (CSS Ruby 1 §3.6). With ruby on both sides it is split above and below in proportion to their thickness. **Results change for documents that use `ruby-position: under` with leading narrower than the ruby**: the space used to be added above the line, so the ruby below overlapped the characters of a following line without ruby. Ruby that fits in the leading and ruby on the over side do not change
- **Boxes of `::before` and `::after`** (HTML): background, border, padding, left and right `margin`, `vertical-align` and `box-decoration-break` now apply to a `display: inline` `::before` or `::after`. A `display: inline-block` `::before` or `::after` also takes `margin` (a negative `margin-left` can move it out to the left), border, background and height (CSS Pseudo 4 §4.1; until now only the text formatting, and the width and padding of an `inline-block`, were applied). **Results change**: backgrounds, borders and margins written on `::before` and `::after` are now drawn and take up space (for example, the space of `li::before { margin-right: 0.5em }` is inserted). An `inline-block` `::before` or `::after` without a width becomes one unbreakable box in the line (no line break inside its content)
- **Negative `margin` of inline boxes and line breaking** (HTML, XSL-FO): the negative left and right `margin` of a `display: inline` box (`span` and so on; in XSL-FO, `space-start`, `space-end` and `margin` of `fo:inline`) is now counted when deciding whether content fits on the line (CSS 2.1 §8.3, §9.4.2, §10.3.1). **Results change**: text that fits on the line once a negative right (end side) `margin` is subtracted now stays on one line (until now the line was broken using the width before subtracting the negative `margin`). Lines without a negative `margin` do not change
- **Text formatting of page margin boxes** (HTML): in margin boxes such as `@top-center`, `font-variant: small-caps` and `font-variant-caps`, the `font` shorthand, `text-transform`, `text-decoration`, `word-spacing`, `white-space`, `font-variant-*`, `font-feature-settings`, `font-kerning`, `font-stretch`, `font-variation-settings`, `font-palette` and `hyphens` now apply (CSS Paged Media 3 §6 and Appendix A; until now only font size, family, weight, style, color, line height and letter spacing were read). These declarations written in `@page` are inherited by the margin boxes. **Results change**: these declarations written on margin boxes (and in `@page`) now take effect (for example, the running head of `@top-right { content: string(heading); font-variant: small-caps }` is set in small caps, and the size and weight of the shorthand `font: bold 9pt sans-serif` apply). `text-transform` and small caps do not apply to the digits of `counter(page)` or to `element()` elements
- **Fonts without a space glyph** (XSL-FO, HTML): in text whose `font-family` names a font that has no glyph for a space (U+0020, U+00A0, U+202F, U+3000 and so on; emoji fonts, icon fonts, Latin fonts without a narrow space), spaces are now set in another font that has the glyph (the same fallback as for other characters missing from that font; CSS Fonts 4 §5.2). **Results change**: until now such a space became the missing-glyph mark (□) or was as wide as the font's missing glyph. The width of those spaces changes, and so does the height of a line that names only such a font (the font that decides the line height is the first font that has a space)
- **Inherited `font-family` and the element's language** (HTML): an element that inherits `font-family` from its parent now also chooses fonts by its own `lang` when it has one (the same result as an element that specifies `font-family` itself; CSS Fonts 4 §5.2). **Results change**: in a Japanese document, in elements whose `lang` is not Japanese, Chinese or Korean (`<p lang="ru">`, `<span lang="en">` and so on, without their own `font-family`), single Cyrillic and Greek letters (Russian `и`, `в`, `у` and so on) and symbols that the Latin font has (`—` and so on) are set in the Latin font instead of the Japanese font. - **Documents that list several `@font-face` rules with the same name** (HTML): when two or more `@font-face` rules have the same `font-family` and the same set of descriptors (`font-weight` and so on), they are now searched per character from the last one written, as in CSS Fonts 4 §4.5 and §5.2 (characters missing from the later font come from the earlier one). **This changes typesetting results**: previously only the first rule was used. A `@font-face` without a `font-weight` descriptor is selected as a weight-400 face even if the font file is bold (§4.4; bold text is drawn by emboldening that font). With `--style ah`, to match the output of AH Formatter, a `@font-face` without a `font-weight` descriptor is used as a face of the weight of the font file itself (usWeightClass in OS/2), so that bold text in a document that lists Regular, Bold and Heavy files under one name is set in the bold file (previously Regular was emboldened, which looked outlined)
- **Line spacing for second-level ruby and for emphasis marks under or to the left** (HTML): second-level ruby without a position (under the base; to the left in vertical writing) and emphasis marks under the text (`text-emphasis-position: under`; `left` in vertical writing) no longer count toward the line height, like ruby and marks on the over side; only the amount that does not fit in the leading is added on the side that has the annotation (CSS Ruby 1 §3.6, CSS Text Decoration 4 §3.4). **Results change**: until now such a line became taller by part or all of the annotation thickness (half the body font size; 5pt for 10pt text) even when the leading had room (2.5pt for a 10pt line with `line-height: 2`). **Lines with emphasis marks under the text or second-level ruby now have the same line pitch as other lines** (when the leading, `line-height` minus the font size, is at least the annotation thickness; when it is not, the line grows only by the missing amount). Ruby and emphasis marks on the over side in Japanese horizontal writing, and XSL-FO, do not change

  - In the result (Area Tree), `GlyphArea.fontFamily` of a glyph set in an italic face or a face of another width has a mark after the font name (`Arial{ital=1}`, `Arial{wdth=75}`)
- **`font-family` lists in XSL-FO**: when the list names two or more loaded fonts (such as `font-family="Times New Roman, MS Mincho"`), characters missing from the first font (Japanese characters, for example) are now typeset in the next font of the list (XSL 1.1 §7.9.2: each character is looked up through the list in order, the same as in HTML). **Typesetting results change**: until now such characters were typeset in the default font (Noto Serif JP and so on), not in the later fonts of the list
- **Images supplied through `resolveResource` (references with `%xx` in the name)**: image references whose names contain spaces, parentheses, Japanese and so on, such as `<img src="/a%20b.png">`, came out as "image not found" even when `resolveResource` returned the data (the function was asked with the URL as written, `%xx` included, while images were matched by the decoded name, so the two did not meet). Fixed; the same applies to CSS `url()` and XSL-FO `fo:external-graphic`. Images passed in `files`, and references to CSS files and fonts, already worked
- **The exception "Trying to access beyond buffer length" when drawing to a canvas (`renderPage`)**: a page with a no-break space (U+00A0, `&nbsp;`) set in the default Latin font (Arimo) with OpenType features applied (`font-feature-settings` and so on) threw and could not be drawn. Fixed. The cause was that fontkit reads the glyph header even for TrueType glyphs without an outline (spaces), so it read past the table when the last glyph of the font is a space (U+00A0 in Arimo). The bounding box of an outline-less glyph is now empty without reading glyf (which also corrects the bogus boxes other spaces got from the neighboring glyph). In addition, a run that cannot be turned into outlines is now drawn with `fillText`, so the rest of the page is still drawn
- **Warnings on the screen (Kumiori in the browser)**: warnings from reading the document are now listed one by one in the left column (before, only the layout warnings were shown, joined into one line; the others went to the console or were not shown). Added: unsupported CSS / XSL-FO and unknown CSS properties, links whose actions were not written to the PDF for safety, nesting deeper than 128 levels and too many `@import`s, EPUB items skipped for exceeding the limits, images not fetched, and font notices. Identical messages are merged, and four or more are collapsed to a count (the count also appears in the top bar)
- **"Default page size" in the screen settings**: choose the paper for HTML that does not specify `size` in `@page` from A4, A5, B5, JIS-B5, letter or free input (`A5 landscape`, `148mm 210mm`); the same as the CLI's `--page-size` and the API's `pageSize` (the default stays A4)
- **Position of SVG `text` when its first character is inside a `tspan`** (SVG images in HTML and XSL-FO): **results change.** In `<text x="…" y="…"><tspan>…</tspan></text>`, where the first character is inside a child `tspan`, the `x` and `y` of the `text` were ignored and the characters were placed at the origin (usually outside the picture). Fixed (SVG 1.1 §10.5: when the `tspan` has no value of its own, the ancestor’s value applies to that character). An empty `y=""` or `dy=""` on a `tspan` is read as not specified. Text that used to disappear now shows in documents that use such an SVG as a background (for example a watermark given as `background-image` on `fo:region-body` in XSL-FO) or as an image
- **XSL-FO: an `fo:flow` is flowed into the region that matches its `flow-name`** (XSL 1.1 §6.4.1.4): **results may change.** When an `fo:page-sequence` has several `fo:flow` elements, the first one used to be flowed into the body whatever its `flow-name`. Now the `fo:flow` whose name matches the body region (`fo:region-body`: its `region-name` if given, otherwise `xsl-region-body`) is flowed into the body. Documents with a single `fo:flow`, and documents whose first `fo:flow` matches the body region, are unchanged. An `fo:flow` whose name matches no region, or one without `flow-name`, is still flowed into the body, with a warning ("no region matches flow-name "…"; its content was flowed into the body region"; it used to be reported as the unread attribute flow-name)
- **XSL-FO: unprefixed attributes on `axf:form-field`** (`field-type`, `field-name`, `field-default-text`, `field-maxlen`, `field-multiline`, `field-checked`, `field-value`, `field-button-face`, `action-type`, and `field-submit-method` on `axf:form`, among others): **results change.** Attributes written without `axf:` on `axf:form` and `axf:form-field`, as in Antenna House’s examples and samples, were not read (every field became a "text" field with a generated name, and default values, options and button captions were lost). They are now read like the `axf:` names (`axf:field-type` etc.), whatever `--compat` is (the `axf:` name wins when both are present). Per-event actions (`axf:form-field-event`) and button `action-type` values other than `submit` and `reset` (`javascript`, `uri` etc.) are still not written to the PDF (no scripts are written); the warning now names them
- **XSL-FO: gradients in `background-image`** (`linear-gradient()`, `radial-gradient()`, `repeating-linear-gradient()`, `repeating-radial-gradient()`): in compatibility mode (`--compat antenna`, `compat: 'antenna'`) they are drawn as the same gradient backgrounds as in HTML (**results change in compatibility mode**: nothing was drawn before, and there was no warning). The values of `background-image` in XSL 1.1 §7.8.3 are `<uri-specification> | none`, so in specification mode they are not drawn and a warning reports them (`background-image:linear-gradient()`). The same applies to a gradient inside the `background` shorthand
- XSL-FO: `axf:background-size` (size of the background image: lengths, percentages, `auto`, `cover`, `contain`; first layer only) is read, whatever `--compat` is (**results change for documents that use this attribute**: it used to be reported as unread). `background-image`, `background-repeat` and `background-position` on `fo:simple-page-master` are read as the page background image in compatibility mode only (by the specification the background properties do not apply to `fo:simple-page-master`, so in specification mode they are still reported in the warning)
- XSL-FO: a `start-indent` written as a length on the `fo:list-item-body` of the second and later list items is read (XSL 1.1 §7.11.7). When it equals the value on the first item the result is unchanged and the warning "unread attribute start-indent (fo:list-item-body)" no longer appears. A value larger than the first item’s indents that body by the difference (**results change for documents written that way**: the body used to be placed at the first item’s position). A smaller value cannot be placed and is still reported in the warning
- **XSL-FO: the background color is now painted up to the padding rectangle** (XSL 1.1 §4.9.4; independent of `--compat`): **results (appearance) change.** The background color used to be painted up to the outer edge of the border (the border box), so it showed through the gaps of dashed, dotted and double borders and under borders with a transparent color. It is now painted up to the inner edge of the border (the padding rectangle), as the specification says. Only boxes that have both a background color and a border with gaps (dashed, dotted, dot-dash, double, wave) or a transparent color on the same element change (`fo:block`, `fo:block-container`, `fo:table`, `fo:table-cell`, region borders in compatibility mode, and so on). Boxes with opaque solid or 3D-style (`groove`, `ridge`, `inset`, `outset`) borders and boxes without borders are unchanged. With rounded corners (`axf:border-radius`) the background corners follow the inner curve of the border. The parts that overlap the outer border of a collapsed-border table are not changed yet (backgrounds of inline boxes, `fo:inline`, are also painted up to the padding rectangle, as described in a separate item above)
- **Content written after `</body></html>`** (HTML; the Node command and the API; **the result changes**): elements and text written after `</html>` (or `</body>`), as in `<html><body><p>a</p></body></html><p>b</p>`, were dropped. They are now laid out as a continuation of body, as browsers do (the "after body" and "after after body" insertion modes of the HTML Standard). Comments after the end, and whitespace at the end of the document, add nothing, as before
- **Positive left and right `margin` on inline boxes and line wrapping** (HTML; **the result changes**): the left and right `margin` of a `display: inline` box (`span` and so on) is no longer separated from the first and last characters of the box (CSS 2.1 §9.4.2, CSS Text 3 §5.5: a line is broken outside the margin edge of the box). Before, the end `margin` could be left at the start of the next line, shifting the first character to the right (setting `一二三四<span style="margin-right: 30pt">五</span>六七` five characters wide shifted 六 by 30pt), the start `margin` could be left at the end of the previous line, an empty line was added at the end of a paragraph, and a full stop could come to the start of a line. Now, when the `margin` does not fit on the line, the character moves to the next line with it (as in browsers). An inline box with `box-decoration-break: clone` also gets its left and right `margin` on each fragment (CSS Fragmentation 3 §5.4). Only with the AH Formatter compatible style (`--style ah`), a start `margin` that comes to the start of a wrapped line is dropped (as in the reference output). Inline boxes without `margin`, negative `margin`, and `space-start` / `space-end` in XSL-FO are unchanged
- **Heading of the conversion report on the screen**: the report said "XSL-FO 変換レポート" (XSL-FO conversion report) even for HTML documents (EPUB included); the heading now follows the kind of document ("HTML 変換レポート" for HTML; the hint for images not found and the line shown when nothing is unsupported also follow the kind of document)
- **`@font-face` fonts of a previously opened document staying on the screen (Kumiori in the browser)**: when HTML documents that use the same `font-family` name for different font files were opened one after another, the later document was set in the font of the earlier one (and a bold face that only the earlier document had could be used for bold text in the later one). Each time a document is opened, its `@font-face` files are now registered again and faces that only the previous document had are removed (including the fonts registered with the browser). Re-laying out the same document after changing a setting does not reload the fonts. The Node command and the API already keep fonts separate per document and are unchanged
- **Kerning in content-size estimates (max-content, min-content)** (HTML): content widths such as those of flex items (children of `display: flex`) were estimated without kerning, so runs that kerning widens (such as "2.2" in some fonts) did not fit the item's width and split into "2." and "2" with `overflow-wrap: break-word`. The estimate now adds the same kerning to the same character pairs as line layout does (following `font-kerning` and the "kern" setting of `font-feature-settings`). **Results change** (boxes sized by their content, with kerned Latin text, get slightly different widths)
- **XSL-FO: `background-color` on `fo:simple-page-master` is read only in compatibility mode (`--compat antenna`)**: the background properties do not apply to `fo:simple-page-master` (XSL 1.1 §6.4.13), so in specification mode (the default) it is not read and the load warnings report it. **Results change for documents typeset in specification mode** (a background color written on the page master no longer appears). `axf:background-color`, whose name carries the prefix, is read in every mode
- **PDF: the original text (ActualText) attached to words in right-to-left scripts (Arabic, Hebrew) is now written in reading order** (ISO 32000-2 §14.9.4: replacement text is the characters equivalent to what a person sees). It used to be written in drawing order (left to right). **Text extracted from the PDF changes**: in the Chrome and Edge viewers (PDFium) the characters of each word now come out in reading order (they were reversed); poppler's pdftotext and MuPDF also reorder ActualText characters, so their words now come out reversed (they used to be in reading order). The appearance does not change

## 0.1.0 (2026-11-08)

The first public release.

- **Input**: HTML+CSS (own CSS cascade), XSL-FO 1.1 (supports part of Antenna House's `axf:*` extensions, focusing on the commonly used ones), JSON logical tree
- **Japanese typesetting**: vertical and horizontal writing, ruby, tate-chu-yoko, emphasis marks (kenten), line-breaking rules (kinsoku), hanging punctuation and pushing out, punctuation compression, spacing between Japanese and Latin text (JLREQ)
- **Pages**: page masters, running heads and page numbers (folios), footnotes, multi-column layout, floats, tables (splitting, repeated headers, automatic column width), page number references, bookmarks, links, annotations, forms
- **Output**: Canvas preview, PDF (subset font embedding, trim marks, PDF/X-3 marking)
- **Other scripts**: right-to-left scripts such as Arabic and Hebrew (UAX #9, joined forms of Arabic letters), Latin hyphenation
- **Usage**: the browser web app, the Node CLI `kumiori` (`--help`, `--version`, `--lang ja|en` and `KUMIORI_LANG` for English messages, a cache for the default fonts, warnings for unsupported CSS and XSL-FO), the library (`kumiori`: ES module; `kumiori/browser`: a single file for browsers with the dependencies bundled; the `lang` option for English warnings)
- **Documentation**: the Conformance Guide (HTML and CSS volume, XSL-FO volume; Japanese and English editions), the Area Tree JSON specification, and English versions of the README and docs (README.en.md, docs/en/)
