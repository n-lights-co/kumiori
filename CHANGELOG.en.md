# Changelog

Version numbers follow [Semantic Versioning](https://semver.org/). During 0.x, incompatible changes may also be released in a minor version (such as 0.2.0).

## 0.2.0 (unreleased)

A release that adds flex features, WOFF/WOFF2, an API for loading referenced files, and more. While in 0.x, it is a minor release because it includes fixes that change typesetting results.

- **flex** (Flexbox 1; the CLI and the default layout path):
  - Shrinking (`flex-shrink`, the automatic minimum size of `min-width: auto`), the growth limit (stop at `max-width` and share the rest), growing when the sum of `flex-grow` is below 1
  - Reversed directions (`row-reverse`, `column-reverse`, `wrap-reverse`), containers with `direction: rtl`, vertical-writing containers
  - Alignment: `baseline` and `last baseline`, cross-axis `margin: auto`, `start`, `end`, `left`, `right`, `safe` and `unsafe` for `justify-content`, `align-content` for wrapping containers
  - Column direction: `row-gap`, `flex-basis`, `flex-shrink`, `flex-wrap` (wrapping into columns), growing in containers with a definite height
  - `order` also applies to `::before`, `::after` and children of `display: contents`; text directly inside a container becomes an anonymous item
  - Percentages in `gap`, `min-content` and `fit-content` for `flex-basis`, items with `visibility: collapse` (struts)
- **CSS**:
  - Supports `visibility` (`hidden`, `collapse`) and `aspect-ratio`
  - The horizontal margins of boxes with a definite width follow CSS 2.1 §10.3.3 (in a containing block with `direction: rtl`, boxes are placed from the right edge; a single `auto` margin takes the remaining space at layout time)
  - Collapsing of the bottom margin of the last child of a box with `min-height` follows CSS 2.1 §8.3.1
  - Sizes of boxes whose writing mode is orthogonal to the parent's (vertical writing inside horizontal, and horizontal inside vertical) now follow CSS Writing Modes 3 §7.3. **This changes typesetting results**: a vertical-writing float with a specified height wraps its lines at that height and is placed at the edge (before, long text ran on without wrapping and overlapped the body text). A vertical-writing item in a flex row takes its specified width (before, it shrank to the width of its lines), and without a specified width takes the width of its lines. A box with no specified size in its line direction (`height` for vertical writing) is fit-content (the length of the content, up to the available length), also inside table cells and absolutely positioned boxes. `max-height` and `min-height` act as the upper and lower limits of the line length
  - A vertical-writing absolutely positioned box with no specified height (its size in the line direction) takes the length of its content (shrink-to-fit, CSS 2.1 §10.3.7; before, it extended to the bottom of the page). Fixed the `width` (cross size) of items in a vertical-writing flex container being dropped
  - For a `display: block` image with both `width` and `max-width`, the wrapping box now has the width of the image
  - Named pages: no first page is created for boxes outside the flow alone (absolutely positioned, floats, etc.) (CSS Page 3 §8.1)
  - Properties that have no effect in print (`cursor`, `transition-*`, etc.) are no longer reported as unsupported CSS
  - `box-decoration-break: clone` (CSS Fragmentation 3 §5.4) is supported. Each fragment of a box broken across pages or columns, and each fragment of an inline box broken across lines (the border and background of a `span`), is wrapped again with its border and padding (vertical writing too; `-webkit-box-decoration-break` is also read). Results with the initial value `slice` are unchanged
  - Content-based sizes (CSS Sizing 3 §3.2): `min-content`, `max-content` and `fit-content` for `width`, `min-width` and `max-width` (`height`, `min-height`, `max-height` in vertical writing), and `fit-content(<length>)` (CSS Sizing 4 §3.2), are supported on block boxes and their floats, absolutely positioned boxes and inline-blocks (a keyword `width` on an item of a row flex container is read as that keyword of `flex-basis`). For the block axis, a keyword `height` behaves as auto. Keyword sizes on flex and grid containers and on tables are not supported and are reported in a warning. **A `fieldset` no longer becomes narrower than the min-content width of its content**, as the default HTML style sheet (`min-inline-size: min-content`) says
  - `initial-letter` (CSS Inline 3 §7; drop caps): the `::first-letter` character is sized by a number of lines and sunk (`initial-letter: 3`, `3 2`, `3 raise`, `initial-letter-align: alphabetic | ideographic | leading`). Its size and position are decided from the `line-height` of the paragraph and the cap height or em box of the font. CJK text (`lang` of `ja`, `zh`, `ko`) is aligned by the em box. Vertical writing is supported. Declarations on boxes other than `::first-letter`, `initial-letter-align: hanging | border-box` and `initial-letter-wrap` are not supported
  - `empty-cells: hide` (CSS 2.1 §17.6.1.1): borders and backgrounds of empty cells are not drawn in tables with separated borders; a row whose cells are all empty gets zero height
  - Percentage values of `vertical-align` (CSS 2.1 §10.8.1): an inline box is raised or lowered by that percentage of its own `line-height`
  - `text-align: justify-all` (CSS Text 3 §6.1): the last line is justified as well
  - XSL-FO: when both of two nested boxes specify `.conditionality="retain"` for their borders and padding, the outer fragment now encloses the trailing border and padding of the inner fragment (it used to be shorter by that amount)
  - Ruby placement: supports `ruby-position` (`under` places ruby below the base, to the left in vertical writing; combinations with `alternate`), `ruby-align` (`start`, `center`, `space-between`, `space-around`), `ruby-overhang` (an explicit `auto` lets ruby overhang adjacent kana and punctuation) and `ruby-merge: merge` (group ruby). The side and overhang of ruby without these properties are unchanged
  - The default distribution of ruby characters is now the initial value `space-around` of `ruby-align` (CSS Ruby 1 §4.3). **The default arrangement of Latin and bopomofo ruby changes**: it is centered over the base without space between its letters (previously every letter was spaced out). Japanese (kanji and kana) ruby and base text are unchanged. Ruby in XSL-FO is unchanged
  - Supports `font-variant-east-asian` (`jis78`, `jis83`, `jis90`, `jis04`, `simplified`, `traditional`, `full-width`, `proportional-width`, `ruby`; glyph forms and widths are selected through the font's OpenType features, and the values are also read from the `font-variant` shorthand)
  - Supports the line style of underlines, overlines and line-throughs (`double`, `dotted`, `dashed` and `wavy` for `text-decoration-style`), their thickness (`text-decoration-thickness`) and the underline offset (`text-underline-offset`); the `text-decoration` shorthand accepts the line style and thickness. The underline of an `abbr` with a `title` is now dotted, as in browsers (it was solid)
  - Supports the color (`text-emphasis-color`) and side (`text-emphasis-position`: `under` in horizontal writing, `left` in vertical writing) of emphasis marks; the `text-emphasis` shorthand accepts a color
  - `fill`, `stroke`, `color` and related properties (`stroke-width`, `fill-opacity`, `stroke-opacity`, `opacity`, `fill-rule`, line caps, joins and dashes) in the document's CSS now apply to an `<svg>` written directly in the document. `currentColor` takes the `color` inherited from outside the `<svg>` (`svg { fill: currentColor }` with `.icon { color: red }` colours the icon). SVG images also honour the `color` attribute with `currentColor`, and the alpha of `rgba()` colours
  - Support for the color functions `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, `color()` (CSS Color 4) and `color-mix()` (CSS Color 5). Output is sRGB; colors outside the sRGB gamut are brought into gamut by reducing chroma while keeping lightness and hue (CSS Color 4 §14.2). Until now, declarations using these colors were dropped (the color fell back to the initial or inherited value)
  - Supports transforms (the 2D functions `translate()`, `scale()`, `rotate()`, `skew()`, `matrix()` and lists of them for `transform`; `transform-origin`, `transform-box`; `translate`, `rotate`, `scale`) and opacity (`opacity`: the box and its content become translucent as a whole; PDF output uses a transparency group). Both take effect only when painting and do not change layout (positions, sizes, page breaks). 3D transforms are reported as unsupported
  - Supports multiple backgrounds (comma-separated layers of `background-image` and `background`, with per-layer position, size and repetition) and `background-clip` / `background-origin` (`border-box`, `padding-box`, `content-box`; also applied to the area the background color is painted in). `background-attachment: fixed` and `background-clip: text` are reported as unsupported
  - Supports `none` and `scale-down` for `object-fit`, `object-position` (the position of an image inside its box) and `list-style-image` (image markers for lists)
  - Hyphenation limits (CSS Text 4 §6.3): supports `hyphenate-character` (the string shown at the end of the line, also for lines broken at a soft hyphen), `hyphenate-limit-chars` (minimum characters in the word and before and after the break), `hyphenate-limit-lines` (maximum number of successive hyphenated lines), `hyphenate-limit-last: always` (no hyphenation before the last line of a paragraph) and `hyphenate-limit-zone`. `column`, `page` and `spread` of `hyphenate-limit-last` are not supported (reported as a warning)
  - Background images are painted under the border with the initial value of `background-clip` (`border-box`) (CSS Backgrounds 3 §2.7). **The rendered result changes**: in HTML, the background image or gradient of a box with a border is now painted under the border as well. With dashed, dotted or double borders, or transparent or translucent borders, the background image shows through the gaps in the lines (a repeated image is tiled from the top left of the padding box under the border as well; the position of a non-repeated image does not change). With opaque solid borders nothing changes, since the border hides it. To paint only inside the border as before, specify `background-clip: padding-box`. XSL-FO backgrounds are unchanged (XSL 1.1 §4.9.4)
  - Transparent and translucent border colors (HTML). **The rendered result changes**: a border with `border-color: transparent` used to be drawn as a black line and is no longer drawn (it still takes up its width). A border with a translucent color (`rgba()` and so on) is blended over the background beneath it with that opacity, instead of being drawn in an opaque color mixed with white (PDF output uses a transparency group; PDF/X-3 issues a warning)
  - CSS gradient backgrounds (`linear-gradient()`, `radial-gradient()` and their `repeating-` forms) are now also drawn on screen (Canvas: `renderPage` and the app view). **Previously they were drawn only in the PDF and were missing on screen** (the PDF output is unchanged)
  - Line decorations (underlines etc.) and atomic inlines (CSS Text Decoration 3 §2). **The rendered result changes**: a link with `display: inline-block` used to get two underlines (one under its text and one at the bottom of the box); it now gets only the one under its text. Images and inline-block boxes inside an underlined element are themselves no longer decorated (the line under an image inside a link disappears), and the lines of ancestors are not propagated to the contents of inline-blocks and inline-tables (the text before and after is still decorated, as in browsers). XSL-FO output is unchanged
  - The width of a box sized to its contents (`inline-block`, floats, absolutely positioned boxes, etc.) that inherits an indent (`text-indent`) now includes the indent (CSS Text 3 §8.1). **The layout result changes**: previously the box was too narrow by the indent, so its first line wrapped or its text stuck out of the box (the default style indents paragraphs by one character, so an `inline-block` inside a paragraph was affected). Now the box is wider by the indent and the contents fit on one line. To avoid indenting inside the box, specify `text-indent: 0` on it
  - `margin` on inline images (`img`; all four sides; CSS 2.1 §8.3 and §10.8). **The layout result changes**: previously the `margin` of an inline image was not read, so the image sat tight against the neighbouring text or images (the `margin` of block and floated images already worked). Now the left and right margins add space before and after, and the top and bottom margins count toward the line height (the `hspace` and `vspace` attributes too). For an inline image with a border, padding or background color, only the left and right margins apply (top and bottom are reported in a warning)
  - List items, table rows and forced breaks inside them (CSS Fragmentation 3 §2.1, §3.1 and §4.3). **The layout result changes**: `break-before` and `break-after` (`page` and so on) now take effect on blocks inside an `li`, on the `li` of a nested list, and on blocks inside a table cell (the item or row is split at that point; previously they were ignored). `left`, `right`, `recto` and `verso` on an `li` in the middle of a list or a `tr` in the middle of a table insert a blank page until the parity matches (previously they only started a new page). `column` on such an `li` or `tr` inside a multi-column context takes effect. `page` on such an `li` or `tr` in a document whose pages are set in columns starts a new page, not the next column. `break-before: column` and `break-after: column` outside a multi-column context have no effect (previously they started a new page even where there were no columns). In XSL-FO too, `break-before` and `break-after` on a block inside a table cell or a list item body split the row at that point (XSL 1.1 §4.8; previously ignored)
  - Containing blocks of absolutely positioned boxes (CSS 2.1 §10.1, CSS Position 3 §2.1). **The layout result changes**: a `position: absolute` box inside a table, table cell, list item or vertical-writing box with `position: relative` (or `transform`) is placed relative to the padding box of that box. When a table or list item lies between the box and its reference block, that block is still the reference (previously the body region of the page was used in all these cases, and the position was far off). The `position: relative` offset of a block in vertical writing is now applied in physical directions (`left` horizontally, `top` vertically). An element within a line (`span`, `inline-block`) with `position: relative` is also a reference (the rectangle around its padding boxes). A `position: absolute` box inside an inline element is no longer dropped. An absolutely positioned box in the middle of the text of a paragraph no longer splits the line. The `position: relative` offset (`top`, `left` and so on) of elements within a line (`span`, `inline-block`, `img`) now takes effect (CSS 2.1 §9.4.3; previously ignored)
  - Percentages for `top`, `bottom` and `height` of absolutely positioned boxes (CSS 2.1 §10.5, CSS Position 3 §3.1). **The layout result changes**: `top: 50%`, `top: 100%` (the drop-down pattern), `bottom: 10%`, `inset: 10%` and `height: 50%` are read as fractions of the height of the padding box of the containing block (when the height of that box depends on its content, the height after layout; with no positioned ancestor, and for `position: fixed`, the height of the page content area; also for absolutely positioned `::before` and `::after`). Before, percentages for `top` and `bottom` were treated as absent (the box appeared at the top of the reference box or where it was found), and percentages for `height` were taken from the content height of the parent
  - Positions of absolutely positioned boxes (NC-28). **The layout result changes**: an absolutely positioned box in the middle of a line of a paragraph whose `left` and `right` (and `top` and `bottom`) are `auto` is placed where it was found in the line (the static position; CSS 2.1 §10.3.7, §10.6.4). Before, it was placed at the start of the first line of the paragraph and overlapped the preceding text. Boxes found inside table cells are handled the same way. An absolutely positioned box inside a flex or grid container (horizontal writing) with `position: relative` (or `transform`) is placed relative to the padding box of the container (CSS Flexbox 1 §4.1, CSS Grid 1 §9.1; before, the body region was the reference). A `position: static` flex or grid container whose height depends on its content lets the reference pass through to an outer containing box. The `position: relative` offsets (`left`, `top`, etc.) of list items (`li`) and table cells (`td`, `th`) now take effect (CSS 2.1 §9.4.3; a list item moves together with its marker, and row heights and the positions of other cells do not change; before, they had no effect)
  - Tables with `writing-mode` (CSS Writing Modes 3 §2.1, CSS 2.1 §17). **The layout result changes**: a table (`table`, `display: table`) with `writing-mode: vertical-rl` or `vertical-lr` in a horizontal document is laid out vertically (rows run from right to left and the cells in a row from top to bottom; previously the `writing-mode` of the table was ignored and it was laid out horizontally). The same applies to a `horizontal-tb` table in a vertical document. The size of a table with separated borders (`border-spacing`) whose writing mode differs from its parent now includes the cell spacing
  - Anonymous table rows and cells (CSS 2.1 §17.2.1). **The layout result changes**: content that is not a table part (text or other elements) directly inside a table (`display: table`, `inline-table`) or a row (`table-row`) is wrapped in an anonymous row and an anonymous cell (previously it was dropped, for example the text of `<span style="display: inline-table">text</span>`)
  - `text-indent` on tables (CSS Text 3 §8.1 and the HTML default style sheet). **The layout result changes**: `text-indent` specified on a table now applies to the lines in its cells (previously ignored). `text-indent` from outside a table (`body`, `div` and so on) does not enter the table (`table { text-indent: initial }`; previously the outer indent applied to the lines in cells; this matches browsers)
  - Outlines (`outline`, `outline-width`, `outline-style`, `outline-color`, `outline-offset`; CSS UI 4 §3) are supported. A line that takes up no space is drawn outside the border box (rounded on boxes with rounded corners; an inline element that breaks across lines and a block that breaks across pages are enclosed fragment by fragment). They were previously reported as unsupported CSS
  - The clipping rectangle (`clip: rect(…)`; CSS 2.1 §11.1.2) is supported. **Results change for absolutely positioned boxes with `clip`**: the background, border and content of the box are drawn clipped to the rectangle. A box with the screen-reader-only idiom (`clip: rect(0 0 0 0)`) is not drawn. Previously `clip` was reported as unsupported CSS and the box was drawn without clipping
  - Tab size (`tab-size`; CSS Text 3 §4.2) is supported. **Results change for tab characters inside `pre` and the like**: a tab character (U+0009) inside `white-space: pre`, `pre-wrap` or `break-spaces` now advances to the next tab stop (every 8 spaces from the content edge of the block; changeable with `tab-size`) (CSS Text 3 §4.1.2). Previously the tab character was drawn as the missing-glyph mark (□)
  - For an `<svg>` written inline in the document, `stop-color`, `stop-opacity`, `text-anchor`, `clip-rule`, `marker` (`marker-start`, `marker-mid`, `marker-end`) and `vector-effect` now also take effect from the document's CSS (like `fill`, `stroke` and so on). Properties that apply only to SVG elements (`paint-order`, `cx`, `r` and so on) are no longer reported when the document has no `<svg>` (no element they apply to exists; with an `<svg>` they are reported as "unsupported (SVG elements)"; previously they were "unknown properties"). The rendering hints (`shape-rendering`, `text-rendering`) are not reported
- **Links and bookmarks**: `<a href>` on blocks, flex containers and tables makes the whole box a link; relative-reference links (GoToR for PDFs, Launch for other files; Launch is not written by default, see "Security" below); `h1` to `h6` become bookmarks with every default style (CSS GCPM 3 Appendix B). Added an option that writes relative-reference links as a URI action with the reference as written (`/S /URI /URI (x.pdf)`; `%xx` is not decoded): `links: { relative: 'uri' }` in the API and `--link-relative uri` on the command line (the default stays `'file'`). Such links also work in PDF viewers inside browsers, which do not handle GoToR and Launch. Relative non-PDF files are then written without `launch` (absolute paths and `//host/…` only with `launch: true`). For file names with non-ASCII characters (GoToR, Launch), `F` of the file specification dictionary is now the UTF-8 bytes of the same name instead of a name with `_` substituted (`UF` remains the Unicode name)
- **Tables**: in tables with `border-collapse: collapse`, the border between a table header or footer repeated at a page break and the adjacent row is chosen again from the borders on both sides (XSL 1.1 §6.7.10, CSS 2.1 §17.6.2.1)
- **Fonts**: reads WOFF and WOFF2 (including font collections) (`--font`, `fonts`, `@font-face`); fonts referenced by `@font-face` over `http(s):` are also fetched (only those whose `unicode-range` overlaps the characters of the document)
- **Variable fonts** (OpenType Font Variations, with TrueType outlines or CFF2 outlines): typeset with the shape (instance) for each combination of axis values. **Results change for documents that use variable fonts**: previously they were typeset as a single weight with the default instance; bold was synthesized by thickening the outlines and `font-stretch` scaled the glyphs
  - `font-weight` → weight axis (wght; no synthetic bold), `font-stretch` / `font-width` → width axis (wdth; glyphs are not scaled), `font-style` `italic` / `oblique <angle>` → ital / slnt axis (if present), `font-optical-sizing` → optical size axis (opsz; the font size in px for HTML, in pt for XSL-FO), `font-variation-settings` (any axis). The precedence follows CSS Fonts 4 §7.2
  - `@font-face` ranges `font-weight: 100 900`, `font-stretch: 75% 125%`, `font-style: oblique 0deg 10deg`, and the `font-variation-settings` and `font-named-instance` descriptors. A variable font without a `font-weight` descriptor also gets its weight axis set (for variable fonts whose default instance is not weight 400, the regular-weight glyphs change too)
  - Variable fonts given with `--font`, `fonts` or alongside an XSL-FO document use the full range of their axes. For XSL-FO, the family name of a variable font is now nameID 16 of the name table (the name covering all weights and widths)
  - In the PDF, each combination of axis values in use is embedded as a static font (advances from HVAR, kerning and mark positions from GPOS, font-wide metrics from MVAR, and glyph substitutions from FeatureVariations are those of the instance). On screen, the instance is registered with the browser as a static font and drawn with it
  - Area Tree: `fontFamily` of a glyph that uses an instance carries a mark for the axis values other than weight (`{;wdth=75}`). Instance entries in `resources.fonts` gain `variation` and `sourceSha256`. `TextStyle` gains `fontVariationSettings`, `fontOpticalSizing`, `fontOpticalSizeUnit` and `fontObliqueAngle`
  - Variable fonts with CFF2 outlines (variable OTF fonts) are also typeset with the shape for each combination of axis values. In the PDF they are rebuilt and embedded as static CFF fonts, including the default instance (previously the font embedded in the PDF was broken: text was displayed with a substitute font and could not be extracted). The shapes do not change, but the hints are not carried over. Non-variable fonts with CFF2 outlines can be embedded in the same way
  - Fixed a nested `font-stretch` that returns to 100% (normal) keeping the width inherited from the parent
- **Font lists** (HTML `font-family`): for each character (for combining sequences and emoji sequences, the whole sequence), the list is tried in order and the first font that has the character is used (CSS Fonts 4 §5.2, §5.3). The typeset result changes for lists where a generic name or the name of a default font comes before a loaded font (`--font`, `fonts`, `@font-face`), such as `"Noto Serif JP", "Noto Emoji", serif`, and for lists with two or more loaded fonts (spaces, digits and symbols that an earlier font has are no longer typeset with a later loaded font; the third and later fonts are also tried in order; Japanese characters are typeset with the font of the generic name)
- **Fonts with colored glyphs** (color emoji and so on): glyphs in the OpenType COLR/CPAL (versions 0 and 1; gradients, transformations, compositing), CBDT/CBLC, sbix and SVG tables are typeset in color. In the PDF they are written as a Type 3 font (the extracted text is the original emoji; each glyph is defined once in the document). The same shapes can be drawn on screen (Canvas). `font-palette` and `@font-palette-values` (`base-palette`, `override-colors`) select the palette. A character followed by U+FE0F is set in a color font, and one followed by U+FE0E in a font without colored glyphs. `fontPalette` was added to `GlyphArea` in the Area Tree (present only when the palette is not the default). **Until now, using a COLR font (Noto Color Emoji, Twemoji) crashed while writing the PDF, and CBDT fonts without outline tables could not be typeset**
- **Glyph shapes of OpenType fonts with CFF outlines (.otf)** (wherever glyphs are drawn from their outlines: outline drawing on the screen (Canvas), math, SVG text, colored glyphs. Body fonts embedded in the PDF were already correct, because the glyphs of the font are embedded as they are. Results with the default fonts (TrueType outlines) do not change):
  - In Japanese, Chinese and Korean fonts (CID-keyed; the .otf of Noto Sans JP, Source Han Serif and so on), some characters were drawn with a completely different shape or could not be drawn (the first glyph of each group of glyphs inside the font; in the Noto Sans JP .otf, 29 characters such as ":", "・", "※", "±", "■" and "ゝ"). This is fixed. Punctuation spacing and line breaking do not change
  - Glyphs that use the shallow-curve operators (Type 2 `hflex` and `hflex1`; fonts converted from Type 1, the mathematical monospace letters of the STIX Two Math .otf, and so on) had part of their outline shifted vertically by a few units, leaving a small step at a corner. This is fixed. The glyph bounding box is corrected too, so **in math that uses these glyphs, the height and depth of characters may change by a few units**
- **PDF**: in ToUnicode, ligature characters (U+FB01 etc.) map to the original character sequences (fi etc.), so text extraction and search find words such as "confiance"
- **API**:
  - `resolveResource(url)`: asks for files referenced by the document or CSS that are not in `files`
  - `fetchStyles`: fetches CSS referenced by the document over `http(s):` (including `@import` targets; default `true`)
  - `kumiori/node`: `createFontLoader` (the same default-font loading and cache as the CLI), `createFileResolver` (reads `file:` references), `defaultFontCacheDir`, `looksLikeFont`
  - Images returned by `resolveResource` are now used even when the URL has no extension (`<img src="https://example.com/img?id=1">`, and likewise `background-image`, `list-style-image`, `content: url()` and XSL-FO `external-graphic`). The image is recognized from the leading bytes of the content. **Previously, for a URL without an extension the returned content was not used and the image was fetched again from the network** (or was unreadable with `fetchImages: false`). Whether to fetch from the network (`fetchImages`) is decided as before
  - `pageSize`: changes the default paper for HTML (the paper of a document that does not specify `size` in `@page`; it was fixed to A4). Written like the CSS `size` property (`"A5"`, `"A5 landscape"`, `"148mm 210mm"`; CSS Paged Media 3 §7.1). A `@page { size }` in the document wins, and `width`, `height` and `orientation` in `@media` are evaluated against this paper. Without it the paper is A4 as before
  - `genericFonts` and the CLI `--generic-font`: the Latin font of the monospace generic family (`monospace`; Cousine by default) and the Japanese fonts of the generic families (`serif-cjk`, `sans-serif-cjk`; Noto Serif JP and Noto Sans JP by default) can also be replaced (CSS Fonts 4 §2.1.3; Japanese text in monospace uses the `sans-serif-cjk` font in HTML and the `serif-cjk` font in XSL-FO). Unknown names in `genericFonts` are now an error (they used to be treated as `sans-serif`)
- **CLI**: reads references given as `file:` URLs; `--no-fetch-styles` disables fetching CSS; `--page-size <size>` changes the default paper for HTML (`A5`, `"A5 landscape"`, `148mm,210mm`; the same as `pageSize` in the API)
- **Page number references inside flex items**: the box of a flex item that contains `target-counter(…, page)` (such as the `::after` of a table-of-contents line) now fits the digits of the number as typeset. It used to be one digit wide, so with `word-break: break-word`, `overflow-wrap: anywhere` and the like a two-digit number broke into "1 / 0" and the table of contents grew longer
- **`createFileResolver`** (`kumiori/node`): `root` accepts a list of directories. Containment is checked on the real paths after resolving symbolic links (a link inside the root could be used to read a file outside it; the checks for another drive on Windows and for file names starting with `..` are also fixed)
- **Security** (protection when typesetting documents written by others):
  - Link actions in the PDF are limited to safe ones. By default only destinations inside the document, URLs with the schemes `http`, `https`, `mailto` and `tel`, and relative references to PDFs (GoToR) are written. Other schemes (`javascript:`, `data:`, `file:` and so on), actions that open a relative non-PDF file (Launch, including `.html`), absolute paths to PDFs and `//host/…` are typeset as plain text without an action and reported in a warning. To get the previous behavior, use `links: { schemes: ['*'], launch: true }` in the API or `--link-schemes '*' --link-launch` on the command line. Schemes are read the way browsers do, after removing leading and trailing control characters and tabs and newlines anywhere (`java<TAB>script:` is dropped too). The same applies to links, bookmarks and form submit targets in XSL-FO
  - A file attachment annotation (`axf:annotation-file-attachment` in XSL-FO) now attaches only files passed in `files` (for the command, files in the input directory). Resources collected by following references (`file:` files returned by `resolveResource`, CSS and fonts fetched from the network) are never attached. An attachment copies the bytes of a file into the PDF as they are, so when collected resources could be attached too, a document written by someone else could, with the default settings, copy files of the machine that typesets it (`file:///etc/passwd`) or responses from the internal network (`http://169.254.169.254/…`) into the output PDF, by making another reference (`<link>`, `url()`; even one written inside an XML comment is picked up) collect them
  - Parentheses in PDF strings are escaped: the name after `#` in a link to a relative PDF (GoToR) and the name of an attached file were written into literal strings as they were, so a `)` could close the string and add entries (`/S /JavaScript /JS (…)` and so on) to the action dictionary, bypassing the link restriction above. For file names the same was possible with characters whose low 8 bits are a parenthesis (U+0128, U+0129). A file name with non-ASCII characters (`資料.pdf`) is now written as a file specification dictionary (ISO 32000-2 §7.11.3, with the Unicode name in `UF`), and the name of a named destination as UTF-8 bytes (before, only the low 8 bits of each character were written, and links to PDFs with Japanese names could not be opened)
  - Node command: control characters in warnings and error messages (escape sequences and line breaks written in the document) are printed in a visible form such as `\x1b`, so that a document written by someone else cannot rewrite the screen or the title of the terminal of the person who typesets it, or forge report lines
  - The allow function passed to `fetchImages` / `fetchStyles` is also asked about redirect targets. On Node, redirects are followed one hop at a time and no request is sent to a target that is not allowed (up to 20 hops). A redirect from `https:` to `http:` is not followed even with the default (`true`). In browsers the request does reach the redirect target, and the response is discarded if the target is not allowed (browsers do not expose the target beforehand)

  - Limits on EPUB decompression (256 MB per entry: skipped with a warning beyond it; 1 GB in total and 65,535 entries: an error beyond them)
  - `root` of `createFileResolver` is checked on real paths (see the item above)
  - GitHub Actions: the token of the CI workflow is read-only, and the permissions to deploy to Pages and to publish to npm are given only to the jobs that deploy and publish. Publishing now takes the tarball built by the checking job and publishes it from a job that installs no dependencies and runs no scripts

GIFs over the limit are not read; a placeholder frame is drawn with a warning. The VP8, JPEG and one-dimensional CCITT values exceed the most pixels one byte can represent in the standard coding (the fixed probabilities of RFC 6386 §11.2 and §11.4, the Huffman code lengths of T.81, the code tables of T.4). **A large lossless WebP that is entirely (or mostly) one colour, and a blank CCITT image wider than 16,384 pixels, are not drawn when they exceed the limit** (the zero-bit codes of VP8L and the one-bit white rows of T.6 have no density limit in the standards). It is now painted up to the inner edge of the border (the padding rectangle), as the specification says. Only boxes that have both a background color and a border with gaps (dashed, dotted, dot-dash, double, wave) or a transparent color on the same element change (`fo:block`, `fo:block-container`, `fo:table`, `fo:table-cell`, region borders in compatibility mode, and so on). Boxes with opaque solid or 3D-style (`groove`, `ridge`, `inset`, `outset`) borders and boxes without borders are unchanged. With rounded corners (`axf:border-radius`) the background corners follow the inner curve of the border. The parts that overlap the outer border of a collapsed-border table are not changed yet (backgrounds of inline boxes, `fo:inline`, are also painted up to the padding rectangle, as described in a separate item above)
- **Content written after `</body></html>`** (HTML; the Node command and the API; **the result changes**): elements and text written after `</html>` (or `</body>`), as in `<html><body><p>a</p></body></html><p>b</p>`, were dropped. They are now laid out as a continuation of body, as browsers do (the "after body" and "after after body" insertion modes of the HTML Standard). Comments after the end, and whitespace at the end of the document, add nothing, as before
- **Positive left and right `margin` on inline boxes and line wrapping** (HTML; **the result changes**): the left and right `margin` of a `display: inline` box (`span` and so on) is no longer separated from the first and last characters of the box (CSS 2.1 §9.4.2, CSS Text 3 §5.5: a line is broken outside the margin edge of the box). Before, the end `margin` could be left at the start of the next line, shifting the first character to the right (setting `一二三四<span style="margin-right: 30pt">五</span>六七` five characters wide shifted 六 by 30pt), the start `margin` could be left at the end of the previous line, an empty line was added at the end of a paragraph, and a full stop could come to the start of a line. Now, when the `margin` does not fit on the line, the character moves to the next line with it (as in browsers). An inline box with `box-decoration-break: clone` also gets its left and right `margin` on each fragment (CSS Fragmentation 3 §5.4). Only with the AH Formatter compatible style (`--style ah`), a start `margin` that comes to the start of a wrapped line is dropped (as in the reference output). Inline boxes without `margin`, negative `margin`, and `space-start` / `space-end` in XSL-FO are unchanged
- **Heading of the conversion report on the screen**: the report said "XSL-FO 変換レポート" (XSL-FO conversion report) even for HTML documents (EPUB included); the heading now follows the kind of document ("HTML 変換レポート" for HTML; the hint for images not found and the line shown when nothing is unsupported also follow the kind of document)
- **`@font-face` fonts of a previously opened document staying on the screen (Kumiori in the browser)**: when HTML documents that use the same `font-family` name for different font files were opened one after another, the later document was set in the font of the earlier one (and a bold face that only the earlier document had could be used for bold text in the later one). Each time a document is opened, its `@font-face` files are now registered again and faces that only the previous document had are removed (including the fonts registered with the browser). Re-laying out the same document after changing a setting does not reload the fonts. The Node command and the API already keep fonts separate per document and are unchanged
- **Kerning in content-size estimates (max-content, min-content)** (HTML): content widths such as those of flex items (children of `display: flex`) were estimated without kerning, so runs that kerning widens (such as "2.2" in some fonts) did not fit the item's width and split into "2." and "2" with `overflow-wrap: break-word`. The estimate now adds the same kerning to the same character pairs as line layout does (following `font-kerning` and the "kern" setting of `font-feature-settings`). **Results change** (boxes sized by their content, with kerned Latin text, get slightly different widths)
- **XSL-FO: `background-color` on `fo:simple-page-master` is read only in compatibility mode (`--compat antenna`)**: the background properties do not apply to `fo:simple-page-master` (XSL 1.1 §6.4.13), so in specification mode (the default) it is not read and the load warnings report it. **Results change for documents typeset in specification mode** (a background color written on the page master no longer appears). `axf:background-color`, whose name carries the prefix, is read in every mode
- **PDF: the original text (ActualText) attached to words in right-to-left scripts (Arabic, Hebrew) is now written in reading order** (ISO 32000-2 §14.9.4: replacement text is the characters equivalent to what a person sees). It used to be written in drawing order (left to right). **Text extracted from the PDF changes**: in the Chrome and Edge viewers (PDFium) the characters of each word now come out in reading order (they were reversed); poppler's pdftotext and MuPDF also reorder ActualText characters, so their words now come out reversed (they used to be in reading order). The appearance does not change
