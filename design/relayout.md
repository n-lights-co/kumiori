# 組み直しを速くする設計の覚え書き (少し直した文書を組み直す)

レビュー台帳の API-04 の、調べと設計の覚え書きです (ブランチ `claude/api-04-relayout-profile`)。
組版の仕組みはまだ変えていません。実装を main に入れるのは、利用者がこの覚え書きを見て、進め方を決めてからです。
この覚え書きは、リリースする文書 (`docs/` など) ではありません。

## 1. 測り方

- 道具: `scripts/profile-relayout.mjs` (このブランチで足したもの)。`createTypesetter()` の器を 1 つ作り、同じ文書を何度も組む。
  - 名前を残し、ソースのファイルごとに分けたビルド (`.cache/profile-build`) を vite で作り、Node の CPU プロファイル (node:inspector) の標本を、
    スタックの外側の関数 (段階) と、いちばん内側のファイル (中身の種類) で分けて数える。
  - 組み直しの回 (`LayoutEngine.layoutOnce`) は、プロトタイプを包んで、回ごとの時間を測る。
  - `renderPage` は、Node に canvas が無いので、何もしない 2D の文脈で呼ぶ (描く命令を作る JS の手間だけ。画素にする手間は入らない)。
  - `--edit` で、2 回目からは文書の中ほどの段落 (`<p>`・`<fo:block>`) に字を足して組む。`--diff-pages` で、ページごとの SVG を前の回と比べる。
  - `--share-measurer` は試し: 字の測りの覚え (`Measurer` の書体ごとの表) を文書をまたいで使い回したときの速さを、道具の中だけで差し替えて測る。
- 文書 (どれも、書体の読み込みが済んだ器で組む):

| 名前 | 中身 | 大きさ | ページ |
|---|---|---|---|
| html-spec | HTML と CSS 編の対応仕様説明書 (`docs/conformance/html`。見本の展開をしたもの) | 421KB・ファイル 43 | 151 |
| fo-spec | XSL-FO 編の対応仕様説明書 (`docs/conformance/fo`。page-sequence 7) | 760KB・ファイル 14 | 103 |
| css-print | 『CSSページ組版入門』第 4 版 (`--style ah`。書体は zip の中の源ノ角ゴシック・源ノ明朝。見本と同じ MS 明朝などには差し替えていない) | 339KB・ファイル 89 | 142 |
| fo:color-named-1 など | アンテナハウスのサンプル FO 集で大きいもの | 〜220KB | 5〜7 |

- 機械: このクラウドのコンテナ (Node 22.23)。回ごとの揺れが ±10% ほどある。プロファイルを取ると 2〜3 割遅くなるので、全体の時間は
  `--no-profile` の値、段階の割合はプロファイルの値で見る。

- 字を 7 字足しても 120 字足しても、時間は変わらない。**1 段落を直しても、全体を初めから組み直している** (読み込み・カスケード・組版・エリアツリーの全部)。
- 組み直しの 2 回目の回 (ページ番号の参照の確定) は、もう前の回の page-sequence を使い回している (`SeqMemo`)。
  HTML は page-sequence が 1 つなので、2 回目の回はページの柱と参照の字の差し替えだけで軽い (0.2 秒)。
  fo-spec は目次の page-sequence を組み直すので 1.1〜1.2 秒かかる。
- 画面の描画 (`renderPage`) は 1 ページ 20〜30ms ほど。プレビューで見えるページだけを描くなら、組み直しの時間に比べて小さい。
- PDF の書き出し (`toPdf`) は 1.6〜3 秒。プレビューでは呼ばないので、組み直しの速さの目標からは外す。

## 3. 使い回せるもの

速さの見込みは、html-spec の 2 回目からの typeset (約 13 秒) に対する値。「危うさ」は、使い回すと、使い回さないときと結果が変わりうる場合。

| # | 使い回すもの | 見込み | 危うさ (結果が変わる場合) と、その防ぎ方 |
|---|---|---|---|
| R1 | 読んだ CSS の構文の木 (`parseCss` の結果) を、CSS の文字列で覚える | 〜20ms (小) | 構文の木を後で書き換える処理があれば、覚えた木が汚れる。凍らせるか、写して渡す。危うさは小 |
| R2 | `@font-face` の書体の解析 (`LoadedFont`) を、書体のバイト列の SHA-256 と記述子 (family・weight・style・unicode-range など) で覚える | 〜600ms (`@font-face` の多い文書) | `LoadedFont` は可変の欄を持つ (`metricsLineHeight`・可変フォントの実体など)。文書ごとの指定で欄を変えるものは、覚えたものを写してから変える。FontManager の `generation` を上げて、行分けの覚えを古くする。危うさは小〜中 |
| R3 | 画像を読んだ結果 (`AssetStore` の中身: 大きさ・SVG に直したもの・画素) と画像の SHA-256 を、バイト列の SHA-256 か、名前・大きさ・中身の比べで覚える | 〜100ms (読み) + 〜500ms (SHA-256。画像の多い文書) | 画像の中身の比べ (SHA-256 を計算すると、覚えの意味が薄い)。器が前の文書の `Uint8Array` と同じものを渡されたときは、その場で当てられる。違う配列なら、長さと中身の比べ (memcmp は SHA-256 より桁違いに速い) で当てる。SVG の画像は、中で使う書体・`resolveResource` の答えで結果が変わるので、それらも鍵に入れるか、SVG は覚えない。危うさは中 |
| R4 | 字の測りの覚え (`Measurer` の表) と、書体を引く覚え (`FontManager` の `getForChar`・`forCharMemo` など) を、器で持つ | `Measurer` の表は試しで差が見えない (揺れの中)。書体を引く覚えは〜100ms | 鍵は `LoadedFont` (器の書体は文書をまたいで同じもの)。文書ごとの書体は別の `LoadedFont` なので当たらない。書体を引く覚えは、文書ごとの書体・別名・`unicode-range` で答えが変わるので、文書ごとの書体の並びが同じときだけ使う。危うさは小 |
| R5 | 段落の行分けの結果 (いまの `lineMemos`) を、中身で覚える (いまは子の配列そのもので覚えるので、文書を読み直すと当たらない) | 行分け + 字の測りの大部分: 〜3〜4 秒 (組版の 4〜5 割) | 鍵に、行分けを変えるものをすべて入れる: 字の並び・行の中の箱の種類と大きさ・字のスタイル (`ResolvedStyle` の全部の欄)・行の長さ・最初の行か・書字方向・分綴の辞書・書体の登録の版 (`Measurer.version()`)・互換の指定 (`kernAh` など)。ページ番号の参照・脚注・画像・行内のコンテナは、いまと同じく覚えない (`hasDynamicInline`)。鍵を作る手間 (中身のハッシュ) が、当たらないときの損になる。いまの覚えの比べ (`sameStyle` の JSON の比べ) を、スタイルの指紋 (読み込みで 1 度作る) に替える。危うさは中 |
| R6 | 前の組版の page-sequence (いまの `SeqMemo`) を、文書をまたいで使い回す。page-sequence の中身 (`LPageSequence` の木) の指紋が同じで、始まりの条件 (開始ページ・左右・脚注の続き番号・参照したページ番号の値) が同じなら、前のページをそのまま使う | page-sequence の多い FO の文書: 直していない page-sequence の分 (fo-spec では組版の半分以上)。HTML は名前付きページで分けない限り 1 つなので、効かない | いまの `SeqMemo` の決まり (組み直しの回の中で使い回すもの) を、そのまま文書をまたいで使う。page-sequence の木の指紋に、組版に効く欄の全部 (`LDocument` の文書全体の設定・ページのマスターを含む) を入れる。前の組版の `PageBuild` を持ち続けるので、メモリが増える (`lowMemory` では使わない)。危うさは中 |
| R7 | 前の組版の、変わらないページ。変わった所の前のページはそのまま使い、変わった所から組み直し、改ページの位置と組版の状態が前の組版と揃ったら、残りのページを前の組版から繋ぐ | 組版の 9 割 (ページの 95% は同じ): 〜6〜7 秒 | 次の 4 で詳しく書く。ページの境目の組版の状態 (Flow の中のどこまで組んだか・続きの断片・浮動・脚注の持ち越し・マーカー・カウンター・keep の連なり・表の見出しの繰り返し・段の釣り合わせ・最後のページのマスター) を、比べられる形で持つ必要がある。比べられない状態があれば、その page-sequence は全部組み直す。危うさは大 |
| R8 | 読み込み・カスケードの差分。前の文書の DOM と新しい DOM を比べ、変わらない要素の計算済みのスタイルと `LDocument` の部分木を使い回す | 読み込みの 6〜7 割: 〜3 秒 | セレクターには、字や兄弟に依るもの (`:empty`・`:nth-child`・`:has()`・`+`・`~`) と、カウンター・`attr()`・`string-set`・`content` がある。字だけが変わった直し (エディタで多い) なら、要素の木の形が同じなので、`:empty` と、字に依るもの (`::first-letter`・`::first-line`・`text-transform` の結果など) を除いて、スタイルは変わらない。要素の木の形が変わったら、その親から後ろの兄弟まで計算し直す。危うさは大 (セレクターの依り先を漏らすと、見えにくい誤りになる) |
| R9 | PDF の書き出し (書体の部分集合・画像の圧縮) を、書体・字形の集まりや画像ごとに覚える | toPdf の一部 (〜0.5〜1 秒) | プレビューでは使わないので、後回しでよい |

- GC (1〜2.7 秒) は、組み直すたびに作る節 (字形の節・行の節・Area) の分。R5〜R7 で作り直す節が減れば、GC も減る。

## 4. 「変わったページから後ろだけ」を組み直すときの難しさ (R7)

1. **どこが変わったか**: 前の `LDocument` と新しい `LDocument` を、上から比べて、最初に違う節と最後に違う節を見つける。
   読み込みを差分にしない (R8 をしない) ときも、`LDocument` の比べは、組版より桁違いに軽い (木をたどるだけ)。比べる欄は、組版に効くものすべて。
2. **どこから組み直すか**: 前の組版で、最初に違う節を含むページの、1 つ前のページの終わりの状態から組む。
   その状態を取っておくには、Flow が「ページの終わりで止めて、続きから組める」形になっている必要がある。いまの Flow は、文書の木を再帰でたどりながら組むので、
   途中の状態は呼び出しのスタックの中にあり、取り出せない。page-sequence の初めから組み直し、変わった所の前のページまでは、組んだ結果を捨てて前の結果を使う、
   という形 (速さは半分ほど) なら、Flow を変えずにできる。
3. **どこで前の組版と揃うか**: 組み直したページの終わりで、「次に組む節と、その中の位置」「持ち越しの脚注・浮動」「マーカー・カウンター」「keep の連なり」が、
   前の組版の同じ所の状態と同じなら、そこから後ろは前の組版と同じページになる。ページ番号は、ページ数がずれていれば違う値になるので、揃ったと見るのは、
   ページの番号 (と左右) も同じときだけ。違えば、後ろの page-sequence まで組み直す。
4. **相互参照**: 揃った後のページでも、目次・索引・`target-counter()`・`page-number-citation` の値が変わることがある (2.3 の目次・索引のページ)。
   いまの組み直しの回の決まり (参照の値が同じ page-sequence は使い回し、違えば字だけ差し替えるか組み直す: `reuseCites`) を、ページの単位に広げる。
5. **ページの柱など**: いまも組み直しの回ごとに全部のページの柱を組む (`sheetStatics`)。柱は、ページ番号・マーカー・総ページ数で変わる。
   マーカーと番号が前と同じページの柱は使い回せる。
6. **確かめ方**: 使い回したときと、使い回さないときの組版を、同じ文書で組み比べ、エリアツリーが同じことを確かめるテストを置く
   (対応仕様説明書・見本の FO・CSS-Print を、ランダムな所で直しながら組み比べる)。違えば、使い回しの側の誤り。

## 5. 段階に分けた案

| 段階 | 中身 | 見込み (html-spec。2 回目からの typeset 約 13 秒) | 手間 | 危うさ |
|---|---|---|---|---|
| 1 | 器で覚える: R1 (CSS の構文の木)・R2 (`@font-face` の書体)・R3 (画像と SHA-256)・R4 (字の測りと書体を引く覚え) | 〜1 秒 (1 割弱。`@font-face`・画像の多い文書ほど効く) | 小 | 小 |
| 2 | 段落の行分けを中身で覚え、文書をまたいで使い回す (R5)。スタイルの指紋を読み込みで作る | 〜3〜4 秒 (組版の 4〜5 割) | 中 | 中 |
| 3 | page-sequence を中身の指紋で、文書をまたいで使い回す (R6) | FO の章ごとの文書で大きい。HTML は効かない | 中 | 中 |
| 4 | 変わったページから組み直し、前の組版と揃ったら繋ぐ (R7)。初めは「page-sequence の初めから組み、変わった所の前までは捨てる」形 | 組版の 5〜9 割 (〜4〜6 秒)。前を捨てる形では半分ほど | 大 (Flow を、ページの境目で止めて続けられる形にするところまで行くなら、さらに大) | 大 |
| 5 | 読み込み・カスケードの差分 (R8) | 読み込みの 6〜7 割 (〜3 秒) | 大 | 大 |

- 段階 1〜2 で 13 秒 → 8〜9 秒、段階 4 まで行くと 13 秒 → 6 秒ほど (読み込みが残る)、段階 5 まで行くと 2〜3 秒ほどの見込み。
- 段階 4 を入れても、読み込み・カスケード (4〜5 秒) が残る。段階 4 と 5 は、組で入れて初めて、長い文書のプレビューが「打つたびに組み直す」速さになる。
- 段階 1〜3 は、使い回しの鍵の比べで、使い回さないときと同じ結果を保てる (鍵の作り方の誤りが危うさ)。段階 4・5 は、組版の状態の比べを漏らすと、
  見えにくい誤り (直していない所のページが崩れる) になるので、4 の 6 の組み比べのテストを先に置く。
- 速さの別の道 (組み直しの仕組みと組み合わせられる):
  - **見えているページまでを先に返す**: プレビューで見ているページまで組んだら、その分を先に返し (参照の値は仮のまま)、残りを続けて組む。
    直した所が後ろの方にあると、効きは小さい。
  - **古い組版を止める**: 打つたびに組み始めるとき、前の組版を途中で止める (`AbortSignal`)。待ち時間は減るが、1 回の組版は速くならない。
- メモリ: 段階 3・4 は、前の組版の途中の木 (`PageBuild`) を持ち続けるので、文書 1 つ分ほど増える。器の設定で切れるようにする
  (`lowMemory` の組版では使わない)。

## 6. 利用者が決めること

1. どこまで進めるか
   1. 段階 1 だけ (小さく、危うさも小さい。1 割ほど速くなる)
   2. **段階 1 と 2 (おすすめ)**: 危うさを抑えたまま、組版の 4〜5 割を減らせる。段階 4・5 の前に、組み比べのテストの土台も作れる
   3. 段階 4 まで (組版の大部分を使い回す。Flow の作り替えが要る)
   4. 段階 5 まで (読み込み・カスケードの差分まで。いちばん速いが、いちばん大きく、危うさも大きい)
2. 使い回しの入れ方
   1. **既定で使い回し、器の設定で切れる (おすすめ)**: 使い回しは結果を変えない前提なので、既定で速くする。誤りを疑うときに切って比べられる
   2. 器の設定で頼んだときだけ使い回す (既定は今と同じ)
3. API の形 (段階 3 以降)
   1. **器が前の組版を覚え、`typesetter.typeset(text)` をそのまま速くする (おすすめ)**: 使う側は変わらない。前の結果を持つ分のメモリは、器を作るときの設定で切れる
   2. 前の結果を明示して渡す (`typesetter.typeset(text, { previous: result })`)。複数の文書を 1 つの器で交互に組む使い方でも当たる
4. 先に入れる別の道 (組み直しの仕組みとは別に)
   1. **入れない (おすすめ)**: まず組み直しを速くする
   2. 見えているページまでを先に返す
   3. 古い組版を止める (`AbortSignal`)
   4. 2 と 3 の両方

## 7. 段階 1 と 2 の実装 (2026-11-21)

利用者の決め (2026-11-20): 段階 1 と 2 まで進める・既定で使い回し、器の設定 (`createTypesetter({ reuse: false })`) で切れる・
API の形は器が覚える (段階 3 以降のための決め)・先に入れる別の道は無し。

### 7.1 入れたもの

- 段階 1 (器で覚える): **書体のファイルの下ごしらえ** (`FontManager.registerBuffer` の初めの WOFF・WOFF2 の戻し・集まりからの取り出し・
  表の確かめ・CFF2 の作り直し) を、ファイルの中身で覚える (`fontManager.ts` の `FontPrepCache`)。鍵はファイルの長さと短いハッシュで、
  当たったら覚えた元の中身とバイトごとに比べる。知らせの文 (表を直したこと・CFF2 を直せなかったこと) は、登録のたびに、その登録の名前で出し直す。
  下ごしらえの後のバッファが文書をまたいで同じになるので、エリアツリーの書体の SHA-256 (`areaResources.ts`。バッファごとに覚える) も計算し直さない。
  - fontkit の書体 (`fk`) は使い回さない。`fk` には、書体ごとの知らせの出し先 (`FONT_NOTICE`)・1 度だけ出す知らせの印・読みの予算 (`fontSanity.ts`) が付くので、
    使い回すと、2 つ目の文書の警告が抜け、読みの予算が文書をまたいで減る。
  - 2 の R1 (CSS の構文の木)・R3 (画像) は入れていない: 測ると、CSS の読みは 1 回 10〜20ms、画像の読みは 100ms ほどで、
    エリアツリーの SHA-256 (0.5 秒) は画像ではなく `@font-face` の書体のものだった (書体の下ごしらえの使い回しで、合わせて消えた)。
    R4 (`Measurer` の表) は、2.4 の試しで効かなかった。
- 段階 2 (段落の行分けを中身で覚える): `layoutEngine.ts` の `SharedLineMemo`。いまの行分けの覚え (子の配列で引く `lineMemos`) に当たらないとき、
  行の中身と書式 (`JSON.stringify` した子の並びと `ResolvedStyle`)・行の長さ・最初の行か・書字方向・中身の幅を測る組版か・block の入力の節の番号・
  互換のカーニング・XSL の空白の扱い・字の測り方を鍵にして引く。
  - 当たるのは、書体の組の印 (`FontManager.signature`: 登録した書体の鍵・名前・太さ・傾き・幅・書体のファイルのバッファの番号・欧文の書体・別名・
    総称の書体の並び・範囲の指定。並びも含む) が同じときだけ。覚えた結果の中の書体 (`LoadedFont`) は、覚えた文書の書体の組のものなので、
    いまの組の同じ鍵の書体に差し替える (置き場所を覚えるときに集めておく)。可変フォントの軸の値の実体を使った結果は覚えない。
  - 覚えないもの: いまの覚えと同じ (組む状況で中身の変わる子 (ページ番号の参照・脚注・画像・行内のコンテナ)・行内の箱・脚注の参照)、
    回り込みのある所、関数の欄を持つ中身、メモリ節約の組版 (`lowMemory`。PDF を書く間に組むので、組み終える前にほかの文書の組版が書体を差し替えうる)。
  - 持つのは、いまの文書と前の文書で使ったものだけで、大きさの上限 (`SHARED_LINE_MEMO_ATOMS` = 100 万。メモリ約 400MB) に達したら、新しい段落は覚えない
    (0.6.0 では古く使ったものから捨てていた。上限より大きな文書 (表の多い 89 ページの `gen:table` で、セルの段落と列の幅を測る組みの約 8,000 件) を
    頭から組み直すと、次に使う段落から順に捨てるので、文書をまたいで 1 つも当たらず、鍵を作る・覚える・持ち続ける (GC) 手間だけがかかって、
    使い回さないときより 2 割ほど遅かった。覚えないようにすると、上限までの前の方の段落 (`gen:table` で約 4,600 件) が当たり続ける)。
    ただし、上限に掛かったとき、いまの文書で 1 つも当たっていなければ (器が別の文書に移った)、前の文書の項目を古く使ったものから捨てて覚える
    (捨てないと、前の文書の段落が残り続けて、使い回しが 1 文書遅れて始まった。0.7.0)。
  - 覚えの鍵には、段落を包むブロックの入力の番号も入れる (0.7.0。D-073。入れないと、keep の試し組みなど包むブロックの違う組みで作った覚えを
    本番の組みが使い、ブロックの直下の字の `sourceRef` が抜けた)。
- 組み比べの試験: `test/reuse.test.ts`。使い回す器と使い回さない器で、少しずつ直した文書の並び (HTML: 見出しと目次のページ番号・脚注・ルビ・等幅・
  `@font-face` の WOFF2・縦書き・表・分綴。XSL-FO: page-sequence 2 つとページ番号の参照) を組み、警告・領域の木・PDF のバイト列が同じことと、
  使い回しが当たったことを確かめる。`typesetToPdf` (メモリ節約を含む) も比べる。
  大きい文書は、測る道具の `--check-reuse` で確かめた: 対応仕様説明書 (HTML・XSL-FO) と CSS-Print を 1 段落ずつ直しながら 4 回組み、
  どの回も、領域の木と警告は同じ。PDF のバイト列は、2 回目からは同じ。1 回目は、比べる相手が「器の初めの文書」と「器の 2 つ目の文書」になるので違う。
  これは使い回しによらない: `reuse: false` の器でも、初めの文書と 2 つ目の文書で、同じ文書の PDF のバイト列が違う
  (初めの文書を組む間に、等幅などの書体を器に足すので、書体の並びが変わる。前からのこと)。

### 7.2 速さの前後 (プロファイルなし。1 段落 (120 字) を直しながら 5 回組む。ミリ秒)

| 文書 | reuse: false (2〜5 回目の typeset) | reuse (既定) |
|---|---|---|
| HTML の対応仕様説明書 (151 ページ) | 12,060〜12,780 | 2 回目 13,270 (使い回せない)・3〜5 回目 9,080〜9,220 (約 −27%) |
| XSL-FO の対応仕様説明書 (103 ページ) | 4,090〜4,120 | 2〜5 回目 3,120〜3,510 (約 −20〜25%) |
| CSS-Print (142 ページ) | 10,060〜10,630 | 3〜5 回目 10,090〜10,730 (別に測った組で 9,040〜9,390 と 9,360〜9,580。差は揺れの中ほど) |

- HTML の 2 回目 (初めの直し) で使い回せないのは、初めの文書を組む間に等幅の書体 (Cousine) を器に足すので、2 つ目の文書から書体の組の並びが変わり、
  印が違うため (代わりの書体を探す順は、登録の並びで決まる: `FontManager.fallbackOrder`。並びの違う組の結果は、使い回すと結果が変わりうる)。
  3 つ目の文書からは並びが同じになる。
- CSS-Print が速くならないのは、行内の箱 (背景・枠のある行内の要素・画像) のある段落が多く (引いた 1 万 2 千回のうち 7 千回あまり)、
  それはいまの覚えでも覚えない段落だから。CSS-Print の組版は、ページ分け・ブロック (2.6 秒) と、行内の箱のある段落の行分けが多い。
- メモリ (`--expose-gc` の後のヒープ): CSS-Print 約 200MB → 約 390MB、HTML の対応仕様説明書 約 265MB → 約 390〜535MB。
- toPdf・renderPage の時間は変わらない (揺れの中)。

### 7.3 残ったこと

- HTML の初めの直しを速くするには、等幅などの書体を、初めの文書の前から器に入れておく (書体の並びを初めから同じにする) 必要がある。
  初めの文書の組版の結果が変わりうるので、入れていない。
- CSS-Print のような、行内の箱の多い文書を速くするには、行内の箱を覚えに入れる (箱の中身の組版の結果を、箱の中身で鍵にする) 必要がある。
- 段階 3〜5 は、利用者の決めのとおり、まだ入れていない (下の 8 のとおり、段階 3・4 は 0.7.0 で入れた)。
